**The rules, as built** — gamma's numbers unchanged, per email address:

| Flow | Short | Long |
|---|---|---|
| Login (`LOGIN_FAIL`) | 5 in 10 min | 10 in 24 h |
| Reset (`RESET_REQUESTED`) | 3 in 60 min | *none* |

Reset having no long rule is deliberate, not an omission: guessing
passwords is only useful if you can keep guessing, so the patient
attacker is a real threat and the 24-hour rule exists for him. Requesting
reset links gains an attacker nothing however long he waits — the link
goes to the student's inbox. The 60-minute rule stops inbox flooding, and
flooding spread over a day is not flooding.

**⭐ SAM'S QUESTION CHANGED THE SHAPE OF THE SLICE.** *"Was gamma doing
the check by email alone? I think it was doing plus device too."* It was
— and reading gamma's SQL rather than our own summary of it turned up
something the doc had glossed: **gamma's `fp_hash` axis carries no email
filter**, so the two axes are not one rule applied twice. The email axis
catches many attempts on ONE address (credential stuffing on a known
target); the device axis catches ONE machine failing against MANY
addresses (a spray). Dropping the fingerprint doesn't weaken the email
rule — it removes the only rule watching a different door. Turnstile is a
**better** substitute than fingerprinting, because the native Supabase
integration also binds the direct auth endpoint our server actions never
see — ⚠ **but only once 2d ships.** Named at the top of
`lib/auth/thresholds.ts` so it cannot quietly become permanent.

**Three deliberate departures from gamma:**
- ⭐ **It fails OPEN.** A broken count query lets the caller through.
  Closed is the instinctive choice and the wrong one — it converts a
  database blip into "nobody can sign in", far worse than ten minutes
  without rate limiting. `domain-and-identity.md` already promised this.
- ⭐ **The countdown reads the Nth-newest row, not `MIN()`.** Gamma
  computes from the oldest attempt in the window, which is right only
  when the count sits exactly on the threshold; with 7 failures against a
  limit of 5 it says "2 minutes", she returns, and she is refused again.
  **A countdown that lies is worse than no countdown**, and the countdown
  is the entire reason this is a rule rather than a flat refusal. Also
  cheaper: 10 rows and one query, where gamma runs two counts over
  everything.
- **No device axis** (above).

**Verified on dev by driving the forms, not by trusting the tests.** 5
failures → 6th refused, *"Try again in 7 minutes"*; three further
attempts left it at 7 minutes, proving **a refusal never feeds the limit
that produced it** (`*_BLOCKED` are separate event types, so the
exclusion is a fact in the data rather than a rule each query remembers).
Reset: 3 requests → 4th refused at 59 minutes. Timeline read back from
the table each time.

**⭐ SAM CAUGHT THE UNTESTED BRANCH:** *"we didn't test the 24 hour
gate."* True — it had only ever run in unit tests. Tested properly by
seeding nine failures **two hours apart**, which makes the 10-minute rule
impossible to trip: the tenth attempt failed normally, the eleventh was
blocked with `reason=threshold_24h` and "about 6 hours". ⓘ **No bug was
found — the code was already correct.** What the exercise exposed was two
assumptions that would fail *silently*, now pinned by tests and
mutation-checked (`Math.max`→`Math.min`, `limit(10)`→`limit(9)` each fail
exactly one test): the fetch cap must equal the deepest threshold, and
the lookback must span the widest window — scoped to 10 minutes, the
24-hour rule becomes permanently unreachable.

**⭐ THEN SAM WALKED THE TIMELINE AND FOUND THE REAL DESIGN HOLE.** Five
failures, a 20-minute wait, then more — *"when they wait and try after
10mins they can't get in because the 24 hour takes effect?"* Run against
the shipped rules: yes. Both rules trip together on the tenth failure and
the code reports whichever holds her longer, so the block she meets is
not the 10-minute one she is expecting — it is **23½ hours, anchored to
her first failure**. His reading of it was sharper than the framing that
preceded it: someone who has failed that many times has genuinely
forgotten their details, so *"come back in about 24 hours"* is not the
wrong duration, **it answers the wrong question**. So the long block now
offers `set a new password instead`, linked and pre-filled with the
address she typed — it works immediately, because the reset limit is a
separate counter her failed sign-ins never touched. ⭐ **The 10-minute
block deliberately does NOT offer it:** there, waiting really is the
right advice, and pushing a reset at someone one typo away creates work
she didn't need. Closed with a Sam copy pass — two sentences made the
link read as an afterthought, so it became one: *"Try again in about 6
hours **or set a new password instead**."*
⚠ Mechanically the action leaves that sentence **unterminated** and the
form closes it after the link; the short branch punctuates itself. Both
branches re-verified, since that change could silently have stripped the
short block's full stop.

**Known behaviours, flagged not fixed** (both also true of gamma):
- **A successful login does not clear the failure counter.** Four fails,
  a success, then one more fail inside the window still counts as five.
  Reachable mainly on the 24-hour rule across a long day. Fix if wanted:
  count only failures since the last success.
- **The 24-hour rule can catch a real student**, not just an attacker.
  She is never stranded — reset is a separate counter — which is exactly
  why the reset offer above matters.

On-machine session, branch `claude/session-adb488`. **5 commits**, ONE

**The top auth gap is closed.** Before today a student who forgot her
password was locked out permanently short of manual admin intervention —
no page, no `resetPasswordForEmail`, no link on the login form.

**Slice 2a — the logbook.** `nclex_auth_events`: one append-only row per
login, registration, invite acceptance, reset or code request. Shipped
BEFORE the flow it serves, because **logs cannot be captured
retroactively** — the table has to exist before the support case does.
⭐ **Append-only is enforced, not remembered:** one SELECT policy for
`USERS_MANAGE` and no insert/update/delete policy for anybody, so the
database refuses rather than trusting future call sites. Writes go over
the top via the service-role client, which is required anyway — the most
important row here is a FAILED login, and a failed login has no session,
so `auth.uid()` is NULL and no policy could ever admit it. Every future
event type is already in the CHECK constraint, so slices 3 and 5 need no
migration. 90-day retention on pg_cron, window in `nclex_config`.

**⭐ SAM'S CATCH RESHAPED THE DESIGN, AND IT WAS RIGHT.** Reading the
first `LOGIN_FAIL` rows he said: *"what the student sees on the form and
what admin will see later can be different — admin could know that this
one email does not exist while this one existed but it was password."*
The analysis had conflated two things. **The anti-enumeration rule
constrains what the PAGE may say; it does not constrain what we may
KNOW.** An admin sits behind a login, a role check and an RLS policy and
has no reason to inherit a visitor's blindfold. My stated reason for not
looking the address up (an extra query on an attacker-controlled path)
did not survive contact: the failed login has *already* run a
deliberately-slow password hash, next to which an indexed lookup is
noise. So 2b fills `user_exists` on `LOGIN_FAIL` and makes `reason` a
diagnosis — `wrong_password` vs `no_such_account` — while the student
still sees the identical "Invalid login credentials". ⓘ It also stopped
being a reset-only column. ⚠ The answer must never travel back to the
user, or we have rebuilt the enumeration oracle by accident.

**⭐ THE IP DECISION ALSO CHANGED ON SAM'S PUSH** (*"if its simple and
easy to store why not"*). The doc had recommended storing none — but
that recommendation sat next to "no fingerprint hashes", whose reasoning
was *no enforcement → no need to store*, and extending it to the IP
quietly assumed **storing means blocking**. It doesn't. Blocking is the
dangerous half, and specifically for this audience: Ghanaian mobile
carriers put thousands of subscribers behind a handful of addresses, so
a per-IP threshold could lock out a whole network's worth of nurses on a
busy evening. Logging carries none of that, and it is the only axis that
can SEE a spray. **Settled: full IP, logged, no rule on it in v1.**

**Slice 2b — the flow.** `/forgot-password` (always the same "check your
email" screen, whatever the truth), `/reset-password`, the login-form
link carrying the typed address across, and `lib/auth/account-lookup.ts`
shared by both. Also logs the **send's own outcome**, not just the
request — gamma logs only that a reset was asked for, which turns a
support case into *"our log says we did our job, she says nothing
arrived"*. That earned its keep the same afternoon, catching a real
`send_failed` on an `@example.com` address.

**⭐ `/reset-password` TOOK THREE ATTEMPTS, AND THE FIRST TWO WERE BUILT
ON PLAUSIBLE STORIES ABOUT THE LIBRARY RATHER THAN ITS SOURCE.** The
symptom: the email arrived, the link landed, and the page said "this
link didn't work" — for a reset that had **succeeded**, with Sam signed
in behind the error (the dev server log showed `/reset-password?code=…`
then `/router` then `/student/picker`). Sam's own observation identified
it: *"it temporarily shows the correct url then quickly switch to the
reset-password only url"* — that flash **was** the library consuming the
code and tidying the address bar.
- **Attempt 1** passed `detectSessionInUrl:false`. Inert:
  `createBrowserClient` sets that key (and `flowType`, `storage`,
  `persistSession`) **after** spreading caller options, so it was
  discarded silently. The client is also a module-level singleton.
- **Attempt 2** waited for the library on both link shapes. Wrong for
  half of them.
- **Attempt 3, after actually reading `node_modules`, worked:** the two
  shapes need **opposite** handling. `?code=` (PKCE, what real emails
  send) is the library's — never exchange it yourself, the code is
  single-use. `#access_token=` (implicit, admin-generated) the library
  **refuses**: `GoTrueClient` throws `"Not a valid PKCE flow url."`
  under `flowType:'pkce'` and sends that error only to its own debug
  channel, so nothing reaches the console — there you MUST call
  `setSession` yourself.
ⓘ **This also corrected an earlier claim of mine that `/welcome` was
"lucky".** It isn't: it calls `setSession` explicitly and never leans on
URL detection, which is the correct handling for the only shape it ever
receives. Written up in `CLAUDE.md` → Known Workarounds, because slice
3's email-code login meets the same trap.

**⚠ TWO OF THE THREE WRONG DIAGNOSES CAME FROM TESTS THAT NEVER RAN.**
Navigating between two URLs differing **only in the fragment does not
