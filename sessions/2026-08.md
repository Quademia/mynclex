### ⭐⭐ Sam's schema change: the trail had to survive a second decision

Reviewing the CD handoff's drawer, Sam saw that the *"full story"* it
promises could not exist: `decision_reason` is scalar, so a rejection
followed by an approval followed by a suspension keeps only the last. He
proposed making the decision columns a tracker, **without a new table**.

He was right, and the reason is sharper than "it would be nice":
**until 1d no row could carry more than one decision** — every doorway
ends in a single APPROVED or a single PENDING — so the derived trail was
not wrong, it was *sufficient by accident*. 1d is precisely the slice
that ends that.

Settled shape:
- **`decision_history`, an append-only JSONB array** of
  `{at, by, from, to, reason}` — one shape for the whole story, since
  every event including re-application is a status transition.
- ⭐ **The rule banked with it:** *a JSONB array is right while a history
  is short, bounded and read whole; a table is earned the day something
  needs to query across rows.* This keeps §13's rejection of an events
  table intact rather than smuggling it back one slice later.
- ⚠ **The scalars stay authoritative.** They answer "what is true now"
  for the catalogue filter, the RLS and the status index, which need it
  indexable; the array answers "how did we get here".
- ⭐ **ONE SQL statement writes both**, so they cannot drift: the entry's
  `from` reads the row's own status on the right-hand side of the UPDATE,
  where it is still the old value — correct by construction rather than
  by the caller remembering to pass it, and safe against two admins
  clicking at once.
- **Visibility: option (i)** — a tutor can read their own row, so reasons
  are written as if the subject will read them. A column-level SELECT
  revoke was considered and refused: it makes `select *` ERROR rather
  than omit, the invisible-to-tsc failure this repo keeps meeting.

Backfill reproduced exactly what the drawer derived — verified on all 7

### Tutor plans PARKED, deliberately

tiers** (free: 50 students / 1 programme … paid: unlimited), and nothing
in `nclex_products` expresses a quota — every column doing real work
answers *how long* or *how many credits*. ⚠ **The free tier also breaks

the sharp question named — **what happens on downgrade**, when a tutor

live alternative for a market where a fixed monthly USD fee is a barrier
to a tutor with no students yet. ⚠ **Do not model a tutor plan as a
`nclex_products` row just because products exist.** **Nothing in the arc
depends on the answer: the table holds no money.**

### ⚠ Two library contracts, read in the installed source rather than assumed

Both would have failed confusingly, and both were caught before the first run:

  `state` covers CSRF and PKCE binds the code.
- **`access_token` IS sent** with the ID token — Google's tokens carry an
  `at_hash` that `auth-js` checks, and omitting it rejects a good token.

### ✅ Two counters — a promise the code never kept, FIXED

`send.ts` and the outbox migration both promised a quota failure *"must NOT

⭐ **The one-line fix fails**, which is why it took a column: the CONFIG branch

### ✅ A bad API key read as PERMANENT — FOUND AND FIXED the same day

Found while forcing that failure. An invalid key does **not** come back as a key
error: Resend answered `code: validation_error`, `message: "API key is
invalid"`. `validation_error` maps to **PERMANENT**, so the row went **DEAD on
the first failure** and the `invalid_api_key → CONFIG` mapping never fired.

⚠ That defeats the whole reason CONFIG exists — *"EVERY email is failing, and it
drains by itself the moment the key is fixed."* In reality the drain would wake
every five minutes and **kill the queue row by row**, and fixing the key would
drain nothing; each row would need a manual Retry.

⭐⭐ **And the drain is what makes it bite.** Before today nothing re-read a
failed row, so a bad key merely left the queue sitting. Now there is a machine
that will methodically kill it. **Building the drain promoted a dormant
misclassification into an active one** — a shape worth remembering: making a
system actually run wakes its latent bugs.

**✅ FIXED 2026-08-18.** `postToResend` now checks **HTTP 401 before the code
table** and classifies it CONFIG. Probed against the live API first, and the
answer was better than hoped: a **malformed** key, a **well-formed but wrong**
key and an **empty** key all return the identical `401 / validation_error /
"API key is invalid"`. Resend does not distinguish them, so there was no
revoked-key case left to check.

⚠ **The fix is deliberately narrow.** `validation_error` KEEPS its PERMANENT
mapping everywhere else, because it is also Resend's genuine code for a
genuinely broken request (bad from-address, missing field). Reclassifying the
name wholesale would fill the queue with rows that can never succeed and
retry forever — the opposite failure, and the reason PERMANENT exists. The
HTTP status is what separates "our credentials were rejected" from "this
email is malformed".

**Proven, not just compiled**: with a wrong key in `.env.local`, a queued row
came back `FAILED` with a retry a minute out — where before it went `DEAD` on
attempt one. ⭐ And it composes with the strike counter: a key outage spends
no strikes, so a long one cannot quietly exhaust an email's retry budget.
