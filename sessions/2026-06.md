### 1. All-questions filter bar — rebuilt (`1fd601c`)
The `/bank/all` filter bar went from a 6-control GET form (Apply button)
to a **live-apply, faceted** bar. List axes are **multi-select checklists**

trend titles → scenario + chart-tab/kind chips). Deferred fast-follow:
question answer-options in the peek.

### 4. Questions list — two-row card + classification tags

### 1. Case-study publish gate (`fa9e9d1`)
Investigating the bank, found that the student-builder eligibility rule
(`nclex_count_eligible_items` / `_nclex_eligible_unit_pool`) requires a
case to be **published AND builder-visible AND all 6 child questions
individually published**. The post-2026-05-01 per-question-housekeeping
retrofit (which moved the visibility flags onto the questions) left
nothing surfacing the "all 6 published" requirement — so a case could read
"Published" yet silently reach no students. **Confirmed live on dev:** 3
published cases (Parkinson's home safety, Home safety II, TB) had all-draft
questions inside → delivered nothing. Earlier I mis-described this as a
worse bug and as already-fixed; corrected after checking the DB (no hidden
trigger/RPC — the old `nclex_save_case_with_children` cascade RPC is gone).
Fix (Sam's design, refined together): gate the **Publish toggle**, not
Save — drafting/saving stays frictionless. Toggle on with draft questions →
"Publish all & publish case" offer (`publishCaseWithChildrenAction`
publishes the 6 questions then the case); <6 questions → plain block notice.
Repaired all 3 broken cases through the new button (no DB surgery).

### 2. Trend publish gate (`af2a865`)
Checked the sibling trend wrapper. Trend is the **mirror image**: a trend
question is delivered standalone (with its data panel), so it reaches
students only when the **question** is published AND its **dataset** is
published. So the gate is reversed — publishing a *question* checks its
*dataset*. Built: publishing a trend question while the dataset is a draft
→ "Publish dataset & question" offer. (Case = wrapper checks children;
trend = child checks wrapper.)

### 3. Trend wrapper polish (`b463d12`)
- The dataset's **"Visible in builder" toggle is a no-op** for trends —
  verified the delivery code reads the *question's* builder flag + the
  *dataset's published* flag, never the dataset's builder flag. Kept for
  wrapper uniformity (Sam's call) with an inline explainer: "No effect on
  trends — each question sets its own builder visibility."
- New Validate **warning** (gap 1): a published dataset whose questions are
  **all** draft reads "Ready to publish" but delivers nothing — now flagged
  ("none of its N questions are published"). A mix of live/draft is fine
  (incremental publishing intended), so it fires only when none are live.

### 4. Wrapper-list published/draft pills (`bc8f895`)
Each case/trend list row now shows a green/grey "N published · N draft"
breakdown of its questions next to the count, so the "published but reaches
nobody" state is visible at a glance. 4 list pages (admin+tutor × cases+
trends) + new shared `lib/bank/wrappers/question-pills.tsx`. Reuses the
existing `.auth-cs-tag` styles; no CSS/migration.

### Debugging headline — modal-in-card traps (3 layers, same root)

programme card**, which caused three escalating bugs:

### Alignment first (no code until locked)
Sam opened by checking we both remembered last session's decisions. Walked
back through **"Option C"**: an attached note/shelf is a **first-class
`nclex_programme_activities` row** (types `LIBRARY_NOTE` / new `SHELF`)
**AND** keeps its `nclex_tutor_library_note_attachments` row, joined by
`activity_id`. For shelves specifically the two load-bearing facts:
**(1) a shelf is ATOMIC** — ONE activity + ONE attachment (`shelf_id` set,
`note_id` NULL), never one-activity-per-note; **(2) completion is
DERIVED** — a rollup of member-note `marked_done_at`, no progress row.
Key realisation that made the migration tiny: the attachment table has had
`shelf_id` + `skipped_note_ids` + the `note_id` XOR `shelf_id` CHECK since
11.1, and `activity_id` since 11.11a — so **the only schema change is
adding `'SHELF'` to the activity-type CHECK.**

Then settled, in plain terms with Sam, four design points:
- **`skipped_note_ids`** = "Hide in this unit" — a per-placement, reversible
  local trim that never touches shelf membership.
- **Tutor card stays uniform** (like every other activity); all shelf detail
  + the member-notes-with-hide controls live in the **edit modal** — matches
  how every activity behaves (Sam's call, diverging from the CD prototype's
  special card).
- **Mixed visibility — "Option A" (full).** A shelf can hold notes whose own
  visibility excludes the target programme. Warn at attach ("N of M won't be
  visible here"); in the modal show a DISTINCT state "Not visible to this
  programme · Make visible here" (never conflated with "Hidden here ·
  Unhide"). "Make visible here" = the same op as editing the note to add the
  programme (inserts a `_note_visibility` row; only ever widens). Sam's
  framing: mixed-visibility is rare/self-inflicted (a reusable shelf carrying
  programme-scoped notes contradicts the shelf's purpose), so we don't
  over-invest — warn + read-the-state + one-click fix is plenty.
- **Live membership** — the shelf reads members at render time, so adding a
  note in the library updates every attachment. New notes opt-out (show
  unless skipped); the skip-list keeps trimming as the shelf grows. The
  11.12c hint explains a change to students.
