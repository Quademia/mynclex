Case Study editor — visual mockup

Visual reference for Slice 1.11a — the case header, metadata, and chart-tab authoring surface. The 6 question slots (Slice 1.11b) and the preview-as-position toggle (Slice 1.11c) are shown as placeholders only, with space reserved in the layout for when those slices land.

Companion to docs/product-plan/slice-1.11-plan.md. Mockup only — no CSS from this file ships into the app.

1. Full editor screen

A single page at /admin/bank/cases/[case_id] (or the tutor twin). On desktop (≥ 900px) the layout is a split pane: chart authoring on the left, question authoring on the right. The divider between them is draggable (default 50/50, last position persists). On mobile or narrow viewports the two panes stack vertically — chart on top, questions below. The top bar is sticky across both panes.

The right pane in this mockup shows a Slice 1.11b placeholder — the question navigator pills and a reserved body area. 1.11a ships the left pane only; 1.11b lands the right. Designing for the split now means 1.11b is additive, not a layout rebuild. The student-facing runner uses the same chart-left / question-right shape, so curator authoring mirrors what students see.

The active question's editor lives here

Each Q1–Q6 pill selects which question is active. The selected question mounts the existing per-type editor (MCQ / SATA / Matrix / Bow-tie / Cloze / Highlight / Drag-drop / TF / Select N) in nested mode inside this pane.

Above the editor: CJMM step dropdown + question-type picker.

On desktop (≥ 900px) the editor is a split pane — chart left, questions right. Below 900px the panes stack vertically: chart on top, questions below. The divider between panes is draggable; default 50/50; last position persists in localStorage. Top bar stays sticky across the full width so Save is always reachable.

Built-in narrative tabs (Nurses' Notes, Orders) and Free-text custom tabs use the same stacked-card shape: one time field + one free-text body + one visible-from segmented control per entry. Built-in structured tabs (Vital Signs, Lab Results) and Rows & columns custom tabs use a table with typed columns — curators define their own columns for the custom variant. 3. Tab-by-tab worked examples

Six built-in tab types ship in the hardcoded registry (lib/bank/case-study/tab-types.ts). Each either renders as a structured table (typed columns) or as stacked cards (free-text body + a handful of fields). Curator never picks the rendering mode — the tab type decides. Section 2 covered Nurses' Notes, Vital Signs, and a custom MAR tab. This section walks through the other four plus two custom examples.

Custom tabs come in two shapes the curator picks at creation time. Free text uses the generic Cards shape (Time · Body · Visible from — same as Nurses' Notes). Rows & columns lets the curator define their own column set — same editing pattern as Vitals or Labs (see 3.6). Visible-from is 1–6 everywhere — even History & Physical, which typically defaults to 1 but can be unfolded mid-case if the curator wants.

3.6 Custom Rows & columns — Intake & Output

When a built-in doesn't exist for what the curator needs — and the data is structured rather than narrative — they can create a Rows & columns custom tab. The curator defines the columns; rows follow the same editing pattern as every other structured tab. Columns are plain text in v1 (no numeric-only or date validation) so curators can freely enter "positive", "+2", "trace", or anything real clinical data requires.

The column definitions sit pinned at the top of the entries pane. Editable anytime — rename, reorder with the arrows, delete with ×. Visible-from is a locked column that sits at the far right on every Rows & columns tab, same as built-in structured tabs.

3.7 What the choice looks like at add-tab time

When the curator adds a custom tab, the popover now asks for the shape. Two radio options. Free text is the default (simpler, covers most cases); Rows & columns is for when the data is structured and deserves a grid.

Add a custom tab

Shape

Shape choice is locked at creation time. A curator who picks Free text then decides they wanted Rows & columns must delete the tab and recreate it — a conversion would mean asking the curator how to map free-text bodies into columns, which isn't worth the UX in v1. The add-tab friction is small.

6. Edge cases worth noticing

Behaviours worth pinning down before build so the parser, editor, and server action agree.

Renaming a built-in tab

Curator changes Vital Signs to Vitals (0800–1400). The label shown to students changes. The underlying tab_key stays vital_signs so the renderer still knows it's a structured tab.
Allowed — label ≠ tab_key

Duplicate built-in tab

Curator tries to add Orders twice. The add-tab popover disables the second attempt — each built-in can appear at most once per case. Custom tabs have no such limit.
Blocked in the picker

Tab with zero entries

Curator adds a tab then leaves it empty. Allowed while drafting (is_published = false). On publish, empty tabs are flagged by the validate-case check (Slice 1.11c) but not blocked at the DB layer.
Allowed in drafts; flagged on publish

Deleting a tab with entries

Curator deletes Diagnostics after filling 3 entries. window.confirm() warns that entries will be lost. Confirmed deletes remove the tab row (cascade removes entries).
Confirm dialog before delete

Custom tab with built-in name

Curator types Vital Signs in the custom-tab input when the built-in is already added. Accepted — the name is just a label. Stored as a custom tab with tab_key = 'custom'. Curator can rename to disambiguate.
Allowed — name collisions tolerated

Reordering tabs

Up / down arrows on each tab shift display_order by ±1. No drag-and-drop in v1 (deferred — matches the curriculum editor's convention).
Arrows, not drag

Visible-from default

New entries default to visible_from = 1 (visible from Q1 onward). Curator changes per entry. No empty / null visible-from state — every entry has one of 1..6.
Defaults to 1

Unsaved-changes guard

Curator edits an entry then navigates away. Sticky top bar shows Unsaved changes. A beforeunload listener asks for confirmation. Same pattern as other editors.
Confirm on navigate away

7. Summary — what 1.11a ships

  • Sub-routes /admin/bank/cases, /admin/bank/cases/[case_id], and tutor twins.
  • Shared reusable component lib/bank/case-study/editor.tsx with a surface prop.
  • Three-accordion metadata shell — Content (open), Classification, Housekeeping. Same mental model as EditorShell.
  • Chart tabs via new child table nclex_case_study_tabs (plus tutor twin). Six hardcoded built-ins plus free-form custom tabs.
  • Left tab rail with per-tab entry count and up/down reorder arrows. Active tab border-left accent.
  • Right pane adapts to tab type — table for structured, stacked cards for narrative and custom.
  • Per-entry visible-from as a 1–6 segmented control. Default 1. No null state.
  • RLS on both new tab tables.
  • Seed: one demo case with 2–3 tab types and realistic entries; no questions attached.
  • Question slots below the chart — placeholder only, buildable in Slice 1.11b.
  • Preview-as-position toggle visible on the section head — non-functional in 1.11a, functional in 1.11c.
