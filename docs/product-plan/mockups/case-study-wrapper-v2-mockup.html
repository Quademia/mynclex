Case-study wrapper v2 — visual mockup

Three-pane wrapper page that hosts case-study scenarios and their attached questions. Defines the geometry, slot mechanics, save semantics, and destructive flows for slice 12 of the questions-and-wrappers rebuild.

Last updated 2026-04-30 · Companion to docs/product-plan/questions-and-wrappers-rebuild.md § 5 and slice 12 in the slice plan.

What this is

A pre-build mockup of the three-pane case-study wrapper. The chart-tab editors themselves (Vital Signs, Lab Results, Orders, History & Physical, Diagnostics, Nurses Notes), plus all add/remove/reorder affordances for tabs, rows, columns, and narrative entries, and the "Add tab" popover with custom-narrative + custom-grid options, are ported as-is from legacy. What is new is the surrounding wrapper shell: layout, slot rail, combined preview, two-button save, and the add/detach/delete-question flows. For per-tab editor visuals (and the add-tab popover) see the older case-study-editor-mockup.html — those frames remain canonical for v2.

1. Why two columns with two modes

The student never sees a wrapper alone — chart tabs are always shown next to a question, never as their own student page. So a "wrapper-only preview" pane would represent a state that doesn't exist for students. The page settles on two columns, never three: the right column is always the combined preview; the left column hosts the curator's work and toggles between two focused modes.

ModeLeft columnRight column
Wrapper mode (default) Wrapper-edit pane: Content / Chart tabs, visibility section, slot rail, Save case study + Validate + Delete + Cancel. Combined preview — always.
Editor mode (slot active) Editor body for the active slot, full vertical height. Slot strip at the top for switching slots; ← Wrapper view button returns to wrapper mode. Save question + Discard buttons in header. Wrapper-edit pane is hidden — Save case study, Validate, Delete, Cancel are not reachable until the editor closes. Combined preview — same component, still tracking the active slot.

Clicking a slot card in the wrapper mode's slot rail enters editor mode. Pressing the ← Wrapper view button (or Save question / Discard) returns to wrapper mode. The right-column preview never moves — it's the curator's continuous reference for what the student sees while authoring at any layer.

Why this and not three panes (wrapper top-left, editor bottom-left, preview right): editors are tall (stem, options, feedback, classification + housekeeping tabs) and were ending up in a cramped bottom-half pane that scrolled badly. A focused mode that takes the full left column avoids the scroll, and the wrapper context is always one click away — the curator doesn't lose orientation because the right column's preview keeps the chart visible.

Save semantics — three independent saves (legacy parity + per-question)

Each save is a draft commit at its own level. None requires "completeness" — the publish gate is what enforces that, server-side, when is_published is toggled to true on Save case study.

  • Save case study — wrapper-edit pane header. Saves case header (title, scenario, visibility, slot ordering, cjmm_step) + all 6 question drafts atomically via the legacy nclex_save_case_with_children RPC. Reads in-flight editor DOM for the active slot so unsaved typing is captured.
  • Save tab — inside each chart-tab editor (ported as-is from legacy). Saves just that one tab via upsertTabAction.
  • Save question — question-edit pane header. Saves just the active question; in case-study context, also sets parent_case_id and writes the nclex_case_study_items join row.

Why redundant Save case + Save question both touching questions: the curator picks the affordance that fits the moment — single-question polish or whole-case sweep. The build-time risk (overwriting per-question saves with stale wrapper sweep) is mitigated by re-reading the active editor's DOM at Save-case time, same as legacy does today.

Two preview lenses, not one

Each chart row has a visible_from (1-6) that tells the student "this entry appears starting at Q<n>." Two distinct controls expose this:

  • Editing-side preview selector — sits on the wrapper-edit pane (top-left). A small Off / 1 / 2 / 3 / 4 / 5 / 6 strip lets the curator flip the chart's editing view to any position without changing the active slot. Rows with visible_from > chosen position go greyed with a "hidden until Qx" tag. Per-session only — reloads reset to Off.
  • Combined preview (right column) — automatic. The chart subsection always reflects what the student sees at the active slot's position. No toggle. The question subsection has a Student / Answer-key toggle that affects only itself, since charts have no answer key.

Independent: flipping the editing-side selector to Q4 doesn't change what the right pane shows. Switching the active slot to Q4 does.

9. Design decisions captured

Seven open questions were settled during the slice-12 design pass. Each subsection records what was on the table, what was chosen, and why — so a future reader (or a next-slice author asking "why does it work this way?") can reconstruct the reasoning without re-doing the audit.

9.1 — visible_from preview model

Question. Each chart row carries a visible_from (1-6) value — the row stays hidden from the student until question position N. How should that mechanic surface to the curator while editing, and to the curator while previewing?

Considered. (a) Keep the legacy "Preview as student at Q1..Q6" toggle on the case header. (b) Use the active slot's position as the implicit preview lens (no separate toggle). (c) Both — independent editing-side toggle for chart preview, plus the active slot driving the combined preview.

Decided. (c) — two independent preview lenses:

  • Editing-side selector — the wrapper-edit pane (Chart tab) carries its own Off / 1 / 2 / 3 / 4 / 5 / 6 strip. Lets the curator flip the chart's editing view to any position without changing the active slot (which would trigger a discard prompt on the active question's draft).
  • Combined preview (right column) — automatic. Chart subsection always reflects what the student sees at the active slot's position. No toggle. The question subsection has a Student / Answer-key toggle that affects only itself, since charts have no answer key.

Why. The legacy single toggle was conflating two needs (editing-time chart preview + student-eye-view of the case). Splitting them lets the curator be on Q2 in the question editor while previewing the chart at Q5 — useful when authoring a "what if I add a row at Q5" question without losing Q2 draft state. The combined preview's automatic tracking means it always answers the same question: "what does the student see right now at this question?"

9.2 — Classifications + visibility flags

Question. Where on the wrapper page do classification fields (client needs, nursing subject, body system, topic, subtopic, difficulty, tags, bloom level) and visibility flags (is_published, is_free_sample, is_builder_visible) live?

Considered. Putting both groups together inside (a) a collapsible accordion at the bottom of the wrapper-edit pane, (b) a side drawer behind a "Settings" button, or (c) a "Metadata" tab on the wrapper-edit pane.

Decided. Split the two concerns rather than co-locate:

  • Classifications — none on the wrapper. They live on each child question only, in the question editor's existing Classification tab.
  • Visibility flags — three switches as a "Visibility" subsection inside the Content tab body, below the title + scenario fields. Visible only when the Content tab is active.

Why classifications. bank.md already documented the rationale for trends ("no classification columns on the dataset"): one wrapper can host questions of different difficulties or subcategories, and duplicating classification on the wrapper recreates the wrapper-vs-child-drift problem from 1.11b. Same applies to case studies — drop the wrapper-level classification UI even though the legacy DB columns still exist (column cleanup is a separate concern).

Why visibility inside Content (not always-visible). An earlier iteration placed the Visibility section between the tab body and the slot rail, so it was always visible regardless of which top tab was active. That created the optical impression of the section "appearing under both tabs" — the curator saw it once on Content and once on Chart, even though it was the same component. Moving it inside the Content tab gives it one stable home, and the placement is semantically right: visibility flags are case-identity metadata (publishing, sample, builder visibility) that belong with title and scenario. When the curator is on the Chart tab, visibility isn't visible — one click to switch back when they need it.

9.3 — Custom tabs + add/reorder affordances

Question. Should v2 keep custom tabs (curator-named narrative + grid)? How should the curator add/remove/reorder tabs, rows, and columns?

Decided. Keep custom tabs (very important — losing them would be a regression). Port every editing affordance from legacy unchanged:

  • Tab rail with up/down reorder arrows + an "Add tab" popover listing built-ins (greyed if already used) plus "+ Custom narrative" / "+ Custom grid".
  • Structured tabs: add/remove/reorder rows + add/remove/reorder columns.
  • Narrative tabs: add/remove/reorder entry cards with the per-row visible_from selector (vf-segmented).
  • All wired to legacy's upsertTabAction / reorderTabsAction / deleteTabAction.

Why. These low-level editing affordances are designed and tested in production today. Reinventing them would burn time and risk regressions. The architecture rebuild plan already calls for vendoring lib/bank/case-study/{tab-rail,structured-tab,narrative-tab,vf-segmented}.tsx into lib/authoring/wrappers/case-study/ for v2. For the per-tab editor visuals (popover, custom-grid column editor, etc.) see the legacy case-study-editor-mockup.html — those frames remain canonical.

9.4 — Save granularity (Position 3)

Question. What save buttons does the curator see, and what does each one cover?

Considered. Three positions:

  • Position 1 — two buttons (Save case study, Save question), with chart-tab content folded into the wrapper save (architecture doc as written, line 323-337).
  • Position 2 — three independent saves (Save case study covers wrapper-metadata only, Save tab per-tab, Save question per-question).
  • Position 3 — legacy parity (Save case batches case header + 6 questions atomically) PLUS per-question saves added on top.

Decided. Position 3.

ButtonWhereSaves
Save case study Wrapper-edit pane header Case header (title, scenario, visibility, slot ordering, cjmm_step) plus all 6 question drafts atomically via legacy nclex_save_case_with_children RPC.
Save tab Inside each chart-tab editor (legacy) Just that tab via upsertTabAction.
Save question Question-edit pane header (new from slices 2-10) Just the active question. In case-study context, also sets parent_case_id and writes the nclex_case_study_items join row.
Validate Wrapper-edit pane header Nothing — opens the validation panel (see 8.5).
Delete tab Inside each chart-tab editor (legacy) Removes that tab.
Delete Wrapper-edit pane header Removes the case (see 8.6 for the two-path confirm).
Cancel Wrapper-edit pane header Navigates back to the case-study list. No save.

All saves are draft saves — none requires "completeness". The publish gate is separate: when is_published is toggled to true on Save case study, server-side validation refuses unless every requirement is met. Save anytime; publish only when ready.

Why. Position 1 is the architecture doc's original intent and is theoretically cleaner, but loses an affordance — the one-click "save everything" sweep — that legacy curators rely on. Position 3 gives the curator both worlds: granular per-question saves AND a single sweep. Costs: redundancy (questions can be saved by either path) and the drift risk that bit 1.11b. Mitigations are baked into 9.1 below.

This decision is an explicit override of the architecture doc's two-button decision. questions-and-wrappers-rebuild.md § 5 "Save semantics" will be updated in slice-12 prep to reflect this.

9.5 — Validate button

Decided. Include in slice 12. Port the rules from lib/bank/case-study/validation.ts unchanged; build a new panel atom in lib/authoring/wrappers/case-study/. Button lives in the wrapper-edit pane header (between Delete and Save case study); opens a floating panel that lists errors first, warnings second.

Rules covered (from the legacy validator):

  • Case-level errors — title missing, scenario missing, no tabs, publish-gate underfill (is_published set with fewer than 6 populated slots).
  • Tab-level warnings — empty tab, tab with no visible_from = 1 entry (student sees an empty tab at Q1).
  • Slot-level errors — stem missing, type missing, CJMM missing (only checked for slots with intent — i.e. stem set OR cjmm picked; truly empty slots are ignored).

Three panel summary states: Ready to publish (published + zero errors), N errors / M warnings — not ready (published + has errors), Draft — N errors / M warnings (not published).

Why. Validate is heavily used by curators preparing to publish. Slot/tab status dots cover at-a-glance feedback, but the panel is the canonical "is this case ready?" answer and surfaces warnings (which dots can't easily express). Removing it would be a regression for curators who currently use it.

9.6 — Two-path delete confirm

Decided. Zero-attached cases: single typed-DELETE confirm. Cases with ≥1 attached question: two-path confirm dialog (frame 6 above):

  • Detach & keep questions — typed-DETACH gate. Unlinks the join rows + clears parent_case_id; questions survive in the bank as standalone. The case wrapper is deleted.
  • Delete everything — typed-DELETE gate. Cascades to delete the case + all attached questions.

Backdrop click and Esc map to Cancel (the safe option, per CLAUDE.md § UI Conventions).

Why. The schema today (parent_case_id is ON DELETE SET NULL) means a naïve "delete case" already auto-orphans questions to standalone — that's the de-facto safe path. The two-path UI makes both intentions explicit instead of forcing the curator to remember which schema behaviour applies. Distinct typed words (DETACH vs DELETE) protect against muscle-memory mistakes when toggling between the two cards.

9.7 — Two modes on the left column (post-design refinement)

Question. Where does the question editor body live when a slot is active? The original architecture-doc layout had three panes — wrapper-edit top-left, question-edit bottom-left, combined preview right. The bottom-left pane turned out cramped: editor bodies are tall (stem, options, feedback, classification + housekeeping tabs) and ended up scrolling the curator's working area badly.

Considered. (a) Stay with the three-pane geometry; live with the scroll. (b) Move the editor body to a full-screen modal overlay (like the standalone bank-list editors). (c) Replace the bottom-left pane with a focused "editor mode" that takes the full left column, leaving the right-column preview untouched.

Decided. (c). The page is two columns; the left column toggles between two modes:

  • Wrapper mode (default) — wrapper-edit pane fills the left column. Slot rail visible. Save case study + Validate + Delete + Cancel in pane header.
  • Editor mode (slot active) — editor body fills the left column at full vertical height. Slot strip at the top for switching slots without leaving editor mode. ← Wrapper view button returns to wrapper mode. Save question + Discard buttons in pane header. Wrapper-level buttons (Save case study, Validate, Delete, Cancel) are hidden — must close editor first to reach them.

Why. The right-column preview is the curator's continuous reference for what the student sees — it should never move. Splitting the left column between wrapper context and editor body gave too little space to either; promoting the editor to a focused mode gives it the room it needs without losing wrapper context (the slot strip keeps slot navigation tight; the right-column preview keeps the chart visible). Hiding wrapper buttons in editor mode is an explicit focus boundary — the curator is editing one thing at a time, not toggling between scopes.

Open considerations baked into 10.1: in-memory wrapper state persists across mode toggles (no DB read on Wrapper view return); slot-strip click on a dirty slot fires the discard/save-first dialog (frame 6).

10. Implementation watch-outs + sub-slice plan

10.1 — Build-time concerns flagged during planning

  1. Save-order interaction (Position 3 hazard). If the curator clicks Save question, then later clicks Save case study, the case sweep could read stale form state for that slot and overwrite the just-saved question. Mitigation: Save case study reads the active editor body's DOM at submit time (legacy already does this via slotFormRef.current in editor.tsx:412-428) — same pattern survives for v2.
  2. Wrapper-vs-child drift trap. Position 3 reintroduces the redundancy that 1.11b was burned by. Concrete rule: the per-question save action's case-context branch only sets parent_case_id + writes the join row. It does NOT touch wrapper-level fields (title, scenario, visibility, classifications). Save case study is the only path that writes those.
  3. Publish gate stays server-side. The legacy RPC nclex_save_case_with_children enforces "all 6 slots populated" when is_published = true. Don't move that check to the client — defence-in-depth. Client-side checks (Validate panel, friendly error in the action) are advisory only.
  4. Validate is manual-only. Per validation.ts design: panel only opens on click; never auto-runs on save or load. Re-clicking Validate while the panel is open closes it.
  5. Two preview lenses are independent state. The editing-side Preview at selector lives in the wrapper-edit pane's local state. The combined preview's chart tracks activeSlot. Switching slots updates the combined preview but does NOT change Preview at. Reloading the page resets both — per-session only, no URL or storage persistence.
  6. Slot rail always shows 6 slots. Schema fixes positions 1-6 (CHECK position BETWEEN 1 AND 6 + UNIQUE (case_id, position)). Empty slots have item_id = NULL; they still occupy a slot card (greyed) so the curator can see "Q4 is the next blank" without re-counting. "+ Add question" fills the lowest-numbered empty slot.
  7. Wrapper state persists across mode toggles. When the curator enters editor mode (clicks a slot card), the wrapper-edit pane's in-flight state (typed-but-unsaved title, scenario edits, chart entry edits, visibility toggles) lives in React state — the wrapper-edit pane unmounts visually but the state holds. Returning via ← Wrapper view re-renders the pane with edits intact. No DB round-trip, no URL param. Same applies to editor-mode state when toggling back: the active editor's draft survives a return-to-wrapper-and-back cycle. The only thing that drops state is a hard reload.
  8. Slot strip dirty indicator must reflect editor-body state. The amber dot on a slot pip in editor mode means that slot's editor draft has unsaved changes (compared to its DB row). Drives the discard/save-first dialog when the curator clicks a different pip. Implementation: the wrapper page tracks one dirty: boolean per slot in its local state, set by each mounted editor body via a callback prop. Drops on successful Save question.
  9. Sticky topbar + scrolling left column + sticky right column. The breadcrumb topbar (with the case title) is position: sticky; top: 0; so it pins at the top of the viewport while the curator scrolls. The right-column combined preview is also sticky (with a top offset matching the topbar height) so it stays in view as a continuous reference while the left column — which can be tall (chart entries, editor body) — scrolls naturally. Mirrors the standalone-editor pattern: fixed chrome, scrollable working area. Implementation note: position: sticky requires no overflow on intermediate ancestors — verify the AdminShell wrapper doesn't break it before slice 12c lands.
