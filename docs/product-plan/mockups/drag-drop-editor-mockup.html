Drag-drop editor — Visual Mockup

Authoring + student views for DRAG_DROP, the ninth and last standalone NGN question type. Two subtypes: Ordered list and Sentence slots, selected via a content.subtype radio.

Slice 1.10 planning reference · companion to ngn-primer.html · resolves Q1 (sentence marker syntax) and Q3 (pool-size rule)

What's already locked

  • Both subtypes ship — Ordered list + Sentence slots, via a content.subtype radio at the top of the editor.
  • Curator picks pool size per question — tokens may include distractors (pool ≥ slot count).
  • Each token fills one slot maximum — no reuse across slots (universal NCLEX behaviour).
  • Slot bounds: 3–8 slots. Feedback granularity: per-slot. Answer shape: correct.slots = { s1: "t3", s2: "t1", … }.

What this mockup settles

  • Q1 — how do sentence slots appear in the stem? (see §4)
  • Q3 — what's the rule on pool size vs slot count? (see §5)

1. Subtype: Ordered list

Curator defines a list of positions (the slots). The student drags tokens from a shared pool into those positions in order. Typical use: priority, sequence, severity, stepwise procedure.

Clinical example: Prioritising actions for a deteriorating post-operative client. Five actions to sequence; six tokens in the pool (one distractor).

3. Decision to close: Q1

Q1Sentence slot-marker syntax

What token does the curator type into the stem to create a slot? Cloze already uses {1} for its blanks. Drag-drop's sentence subtype is structurally similar, but confusing the two would be costly. The marker needs to be visually distinct from Cloze, easy to type, and safe vs. real medical text (nothing that naturally appears in clinical passages).

Option A · square brackets
[1] [2] [3]
Distinct from Cloze's {1}. Easy to type. Visual signature matches Highlight's [[…]] but not confusable (single vs. double bracket, and numerals vs. text inside). Clean on student render.
Option B · double curly
{{1}} {{2}}
Distinct from Cloze's single-curly. But typing {{ }} is awkward and visually heavy. Adds friction for no real gain over square brackets.
Option C · underscore-wrapped
__1__ __2__
Visually resembles a blank line. Unfortunately clashes with Markdown italic _x_ and bold __x__, which matters if curators later paste rich text. Avoid.
Option D · angle quotes
⟨1⟩ ⟨2⟩
Visually elegant and unambiguous, but requires a special-character picker to type. Accessibility concern for curators using basic keyboards.

Recommendation: Option A — [1] [2]. Parser regex: /\[(\d+)\]/g. Marker IDs in content.slots map 1:1 to the numerals (s1, s2, …). Re-uses the same + Add slot toolbar pattern Cloze established — find lowest free N in 1–8, insert at cursor.

4. Decision to close: Q3

Q3Pool size vs. slot count

How many tokens can a curator put in the pool, given N slots? Too many and the student faces a needle-in-haystack; too few and there are no distractors. This matters because it constrains the parser's validation, the editor's bounds-meter, and the student's experience.

Option A · N to N + 4
4 slots → 4–8 tokens
Structured bound. Author can use the pool exactly (no distractors) or add up to four. Matches NCSBN sample drag-drop items where distractor count is almost always 0–4. Easy to explain in tooltip.
Option B · N to 12
4 slots → 4–12 tokens
Single global ceiling. Simpler rule. But a 3-slot item with 12 tokens is a bad exam experience — nine tokens are distractors. Curators will need discipline the rule doesn't enforce.
Option C · no upper limit
4 slots → 4–∞ tokens
Maximum flexibility. Zero structural guardrails. In practice we'd still cap at 12 to keep the pool renderable on mobile, so this collapses into Option B with a hidden ceiling.
Option D · exactly N
4 slots → 4 tokens
No distractors. The student's strategy becomes "eliminate what's placed and drop the rest" — which defeats the point of drag-drop. NCSBN items routinely include distractors. Do not choose.

Recommendation: Option A — N to N + 4. Parser asserts tokens.length ≥ slots.length (fewer tokens than slots is structurally invalid) and tokens.length ≤ slots.length + 4. Bounds-meter shows "5 tokens · 1 distractor" so the curator always sees the distractor count.

5. Edge cases worth noticing

Five behaviours worth thinking through during implementation. Each affects parser logic or editor UX.

Curator deletes a slot marker mid-edit

In sentence mode, curator types [1] [2], assigns tokens, then edits the stem and deletes [2]. The s2 card still holds a token assignment.
Orphan — preserve card, dim it, drop on save

Pool smaller than slot count

Curator adds 5 slots but only 3 tokens. Clearly unfinished but we don't want to reject mid-authoring.
Bounds-meter turns amber; save is blocked

Pool bigger than N + 4

Curator adds 4 slots and 9 tokens (5 distractors). Exceeds the recommended rule.
Reject on save with a clear message

Same token in two slots

Curator accidentally assigns t3 to both s1 and s2. Our locked rule says one use max.
Editor prevents double-assign on click

Slot with no assigned token

Curator adds s5 but forgets to pick a correct token for it.
Reject on save — "every slot needs a correct token"

6. Summary

Once Q1 and Q3 are confirmed, the full decision set for Slice 1.10 is:

  • Two subtypes — content.subtype = 'ORDERED' or 'SENTENCE'.
  • Ordered subtype: position-based slot IDs s1, s2, ….
  • Sentence subtype: inline markers [1] [2], mapped to slot IDs s1, s2, ….
  • Token IDs t1, t2, ….
  • Slot bounds 3–8. Token bounds N to N + 4, absolute max 12.
  • Each token fills one slot max.
  • Per-slot feedback, optional.
  • Answer shape: correct.slots = { s1: "t3", s2: "t1", … }.
  • Item-ID prefix NCLEX_DD_ (admin) / NCLEX_TUT_DD_ (tutor).
  • Auto-inherits the instruction field from the shell (Slice 1.8).
  • Auto-inherits tutor-surface reuse from Slice 2.1 — zero extra wiring.
