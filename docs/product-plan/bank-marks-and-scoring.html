Why this doc exists

Scoring spans authoring (the curator decides what's correct) and consumption (the runner produces a number from what the student picked). The decisions are tangled enough — partial credit, NCSBN-exact rules, what "max score" means, whether curators can override weight — that they need their own planning home rather than living scattered across bank.md §scoring, bank-consumption.html §3 (Pillar 2), and the runner sub-plan §11.

This doc is the consolidating reference. bank.md §scoring keeps its short cheat-sheet of which function applies to which question type — that's a quick reference. This doc explains the decisions, the tradeoffs, the edge cases, the migration path, and where the code lives.

2. The real NCLEX scoring landscape settled — research

Two eras matter. Our scoring rules track NGN (the current real exam), not the legacy form.

2.1 Pre-NGN (before April 2023)

Everything was dichotomous — right or wrong. Even SATA was all-or-nothing: the student had to pick exactly the right combination. Simple to grade, no partial credit anywhere.

2.2 NGN (Next Generation NCLEX, April 2023 onwards) — the current real exam

NCSBN introduced three scoring rules to handle the new item types:

RuleHow it worksUsed for
Dichotomous (0/1) Right or wrong. No middle ground. Single-best-answer items: MCQ, TF, traditional single-answer types.
+/− polytomous (partial credit with floor) Each correct selection = +1, each wrong selection = −1, score floored at 0. Maximum = number of correct options. SATA, multi-response highlight, multi-response matrix cells.
0/1-per-element (independent per row / blank / slot) Each row, blank, or slot scored independently as 0 or 1, summed. Matrix multiple-choice (one answer per row), bow-tie, cloze drop-down, drag-to-slot.

2.3 Crucially — NCSBN does not expose per-item "marks"

On the real NCLEX, items don't carry a curator-set point value. Each item produces a raw score per its rule (0/1, 0/3, 0/5, etc.), then IRT (Item Response Theory) weights items by difficulty for the pass/fail decision. The student never sees "this question is worth 2 points and that one is worth 5." Items are just items, pre-calibrated at NCSBN's testing labs.

For us — a practice product, not the actual exam — that's a design choice we have to make explicitly: do we mimic this (no curator-settable weight) or let curators emphasise certain questions? See §5.4.

3. The five scoring functions settled — see bank.md

Already documented in bank.md §scoring. Reproduced here for cross-reference. These are application-code functions (not database structure), each implemented against NCSBN's official rules and tested in isolation against released sample questions.

FunctionLogicMaps to NGN rule
scoreAllOrNothing Full marks if exactly correct, else 0 Dichotomous
scorePlusMinus +1 per right, −1 per wrong, floor at 0 +/− polytomous
scorePerRow 0/1 per row, summed (no floor needed — can't go negative) 0/1-per-element. v1 supports single-response matrix only; multi-response deferred (§11).
scorePerBlank 0/1 per blank, summed (no floor needed) 0/1-per-element. v1 supports simple drop-down only; cause-effect paired variant deferred (§11).
scorePerSlot 0/1 per slot/correct-token, summed (no floor needed in v1 — picks are constrained by the runner UI) 0/1-per-element. Drag-drop is single-token-per-slot; bow-tie picks are 2/1/2 constrained per wing — neither can be gamed by "select everything", so +/− is unnecessary.

Note on +/− framing. bank.md §scoring originally described scorePerSlot as "+/− per slot, sum with floor." That framing was inherited from a hypothetical multi-token-per-slot model we don't have in v1. Our drag-drop and bow-tie are 0/1 per element. The bank.md table is being updated to match.

Paired scoring (Cloze cause-effect): NCSBN's NGN cause-effect cloze items would require both halves of a pair to match together — first right + second wrong = 0 for the pair. Our v1 cloze does not implement this; each blank scores independently. Deferred to v2 (§11).

4. Per-type rule mapping settled

Settled per-type by walking each type one at a time against the actual authoring code (parsers in lib/bank/parsers/). Some types had multiple NGN variants in theory; our system implements only one of each. The "deferred" notes in §11 capture the unsupported variants.

Question type Scoring function Max formula Notes
MCQ scoreAllOrNothing 1 (always) Single-best-answer dichotomous.
TF scoreAllOrNothing 1 (always) Functionally a 2-option MCQ; separate type for curator UX.
SATA scorePlusMinus count of correct options in answer key +/− with floor 0. Defends against "select everything" gaming since picks are unconstrained.
SELECT_N scorePlusMinus N (== count of correct in answer key — see §4.1) Same scoring as SATA. Editor enforces N == count(correct) at save time. UI forces "pick exactly N".
MATRIX scorePerRow count of rows (2–6 in practice) Single-response only (one column per row). Multi-response variant deferred (§11).
HIGHLIGHT scorePlusMinus count of correct chunks in answer key +/− with floor 0. Parser requires ≥1 distractor (wrong chunk).
CLOZE scorePerBlank count of blanks (2–6 in practice) Simple drop-down per blank; each independent. Cause-effect (paired) variant deferred (§11).
DRAG_DROP scorePerSlot count of active slots (3–8 in practice) Two subtypes (ORDERED, SENTENCE) share the same scoring math. Single-token-per-slot. Distractors don't affect max.
BOWTIE scorePerSlot 5 (fixed: 2 left-wing correct + 1 centre + 2 right-wing) Per-wing tally of correct picks, summed. No +/−, no floor — see §4.2.

4.1 Select-N — settled: +/− polytomous, force N == count(correct)

Select-N forces the student to pick exactly N options at runtime. Two scoring interpretations were on the table — dichotomous (any wrong combination = 0) or +/− like SATA. Locked: +/− like SATA.

The structural rule that closes the curator-setup ambiguity: the editor must force N == count(correct). If the curator marks 3 options as correct, N is 3 — no separate "N field." This means there's only one valid scoring shape: the student picks 3, each correct contributes +1, each wrong contributes −1, floor 0. Max = N = count(correct).

This eliminates the "curator marked 4 correct but set N=3" edge case — it can't happen. Editor save validation must enforce the equality.

4.2 Bow-tie — settled: per-wing tally, no +/−, no floor

Our bow-tie has 3 wings (Left = Actions, Centre = Condition, Right = Parameters), each with its own token pool. The parser hard-validates exactly 2 / 1 / 2 correct tokens across the three wings — total always 5. Each wing's pool is isolated; tokens don't cross wings.

At runtime the UI forces the student to pick exactly 2 from the left pool, 1 from the centre pool, 2 from the right pool. Because the picks are constrained, +/− gaming defence isn't needed — the student literally cannot pick "all options" and overflow.

Scoring rule: per-wing tally of correct picks, summed. For each correct token in a wing's answer key, +1 if the student picked it, 0 otherwise. No subtraction for wrong picks; no floor needed (can't go negative).

Why simple-count beats +/− here: a student picking 1 of 2 correct + 1 wrong in the left wing has demonstrated partial competence. Under +/− they'd score 0 (1 − 1, floored). Under simple-count they score 1 out of 2. Simple-count rewards the partial competence; +/− zeroes it out unnecessarily because the UI constraint already prevents the gaming the +/− rule was designed to prevent.

Per-wing sub-scores are recoverable (each wing's contribution is computed independently before summing). This opens up future analytics — "this student is good at recognising conditions but weak at choosing actions" — without changing the v1 storage shape.

5. Marks — derived, system-managed settled in principle

Decision (2026-05-04): keep the marks column on nclex_bank_items and nclex_tutor_questions, but change its semantics from curator-settable free-form to editor-computed, system-managed.

5.1 The decision and why

Two alternative positions were considered:

  • Drop the column entirely and derive max at attempt creation, on every attempt, from the answer key. Cleanest single-source-of-truth.
  • Keep the column, compute its value in the editor at save time from the answer key, then treat it as a stored read-only display value the curator can see. (Adopted.)

The "keep + compute in editor" approach won on five points:

  1. Curator visibility is real value. A SATA with 4 correct options is a different question than a SATA with 6 correct — the curator should see "max 4" / "max 6" when reviewing, not have to mentally count answer keys.
  2. Single write path = single derivation point. The editor is already the gatekeeper for correct. Adding "and compute marks here" is a natural extension. Runtime never derives; it just reads the column.
  3. Performance. Derive once per question edit, not once per attempt creation. For a popular question seen in 10,000 attempts, that's 10,000 derivations vs 1.
  4. Snapshot path is cleaner. nclex_attempt_items.marks_snapshot = source_item.marks is a trivial read. The alternative would have meant running the derivation function inside the attempt-creation transaction — more code in a hot path.
  5. Auditability. The stored value persists. If the curator changes correct later, we can see when marks changed via row history. With pure derivation there's no record to audit.

5.4 Curator override deferred — decide at build

Should curators have the ability to override the system-computed marks for high-weight questions?

Decision (2026-05-04): defer to build. The implicit default while building marks-as-system-managed is "no override" — that's the simplest, most NCSBN-authentic starting point and what the editor will produce unless we decide otherwise during build. If a real tutor complaint surfaces, or if a use case becomes concrete, revisit this section then.

The tension was laid out in earlier discussion:

  • Authenticity (Pillars 1+2): the real NCLEX has no curator-set weights. Items contribute via IRT difficulty, not human-tuned points. A pure NCSBN-mirrored product has no override.
  • Practical reality: some questions ARE more important. A tutor's "this is THE question for understanding pharmacokinetics" deserves more weight than a routine recall question.
  • Risk if we allow override: curators inflate their pet questions, scores become incomparable across attempts, Readiness Signal calibration breaks, percentile comparisons distort.

If the decision later goes "yes, allow override," candidate shapes:

  • Multiplier-only: curator sets a numeric "weight" (default 1.0). Final marks = derived max × weight. Preserves the per-type rule; just scales the whole question.
  • Restricted to tutor-private bank: bank questions stay system-managed (authoritative). Tutor's own bank can have curator-set weights — they're customising their own programme content.
  • Hard cap on multiplier range: e.g. 0.5–2.0. Prevents extreme inflation while allowing meaningful emphasis.

5.5 is_correct policy — full credit only settled

nclex_attempt_answers.is_correct (per attempt-creation §6.3) is the binary "did the student get this question right?" verdict. Separate from score_awarded, which holds the partial number.

Policy: is_correct = true only when the student earned the full max score for the question — every correct option / row / blank / slot / token, and no wrong picks. Anything less, including high partial scores, is is_correct = false.

This is a cross-cutting decision that cascades to every partial-credit type:

  • For dichotomous types (MCQ, TF), is_correct and score_awarded > 0 carry the same information — no policy decision needed.
  • For SATA, SELECT_N, HIGHLIGHT (+/− types) — is_correct = true only when the student picked exactly the correct set with zero wrongs and zero missing.
  • For MATRIX (0/1 per row) — true only if every row is right.
  • For CLOZE (0/1 per blank) — true only if every blank is right.
  • For DRAG_DROP (0/1 per slot) — true only if every slot has its correct token.
  • For BOWTIE (0/1 per correct token, summed) — true only on all 5 correct.

Three reasons for full-credit-only over a threshold rule (e.g. "≥ 75% of max"):

  1. Matches NCLEX semantic. "Did the student get the question right?" In NCLEX speak, partial credit changes the score, not the verdict. Getting 3 of 4 right means you didn't get the question.
  2. 4-state per-question history is honest. A student picking "Practice my wrong answers" (parent §10) wants the questions they didn't fully nail — not just the catastrophes. A 3-of-4 SATA is exactly the question they should re-attempt.
  3. No threshold to argue about. Threshold-based opens up "why 50% and not 60%?" debates with no clean answer.

The partial-credit number is preserved on score_awarded and feeds the percentage scoring (§7). We don't lose the partial signal — we just keep is_correct as the strict verdict.

6. Edge cases deferred — handle per-case at build

Decision (2026-05-04): defer to build, case-by-case. Most edge cases were already settled inline during the §4 per-type passes (e.g. "SATA with 0 selections scores 0", "drag-drop unplaced tokens don't subtract", "bow-tie partial-wing handled by per-wing tally"). The remaining cases that aren't covered inline are mechanical and best decided when the relevant code is being written, not now.

The list below is kept as a checklist for the build session. Each will be settled at the moment the code touches it:

  • SATA with 0 options selected → score 0, no negative (settled inline §4 SATA row).
  • SATA with every option selected → corrects − wrongs, floored (settled inline).
  • SATA with 0 correct in answer key → editor validation rejects (settled inline).
  • Matrix with rows missing a correct column → editor validation rejects (settled inline).
  • Drag-drop with un-placed tokens in pool → don't affect score (settled inline §4 DRAG_DROP row).
  • Bow-tie with a wing fully blank → that wing scores 0; other wings unaffected (settled inline §4.2).
  • Highlight with no chunks selected → score 0 (settled inline §4 HIGHLIGHT row).
  • Auto-submitted (timer expiry) with partial answer — covered by attempt-creation §6.3.1; per-type rules apply unchanged.
  • Cloze paired-blanks (cause-effect) — N/A in v1; deferred variant (§11).

7. Session-level scoring (aggregation) settled

Once each per-question score is computed, what does "you got 78% on this quiz" mean? Partial credit makes this ambiguous — there's no single "correct" rollup.

7.1 The three honest answers

Three different ways to compute a session score from the same data. A worked 5-question example shows the divergence:

#TypeMaxStudent gotScore
Q1MCQ1Right1 / 1
Q2SATA (3 correct)32 right + 1 wrong1 / 3 (after +/− floor)
Q3BOWTIE54 of 5 correct4 / 5
Q4CLOZE (3 blanks)3All 3 right3 / 3
Q5SATA (4 correct)4Missed 1, no wrongs3 / 4
MethodComputationResult
(a) Items-correct ratio Count of items with is_correct = true ÷ total items. Only Q1 + Q4 fully right. 2 / 5 = 40%
(b) Total points ratio Sum of score_awarded ÷ sum of marks_snapshot. (1+1+4+3+3) / (1+3+5+3+4). 12 / 16 = 75%
(c) Item-equivalent average Each item normalised to 0..1 (score_awarded / marks_snapshot), then averaged. (1 + 0.333 + 0.8 + 1 + 0.75) / 5. 3.883 / 5 = 77.7%

7.2 Decision — show all three; (c) is the headline

All three numbers are computed and displayed on the results screen. Item-equivalent (option c) is the headline big number; items-correct and total-points sit underneath as supporting sub-lines.

NumberTells the studentStorage
78% (item-equivalent) — headline "Overall, you handled most questions reasonably well." Stored on nclex_attempts.final_score as NUMERIC 0..1. Display ×100.
12 of 16 points "You earned 12 out of 16 possible points." Computed on read from nclex_attempt_answers + nclex_attempt_items at results-screen render.
2 of 5 fully correct "You fully nailed 2 questions." Computed on read by counting is_correct = true rows.

7.3 Why item-equivalent is the canonical headline

  1. Each question contributes equally. The student answered 5 questions; they put cognitive effort into each. Why should the bow-tie count 5× more in the rollup just because partial credit is finer on it? "Worth 5 points" is a scoring mechanism (so partial credit can resolve to 0/1/2/3/4/5), not a valuing mechanism. Under (b), point-heavy types dominate the session score; under (c) they don't.
  2. Most NCSBN-aligned. NCSBN's IRT model treats every item as one observation of student ability, scaled by difficulty (not by max-points). Item-equivalent matches this — each question is one data point of "how well did the student handle this item, on a 0..1 scale."
  3. Cleanest input to Readiness Signal. Parent §6 wants a 0..100 readiness score across history. Feeding it (b) total-points would force us to undo the point-weighting later for fair item-by-item math; item-equivalent already is the item-by-item picture.

Why NOT (a) as the headline: items-correct hides 100% of the partial-credit signal. A student who got 2/3 right on every SATA shows the same number as a student who got 0/3 — which would be misleading. (a) is honest as a supplementary number but wrong as the canonical one.

7.4 Edge cases that fall out cleanly

  • Skipped / unanswered questions — score_awarded = 0, contributes 0 / max = 0 to the average. Drags the score down, which is what we want.
  • Case-study children — each child contributes one data point to the average. A 6-question case in a 25-question quiz contributes 6 / 25 of the weighting, not 1 / 25. Consistent with the data model (one row per child in attempt_items).
  • MCQ-only / dichotomous-only quizzes — items-correct and item-equivalent give the same number. They only diverge when partial credit is in play.
  • Single-question quiz — all three methods give the same number.

7.5 Schema ripple

nclex_attempts gains a final_score NUMERIC 0..1 column (settled in bank-consumption-attempt-creation.html §6.1's "Result" group). Set when status transitions to COMPLETED or TIMED_OUT; NULL while IN_PROGRESS. The other two display numbers are not stored — they're cheap to compute from nclex_attempt_answers at render time, and storing would be denorm without payoff.

8. Where scoring code lives settled

Decision (2026-05-04): lib/scoring/ at the lib root, not nested under lib/bank/.

Reasoning: scoring isn't bank-specific. The functions are consumed at multiple call sites — the editor (to compute marks at save time), the runner (to score student submissions), session aggregation (to compute final_score), and analytics paths. They're a domain-cross-cutting utility that belongs at the same level as other shared lib folders, not buried inside the authoring tree.

The exact location within lib/ can be revisited at build time — the file is small (5 pure TS functions plus a "compute marks" wrapper) and trivially movable. Don't over-plan it.

Settled in principle:

  • Pure TS, no DB calls, deterministic. Functions take (question_type, content, correct, answer) and produce { score_awarded, is_correct }.
  • The editor-side "compute marks from answer key" wrapper sits in the same module — both call sites take (question_type, correct) and need the same per-type dispatch.
  • Tests live alongside the functions (each tested against released NCSBN sample questions where available).
  • Versioning: scoring functions versioned separately from schema (per bank.md). When NCSBN updates NGN rules, function signatures stay; internals change.

10. Migration path settled

Decision (2026-05-04): manual backfill for existing rows; future rows handled correctly by the editor save handler.

The plan when the marks-as-system-managed change ships:

  • Existing rows (in nclex_bank_items and nclex_tutor_questions) get their marks manually corrected — either via a one-shot UPDATE that recomputes from question_type + correct, or row-by-row through the editor as curators next touch each question. Either approach reaches the same end state. Volume is small enough that we don't need a fancy migration script.
  • Future rows are correct by construction — the editor's compute-and-write step ensures every save produces an accurate marks value derived from the answer key. Save validation blocks malformed correct shapes before they can produce a wrong marks value.
  • The DEFAULT 1 on the column can stay or go — practically meaningless once the editor always computes, but harmless to keep. Drop at build time if the surrounding migration is already touching the column; otherwise leave it.

Belt-and-braces enforcement (PL/pgSQL trigger that recomputes on INSERT/UPDATE) is not in v1 — soft enforcement via editor discipline is fine, since the editor is the only write path. Revisit only if a drift incident surfaces.
