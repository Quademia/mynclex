2. Architecture settled

Five settled architecture decisions. Each was discussed and locked one at a time. Implementation specifics (exact RPC signatures, debounce timing, optimistic UI patterns) defer to build — those don't change what the runner does, only how the network calls are structured.

2.1 Route path

URL: /session/[attempt_id]. Top-level, audience-neutral — not nested under /student/, /tutor/, or /admin/.

File location: app/(app)/(focused)/session/[attempt_id]/. The (focused) is a Next.js route group — parentheses mean "use this folder for layout grouping but don't include it in the URL." It defines the focused chrome (minimal topbar, no sidebar, distraction-free) applied to anything inside.

Why audience-neutral. The runner is invoked by all three audiences — students take quizzes, tutors preview assigned content, admins QA questions. CLAUDE.md's "audience grouping" rule was set for audience-specific surfaces (dashboards, settings); the runner is a focused tool that doesn't fit any one audience's chrome.

Why "session" and not "runner" / "quiz" / "attempt". "Runner" is internal terminology, never visible to users. "Attempt" is schema language, not student-vocabulary. "Session" matches our existing parent doc terminology (parent §15 — Source / Mode / Session State) and works naturally for both live AND review variants ("I'm starting a new session" / "I'm reviewing my last session").

Mode (live vs review) is derived from nclex_attempts.status — same URL for both. The runner reads the attempt row, sees status = IN_PROGRESS → live mode; status = COMPLETED / TIMED_OUT → review mode. The student clicks "Review" in History → lands on the same URL; component tree, data model, and layout are all the same with rationales visible and submit disabled.

2.2 Component shape — six block categories

The runner is a page with composed component blocks. Six categories:

  1. Page-level container — one top-level component (e.g. SessionPage). Loads attempt + items + snapshots + answers. Manages overall state (current position, mode). Branches into live or review variant based on status.
  2. Chrome (always-visible UI) — minimal topbar (session title, exit button, mark-for-review toggle), timer (only for timed modes), progress indicator ("Q3 of 25"), navigation footer / sidebar (shape varies by mode — sequential locks, free-nav allows jumps).
  3. Question rendering — a Question Area component that receives the current attempt_item + snapshot data, then branches by question_type into one of 9 per-type question components (one each for MCQ / TF / SATA / Select-N / Matrix / Highlight / Cloze / Drag-drop / Bow-tie). Each handles its own UI for that type.
  4. Wrapper panels (the "two-sided" case) — when the current item has parent_case_id (case child) or trend_id (trend question), the layout splits: [ Wrapper context ] | [ Question Area ]. Two wrapper components — Case panel (scenario + chart tabs; persists across all 6 case children) and Trend panel (time-series dataset). For non-wrapper questions the question takes full width.
  5. Submit / scoring feedback:
    • Submit button — chrome, not per-type
    • Per-element feedback decorations — folded into each per-type component (controlled by the mode prop — see §2.2.1)
    • Rationale (text + image) — shared <Rationale> sub-component, rendered by the page container in review mode (and in Untimed Learning per-Q after submit)
  6. Modals / overlays — discard confirmation (with type-DELETE-to-confirm per CLAUDE.md UI Conventions), Resume / Start fresh dialog, end-of-quiz confirmation, time-up notification.

2.2.1 Per-type components: single component, mode prop

Each per-type component takes a mode: "answering" | "review" prop and handles both states internally. One component per type; nine total. Three alternatives were considered:

  • (α) Single component, internal mode prop — adopted
  • (β) Two separate components per type (Answering + Review variants) — 18 total — rejected
  • (γ) Headless logic + thin wrappers — over-engineered for v1

Reasoning: the structural shape (option list, row grid, blank list, etc.) is identical between answering and review — only the decorations differ. Single component captures that without duplication. 9 components vs 18 means less drift risk. The component branches internally on render: answering = interactive controls; review = read-only with right/wrong indicators, per-option feedback, and correct-answer reveal.

Per-element feedback lives inside the type component because feedback isn't a separate block sitting below the question — it's woven into the question's structure (per-option indicator on MCQ, per-row marker on Matrix, per-blank dropdown reveal on Cloze, etc.). Only the per-type component knows where to put the decorations.

2.3 Data flow

By the time the runner page loads, every snapshot row already exists — the create-attempt transaction (covered in bank-consumption-attempt-creation.html) populated all 5 tables in advance. The runner is purely a reader. 

Builder: student clicks "Start Quiz"
         ↓
[create-attempt transaction]
  - 1 row in nclex_attempts
  - N rows in nclex_attempt_items (snapshots of questions)
  - rows in nclex_attempt_case_snapshots (one per case used)
  - rows in nclex_attempt_trend_snapshots (one per dataset used)
  - returns attempt_id
         ↓
Frontend routes to /session/[attempt_id]
         ↓
Runner mounts → reads from those 5 tables → renders Q1

Reads only from the 5 snapshot tables at runtime:

  • nclex_attempts — the row itself (mode, intent, status, timer state, source)
  • nclex_attempt_items — all delivered items in position order
  • nclex_attempt_case_snapshots — case scenarios + chart tabs
  • nclex_attempt_trend_snapshots — trend datasets
  • nclex_attempt_answers — any answers already submitted (for Resume / Review)

Never reads from nclex_bank_items, nclex_case_studies, nclex_case_study_tabs, nclex_trend_datasets, or nclex_tutor_*.

Writes only to:

  • nclex_attempt_answers — DRAFT rows (STUDY save-progress) and SUBMITTED rows on submit
  • nclex_attempts.last_activity_at — heartbeat
  • nclex_attempts.status — on terminal transitions (COMPLETED / TIMED_OUT / ABANDONED)
  • The mark-for-review table (settled per attempt-creation §6.3.4) on toggle

2.3.1 No answer-key leakage to live-mode client (Pillar 2 protection)

Pillar 2 (parent §3) says "no answer leakage." If the client receives correct_answer_snapshot_json for upcoming questions in live mode, a student with browser dev tools can read it. So:

ModeClient receives
Live mode (status = IN_PROGRESS) Attempt + items without correct_answer_snapshot_json, rationale_snapshot, rationale_img_snapshot — only the question shape (stem, options, etc.). Plus case/trend snapshots, plus existing answers.
After per-Q submit (Untimed Learning only) Submit RPC returns score_awarded, is_correct, plus correct answer + rationale + per-option feedback for that one question only. Upcoming questions stay sealed.
Review mode (status = COMPLETED or TIMED_OUT) Full keys, rationales, and rationale images for every item. The student needs to see what was correct.

The exact RPC signatures (single function that branches on status, vs two separate functions) defer to build — the rule is the planning decision.

2.4 Local state shape

Most state decisions are inherited from earlier docs; the runner just adopts them.

Lives in client memory (lost on refresh in EXAM, restored from server in STUDY):

  • Which question the student is currently looking at
  • Their in-progress answer for that question (before submit)
  • Mark-for-review toggles for the current session (cached from the marks table)
  • Modal / overlay state (is the discard dialog open?)

Persisted to the server (designed in earlier docs):

  • Submitted answers → nclex_attempt_answers rows on submit (attempt-creation §6.3)
  • Save-progress drafts → DRAFT rows in same table, STUDY mode only (§6.3.1)
  • Answer-change log → answer_changes_json event log (§6.3.3)
  • Mark-for-review toggles → its own table, written immediately on toggle (§6.3.4)
  • Activity heartbeat → nclex_attempts.last_activity_at (§6.1)
  • Status transitions → nclex_attempts.status on terminal (§6.1.3)

Core principle: in STUDY, client memory is a cache of server state — refresh and resume work because everything important hits the server. In EXAM, client memory is authoritative for in-progress answers (no drafts written) — refresh = lose state, but EXAM is single-sitting so it doesn't matter for product flow. Edge case: timer-expiry auto-submit when the client is connected uses whatever client memory has; lost-connection scenarios in timed exams are an edge-case settled at build.

2.5 Reuse from authoring previews

Each of the 9 authoring editors (lib/bank/editors/*-editor.tsx) has a working "preview" rendering that draws the question as a student would see it. Same for the case-study editor's chart-tabs preview and the trend editor's dataset preview.

Those become the structural starting point for the runner's per-type question components and the wrapper panels. The lift is "copy the rendering, swap the data source" (form state → snapshot data) and "add a mode prop for review/feedback decorations." No fresh design from scratch.

This is implementation guidance, not a planning decision — but worth recording so build sessions know to start from the existing previews rather than redesigning each component.

5. Question rendering — per type settled (6 of 9)

9 question types from §15 of parent doc. Each lives at lib/bank/runner/types/<type>.tsx as a single component with a mode: "answering" | "review" prop, structurally mirroring the MCQ pattern. Each module also exports a small isXxxComplete helper (boolean) that the runner consults to decide whether the Submit button is enabled — see §10.2 for the dispatch.

5.1 MCQ — single-select settled

Academic / paper-exam treatment (settled 2026-05-07 in mockup review). Each option is a row with:

  • Bold "A." letter prefix in default state — fixed 22×22 letter slot, period right-aligned within the slot.
  • State (selected / correct / wrong-pick) fills the slot with a coloured circle and drops the period; no horizontal layout shift on state change.
  • No tinted backgrounds — state is signalled by a 3px left-border accent + the letter circle.
  • Options indented (margin-left: 32px) and constrained (max-width: 460px) so they read as a narrow indented list rather than full-width cards.
  • Per-option feedback in review mode is a single italic muted line directly under the option text — no dashed top divider, no extra padding.
  • Verdict label is plain coloured text "✓ Correct" / "✕ Your answer" — no chip background.

Submit gate: must pick one option (selected != null).

5.9 TF — true / false settled

TF is a thin wrapper around McqRunner — TfContent = McqContent and TfCorrect = McqCorrect (lib/bank/types.ts §TF). The wrapper exists so each type owns its own component file (per BUILD_LIST §4.2), and to give TF-specific divergence a natural future home (locked 2-option semantics, marks max fixed at 1 per scoring §5.2).

Submit gate: same as MCQ — must pick.

5.2 SATA — select all that apply settled

Multi-select option list. Differs from MCQ:

  • Answer is string[] (toggleable membership). A click TOGGLES in/out of the array rather than replacing.
  • Review mode has 4 states per option (vs MCQ's 3):
    • right — picked AND correct (green circle, ✓ Correct)
    • wrong — picked AND not correct (red circle, ✕ Wrong pick)
    • missed — not picked AND correct (amber dashed border, ⚠ Missed)
    • (dim) — not picked AND not correct (no styling)
  • aria pattern is a group of toggle buttons (aria-pressed), not a radiogroup.

Submit gate: always submittable. Zero selections is a valid "none of these apply" answer (standard NCLEX behaviour, settled with Sam 2026-05-07). Untouched answers (Map has no entry → undefined) are coerced to [] at the call site.

5.8 SELECT_N — pick exactly N settled

SATA with a fixed pick-cap. The curator sets select_count (N); the student must pick exactly N.

  • Toggle behaviour caps additions at N — deselect always allowed, but adding when at the cap is a no-op.
  • When the cap is reached, unpicked options dim and become non-interactive (reuses .rn-opt.dim).
  • A small header above the options shows progressive state (count line):
    • 0 picked: Select 3.
    • 1 to N-1: 1 of 3 chosen · tap to deselect (italic, muted)
    • at cap: 3 of 3 chosen · tap a selected option to swap (accent, bold)
    The progression introduces the "tap to deselect" affordance BEFORE the student hits the cap — no surprise when they realise they want to swap a pick.

Submit gate: exactly select_count picks required. Hint when disabled: "Select N of N to submit".

5.7 Matrix — rows × columns settled

Each row picks exactly one column. Layout: each row is its own CSS Grid sharing the template minmax(180px, 30%) repeat(N, 1fr) where N = content.columns.length. Cells are clickable buttons with a radio-style ○/● glyph.

Visual hierarchy (settled 2026-05-08 in mockup review):

  • Outer 2px border + 6px radius wraps the entire matrix as a contained unit.
  • Each body row sits in a 1.5px-bordered row-block.
  • Header row uses just a bottom divider (no all-sides border) — frames the body without competing.
  • Cell radio glyphs are 20px (default ○ / picked ●) so they read clearly at a glance; missed-state ✓ is 18px.
  • Per-row feedback (review mode) renders below each row as a muted italic line.

Considered Variant A (constrained 60px cells) and Variant B (cells with column label inline). Both addressed the "wide empty cells" critique but introduced new costs — Variant B repeats long column labels in every cell, heavy with NCLEX-style wording (e.g. "Continue monitoring" / "Stop intervention"). Mobile-friendly variant deferred to slice 5.1e.

Reuses SATA's review-state classes (.right / .wrong / .missed) on cells: right = picked AND correct, wrong = picked AND not correct, missed = not picked AND correct.

Submit gate: every row must have a pick. Hint when disabled: "X of N rows answered — finish all to submit".

5.6 Highlight — passage with [[bracketed]] chunks settled

Passage text with double-bracket markers around clickable spans. The runner parses the stem positionally and matches the i-th [[..]] to content.chunks[i] for the chunk ID. Single brackets ([K+] = 3.2) are passage text and stay literal.

Architectural note: HIGHLIGHT is the first type where the per-type runner takes over stem rendering. RunnerQuestionArea skips its .rn-stem render for HIGHLIGHT and the runner emits its own parsed stem with chunks-as-buttons inline. Instruction also moves to ABOVE the passage for HIGHLIGHT — the student needs to know what they're hunting for before reading. CLOZE will follow the same pattern when wired (also stem-takeover, dropdowns inside the stem).

Universal no-hint design (settled 2026-05-08 with Sam):

  • Default chunks render as ordinary passage text — no background, no underline, no border colour, no hover affordance. Just cursor: pointer when over one.
  • Tap a chunk → goes yellow (selected). Tap plain text → silent. The "nothing happens" outcome IS the search feedback — the student infers "not a relevant phrase, keep reading."
  • Review states (right / wrong / missed) light up after submit; chunks the student didn't pick AND aren't correct render as plain text (no chrome).
  • Why no hint: the cognitive work IS the search. Pre-marking chunks would telegraph the answer space and shortcut the clinical reasoning the student is meant to do — same as the real NCLEX.

Orientation hint above the passage (discoverability safety net):

  • 0 picked: Tap a clinical finding in the passage to highlight it.
  • 1+ picked: X highlighted · tap a highlight to remove

Always visible. Students who tap and see "nothing happen" still know the question is interactive, they just haven't found a real target yet — the failure mode is "keep searching" not "give up."

Touch precision: chunks have 2x6 padding extending the tap-hit area beyond the visible text without visual effect. Keyboard a11y: :focus-visible shows a ring on each chunk as the user tabs through — mouse/touch users don't get this preview, accepted inconsistency.

Per-chunk feedback list (review mode) shows only chunks the student engaged with (picked) or should have engaged with (correct). Neutral chunks aren't shown — feedback for passage text the student rightly ignored is noise.

Submit gate: zero highlights allowed (SATA precedent). A deliberate "no chunks are relevant" answer is valid.

8. Timer behaviour settled (2026-05-09)

8.1 Unified clock — always present, behaviour differs by mode

Every attempt has a clock pill in the topbar regardless of mode. The clock is visible by default; the student can hide it via a small eye-icon next to the pill (per-attempt scope — preference resets at next attempt). What the pill shows differs by mode:

  • Untimed modes render a stopwatch — count-up from started_at, permanently neutral grey, no animations, no warnings. This attempt-level stopwatch is independent of the per-question engaged-time engine (attempt-creation §6.3.2) — different clock, different rule; the two do not sum.
  • Timed modes render a countdown — counts down toward started_at + duration_seconds, escalates tone at warning tiers, locks visibility once the first warning fires.

Why unified. Implementation cost is essentially zero (same React effect, same format function, the only branch is whether delta = now − started_at or (started_at + duration) − now). Showing untimed students how long they're spending trains pacing awareness without imposing pressure. Industry pattern (UWorld, ATI both show running time in practice mode). Real NCLEX shows only a countdown, never a per-question stopwatch — but Untimed Learning isn't simulating the real exam, so authenticity (Pillar 2) doesn't bind here.

8.2 Format

One format function used by both stopwatch and countdown:

  • mm:ss for any time under 1 hour (e.g. 14:32).
  • h:mm:ss once the time crosses 1 hour (e.g. 1:00:00, 2:34:18).

8.3 Stopwatch — visual rules

Permanently neutral. Same grey pill family across the entire attempt. Never amber, never red, never animated. The point is information without pressure — the moment the pill changes tone, it becomes a stress signal, which defeats the untimed framing.

No expiry, no auto-submit. Status transitions only on explicit Finish (→ COMPLETED) or via discard / orphan cleanup (→ ABANDONED). Never TIMED_OUT.

Reset on Resume. Untimed STUDY supports Resume (slice 4.6). When a student returns three days after their first session, the literal now − started_at elapsed time would read "72:14:33" — useless and confusing. The stopwatch resets to 0:00 on Resume, with a small "Resumed" tag below the pill. We don't claim cumulative engagement-time as a number we'd hold the student accountable to. This sidesteps the engagement-clock pause/resume complexity that STUDY-timed needed (deferred to v2 anyway per §11).

8.4 Countdown — warning tiers and tone progression

Warnings fire at 30, 15, 5, and 1 minute remaining. Each tier only fires when the attempt is long enough for the warning to be a meaningful "approaching the end" signal rather than a distraction near the start.

TierTriggerFires when duration_seconds ≥ToneEffect
30 minremaining ≤ 30 min60 minsubtle ambersingle pulse on appearance, locks re-hide
15 minremaining ≤ 15 min30 minmedium ambersingle pulse
5 minremaining ≤ 5 min10 minstrong ambersingle pulse
1 minremaining ≤ 1 minalways (any timed mode)redbrighter pulse on appearance, subtle pulse every 10s; pill copy gains "1 min left" label

Examples — so the "fires when ≥" rule is concrete:

  • A 38-min quiz sees 5 min → 1 min only (30 and 15 don't qualify).
  • A 113-min mock sees 30 → 15 → 5 → 1 — the full ladder.
  • An 8-min curator-set timed attempt sees 1 min only — the 5-min tier requires duration ≥ 10 min so it doesn't fire 3 minutes in. Acceptable: an 8-min attempt is so short the 1-min red is enough.

Tone escalates only — never reverts. Once amber, stays amber-or-darker for the rest of the attempt. Once red, stays red. Cleaner mental model than "tone resets between tiers" — the student reads tone as "how close to the end am I" without tracking which warning was last.

8.5 Hide toggle

Small eye-icon button in the topbar next to the clock pill. Default visible; clicking the eye hides the pill but leaves the eye visible so the student can re-show. Behaviour:

  • Per-attempt scope. Hide preference resets at each new attempt. No localStorage, no global preference — default-safe so a one-time anxious hide doesn't silently follow the student forever.
  • Allowed in all 8 (mode, intent) tuples — including timed EXAM. Even on the real exam, students cover the clock with their hand; on-screen visibility doesn't actually prevent the workaround. The auto-reappear at warning is the safety net.
  • Auto-reappears at the first warning that fires. Once the topbar enters warning territory (any tier), the pill becomes visible again with the warning tone applied, brief pulse to draw attention. The eye-icon disables — the student cannot re-hide for the rest of the attempt. Locking re-hide once warning fires is the safety mechanism.
  • No auto-reappear in untimed modes — there's no warning to trigger it. The student can hide and show freely throughout.

8.6 Expiry behaviour (timed modes)

When now() ≥ started_at + duration_seconds:

  • Status flips to TIMED_OUT (per attempt-creation §6.1.3).
  • Any DRAFT rows in nclex_attempt_answers flip to AUTO_SUBMITTED with submitted_at = ended_at. Pending state lives server-side via universal save-on-tap (§9.1), so auto-submit is a single SQL UPDATE — no client-flush race.
  • Items with no answer row at expiry get a SKIPPED row inserted (status SKIPPED, answer_json null, score 0).
  • Final score computes across all rows. ended_at = started_at + duration_seconds (the true expiry moment, not the detection moment).
  • Runner transitions to review mode — same render path as a deliberately-finished COMPLETED attempt.

Detection is lazy per attempt-creation §6.1.3: the cleanup sweep or the runner-on-page-mount notices the expiry condition and triggers the flip. No active server poll required.

9. Save-progress and Resume 9.1 settled · 9.2 skeleton (slice 4.6)

9.1 Save-progress — universal save-on-tap settled (2026-05-09)

Every meaningful answer change writes to nclex_attempt_answers immediately — not just at Submit click. The runner calls nclex_save_progress(attempt_item_id, answer_json) on every material change to the student's pick (debounced for rapid clicks). The RPC upserts a row with submission_status = 'DRAFT' and appends an entry to answer_changes_json per attempt-creation §6.3.3.

Universal across all 7 active tuples — Untimed Learning included (backported from the original "submit-creates-row directly" approach). One mental model: the runner persists every intermediate state, and the final submit (per-Q for UL, batched Finish for UT/TFN, per-Q Submit-and-continue for TS) is just a status flip from DRAFT → SUBMITTED on the existing row. CAT remains the exception per §6.1.2 — pause/resume invalidates the IRT estimate, so save-on-tap doesn't apply.

Why universal, not STUDY-only. The original plan deferred save_progress to slice 4.6 on the assumption that Resume was its only consumer. Three things changed during slice 4.5 design: (1) timed exams became resumable mid-timer (revised §6.1.3) — the universal save now serves EXAM too; (2) auto-submit on timer expiry is dramatically simpler when the server already has the latest pending state (single UPDATE flips DRAFT → AUTO_SUBMITTED, no client-flush race condition); (3) answer-changes analytics (§13) require the per-tap event log regardless of mode — UL is in fact the mode where changes-tracking is most valuable. Save-on-tap does triple duty.

Cadence — debounced per material change. Per attempt-creation §6.3.3, "material change" means each distinct option toggle (SATA, Bow-tie, Drag-drop), per-blank commit (Cloze), or completed selection (MCQ, TF, Select-N, Matrix row, Highlight chunk). Rapid keystroke-level edits coalesce via a client-side ~500ms debounce before the RPC fires (tunable at build).

Heartbeat. Every save-progress call also bumps last_activity_at server-side. Drives orphan-cleanup detection (slice 2.4) and EXAM re-entry detection threshold (attempt-creation §6.1.3 — 60s inactivity is the heuristic for "they left and came back").

Conflict resolution. Snapshots prevent shape mismatch — if a curator edits the underlying question mid-session, the runner reads the snapshot from nclex_attempt_items, not the live bank. Pending answer's structure stays valid for the lifetime of the attempt.

9.2 Resume detection on mount skeleton — slice 4.6

When the runner mounts and finds existing DRAFT rows for the attempt, it restores the pendingAnswers map and positions the student at the last-viewed Q (settled — not last-submitted-Q+1, not Q1; matches user expectation "pick up where I left off").

Save half is now done in 4.5 (§9.1 above). Slice 4.6 only adds the load-on-mount logic + the Resume banner UI on the Builder dashboard.

10. Submission flow settled (per-Q + per-type completeness gates)

10.1 Two submission models by mode

Two submission models depending on mode:

  • Per-question submit (Untimed Learning): student picks answer → clicks Submit → sees rationale → clicks Next → next question.
  • Batched submit (Untimed Test, Timed Free Nav, Timed Sequential): student answers all questions → clicks final Submit → sees results.

Each submission writes to nclex_attempt_answers via submitAnswerAction; scoring runs in TS (lib/scoring/scoreAttempt) so the test suite is the single source of truth. The submit RPC is thin (validate ownership + status, INSERT row, bump last_activity_at); for live mode it returns the per-Q unseal envelope (correct + rationale + marks_max) for the one item the student just submitted — other items stay sealed.

10.2 Per-type completeness gate settled

Each per-type module (lib/bank/runner/types/<type>.tsx) exports a small isXxxComplete helper that returns whether the current pending answer is enough to enable Submit. runner.tsx dispatches through a switch (getSubmitGate) that returns:

  • canSubmit: boolean — controls the Submit button.
  • submitValue: BankItemAnswer | null — the value to send to submitAnswerAction (null when the gate fails).
  • hint: string | undefined — footer copy when canSubmit is false. Type-aware (e.g. "Select 3 of 3 to submit" for SELECT_N).

Per-type rules (settled 2026-05-08 with Sam):

TypeRuleHint when blocked
MCQ / TFMust pick one"Pick an option to enable Submit"
SATAAlways submittable (zero allowed — "none of these apply")—
SELECT_NExactly select_count picks"Select N of N to submit"
MATRIXEvery row must have a pick"X of N rows answered — finish all to submit"
HIGHLIGHTAlways submittable (zero allowed — "no chunks are relevant")—
CLOZE / DRAG_DROP / BOWTIETo be settled in 4.2 (likely "every blank / slot / wing filled")—

Architectural reason for per-type ownership: keeps runner.tsx from accumulating a long if-chain of per-type rules. When a 10th type is added, it ships with its own isXxxComplete helper and one new case in the switch — no central file gets bloated, and the rule visibly belongs to its type.

Edge case: SATA / HIGHLIGHT have a "zero is fine" rule — when the student lands on the question and never interacts, the pending Map has no entry (undefined). The dispatcher coerces undefined → empty array at the call site so the submit can fire with an empty answer (which is then scored as wrong).

11. Scoring skeleton

Per Pillar 2 (authentic exam mechanics), scoring follows NCSBN rules: partial credit where the real exam allows it, all-or-nothing where it doesn't. Per question type:

  • MCQ / TF / Select-N: all-or-nothing
  • SATA: partial credit (NCSBN's "all correct, no incorrect" rule — TBD exact algorithm)
  • Matrix: per-cell partial credit
  • Bow-tie: per-section partial credit (priority + actions + parameters scored separately)
  • Drag-drop / Cloze / Highlight: TBD per type

Scoring should run from correct_answer_snapshot_json against answer_json, not from live authoring tables. Probably a server-side function per question type.

12. Feedback timing skeleton

When does the student see whether they got it right + the rationale?

  • Untimed Learning — immediately after submit, before advancing
  • Untimed Test — at the end (results screen + Review)
  • Timed Free Navigation — at the end
  • Timed Sequential — at the end
  • CAT — at the end (verdict only, not per-question)

13. Answer-changes tracking settled (2026-05-09)

The runner tracks every intermediate selection change to enable the R→W and W→R analytics in parent §11 ("you changed 14 correct answers to wrong"). Storage is settled in attempt-creation §6.3.3 as an append-only event log on nclex_attempt_answers.answer_changes_json: 

[
  { "at": "2026-05-04T12:30:14Z", "from": null,        "to": ["A"]       },
  { "at": "2026-05-04T12:30:31Z", "from": ["A"],       "to": ["A","C"]   },
  { "at": "2026-05-04T12:30:48Z", "from": ["A","C"],   "to": ["B","C"]   }
]

Trigger — every material change, debounced for rapid clicks. Settled in §9.1 + §6.3.3: one entry per distinct option toggle, per-blank commit, or completed selection. Keystroke-level edits coalesce via the same ~500ms debounce that drives save-on-tap. The same RPC (nclex_save_progress) writes both the answer state and the changes log entry — answer state and changes are not separate concerns.

R→W / W→R counts are derived, not stored. They're computable from the log + the correct-answer-key snapshot at any point. Counts cannot be reconstructed from each other, but both can be reconstructed from the log — so we keep the log canonical and surface counts wherever needed. Surfacing in the results screen + analytics page (parent §11) is review/analytics work, not runner work.

16. Question grid — the navigation surface settled

The runner's primary navigation surface for any mode that allows free movement between questions, and the default review surface for every finished session regardless of mode. Settled across six structural dimensions (where it shows, placement, cell content, cell state palette, cell layout, interaction model, mobile variant) on 2026-05-06. Pixel values, exact palette tones, and the final visual treatment defer to Claude Design.

16.1 Where the grid shows — by mode and state

Two contexts: active session (student is taking the quiz) and review (student is looking at a finished attempt). The grid has different visibility rules in each.

ModeActive sessionReview
Untimed Learning (STUDY)✅ grid✅ grid
Untimed Test✅ grid✅ grid
Timed Free Navigation✅ grid✅ grid
Timed Sequential❌ no grid✅ grid
CAT❌ no grid✅ grid

Rule: active session shows a grid wherever navigation is free; sequential and CAT have no grid during the run. Every finished attempt shows a grid in review, regardless of which mode ran — because the answer key is unsealed post-completion and the grid is the natural surface for "show me where I went wrong" navigation.

16.1.1 Untimed Learning's hybrid state

Other free-nav modes (Untimed Test, Timed Free Nav) keep every cell uniformly pre-submit until a single batched submit grades everything in one event. Untimed Learning is different: each question gets per-Q submit with immediate feedback. So at any point during an Untimed Learning session, some cells are already-graded post-submit (rationale visible, key unsealed) and some are still-answerable pre-submit (key sealed). Both populations co-exist in the same grid.

Two architectural notes that follow:

  1. The "no answer-key leakage" rule (§2.3.1) already accommodates this — there is an explicit "after per-Q submit (Untimed Learning only)" path that returns the key for that one Q only. Each cell's seal flips independently.
  2. The mode: "answering" | "review" prop on per-type components is per-item in Untimed Learning, not per-attempt. §2.2.1 phrasing implies attempt-wide; Untimed Learning needs item-level granularity.

16.2 Placement on screen

Desktop

  • Right-edge sticky panel — flush to the viewport edge (no gutter on the right). Visual continuity is the placement metaphor with the Builder's summary card, not the spacing — runner uses focused chrome (no sidebar nav), so it has the full viewport to work with.
  • Default state: open. Question (or [Case panel | Question Area] when a wrapper is showing) reflows to fit the remaining width.
  • Width when open: ~220px. Slim — cells are small numbered squares and don't need Builder's text-heavy 340px column.
  • Toggle on the inner (left) edge of the panel collapses or reopens.
  • Collapsed = thin handle. A vertical strip carrying just the reopen toggle. No ambient state strip — the chrome counter (Q 14 of 75) handles glanceable progress.

Mobile

  • Default state: collapsed. No grid card visible.
  • Open shape: full-screen bottom sheet. Slides up from the bottom, dominates the viewport. The student is navigating — they don't need to see the current question while picking another. Half-sheet wastes pixels; popover can't fit 25–75 cells.
  • Open control: a grid icon in the topbar (not a hamburger — that traditionally reads as "site nav menu" and would be ambiguous).

Wrapper interaction (cases + trends) — desktop only

When a wrapper renders, the [Case panel | Question Area] split needs the room. The grid auto-collapses on wrapper entry, sticky-restores on wrapper exit. Three modes follow:

  • Push mode (normal) — grid open, runner area reflows to fit. Used when no wrapper is showing.
  • Auto-collapsed mode (wrapper entry) — grid collapses to its handle. Sticky behaviour: when the wrapper ends, grid reopens to whatever the student had set (open or closed). The auto-collapse is a temporary accommodation, not a state change.
  • Overlay mode (manual-open during a wrapper) — student can still open the grid during a wrapper. When they do, it floats over the right edge of the runner instead of pushing — preserves the [Case panel | Question Area] layout. Tapping a cell collapses the overlay back to the handle.

On mobile the rule doesn't apply — grid is never auto-open on mobile, so there is nothing to auto-collapse.

16.3 Cell content

Just the question number, centred. No glyphs, no icons, no question-type indicators, no time readouts. All state is encoded via colour (§16.4 below).

Above the grid: a filter toggle row. Single-select toggles to switch the visible subset:

  • All — default, every cell visible
  • Marked — only flagged cells
  • Unanswered — only cells with no answer committed
  • Wrong — only cells the student got wrong (review state and Untimed Learning post-submit cells)

Filtering replaces the need for corner glyphs — students who care about a state filter it down rather than hunting visually.

16.4 Cell state palette

The state list

Pre-submit fill states (key sealed):

  • Unanswered — neutral, default
  • Answered — student has committed an answer (will be graded at final submit)

Post-submit fill states (key unsealed):

  • Right — answer matched the key
  • Wrong — didn't match
  • Skipped / null — locked in with no answer (timer expiry only — distinct from unanswered, because the student can no longer act on it)

Cross-cutting (apply on top of any fill state):

  • Current — the cell the student is on right now. Exactly one at a time.
  • Marked — flagged for review. Independent of every other state — a marked Q can be answered, unanswered, right, or wrong.

Three-channel encoding

Current + Marked + (any fill) can all be true on the same cell. Background cannot carry both marked and fill state. The encoding uses three orthogonal channels:

ChannelEncodesBehaviour
Fill (background) The 5 fill states (unanswered / answered / right / wrong / skipped) 5 distinct tones
Border Marked (yes/no) Default thin border, or distinct accent colour when marked
Outer ring / glow Current (yes/no) Off by default. On for the current cell — a coloured outline drawn outside the cell, like a focus ring. Sits on top, doesn't fight fill or border.

Composes cleanly: a cell can be right + marked + current and still read distinctly (e.g. green fill + amber border + blue outer ring).

Semantic direction design picks tones

  • Unanswered → neutral (off-white / pale grey)
  • Answered → soft fill (typically a muted blue or slate) — "you've done something here, but no judgement yet"
  • Right → green family
  • Wrong → red family
  • Skipped → amber / yellow family — distinct from grey unanswered, distinct from red wrong

Accessibility constraint

Palette pairs must differ in brightness as well as hue. Right (green) and wrong (red) read as the same grey to red-green colour-blind users if hue is all that distinguishes them — but a light green vs dark red still reads as light vs dark. Cheap, no glyphs, doesn't break the lean look.

Re-submit lock in Untimed Learning

An answered-wrong cell in Untimed Learning is locked at "wrong" — student cannot resubmit after seeing the rationale. Resubmitting after seeing the key would corrupt both the learning loop (immediate feedback turns into immediate correction) and the answer-changes analytics (parent §11). So there is no "wrong but resubmittable" state to render.

16.5 Cell layout

Shape and size

  • Square cells (UWorld / Archer / NCSBN convention; 1–2 digit numbers fit cleanly).
  • Desktop: ~36–40px (fits ~5 across in the 220px sidebar).
  • Mobile: ~44px (iOS tap-target floor).

Columns

  • Desktop: fixed 5 columns. Sidebar is fixed-width, so the column count is fixed too.
  • Mobile: responsive 5–7 columns. Sheet is wider; column count adapts to screen width.

Spacing

Tight gaps (~4–6px between cells, slightly larger between rows). Density helps the student see more at once. The grid is a navigation tool, not a layout to admire.

Case grouping

Six case-child cells are visually grouped by a subtle tinted band behind them — no labels, no dividers. The band can be L-shaped if the case spans two rows (it always will at 5 cells per row). All cases in a session use the same tint — answers "where does this case start/end" without trying to answer "are these two cases the same?" (a question students don't ask).

Trend questions are not grouped — they scatter individually per attempt-creation §8.3. Each trend question is just a standalone cell.

Filter header + scroll

The filter toggle row (§16.3) lives in a sticky header at the top of the grid panel. Cells scroll under that header. The panel itself stays sticky to the viewport edge (desktop) or full-sheet positioning (mobile).

16.6 Interaction model

Primary — single click/tap navigates

  • Desktop sticky panel (push mode) — click a cell → cell becomes current (gets the outer ring), grid stays open.
  • Desktop overlay mode (manual-opened during a wrapper) — click → navigate, AND the overlay collapses back to the thin handle. The student opened it for one navigation move; once moved, get it out of the way.
  • Mobile sheet — tap → sheet closes → question loads. Always.

Filter toggles — single-select

Tap Marked → only marked cells visible. Tap All to reset, or tap the same filter again to deselect. Multi-select (e.g. "marked AND wrong") is a v2 ask. Single-select keeps the toggle row clean.

v1 skips

  • Hover tooltips (would re-introduce per-cell content we just stripped)
  • Keyboard shortcuts beyond a11y minimums (no number-to-jump, no arrow-key nav)
  • Long-press / right-click context menus
  • Search box ("jump to Q __")
  • Drag to reorder (n/a — order is fixed by the snapshot)

v1 keeps — accessibility minimums

  • Cells are tab-focusable; tab moves through cells in order
  • Enter / Space activates a focused cell
  • Filter toggles are keyboard-reachable
  • Each cell announces its state to screen readers (e.g. "Question 47, answered, marked"). State expressed by colour alone fails screen readers — the announcement is required.

No disabled cells in v1

All four grid-eligible modes (Untimed Learning, Untimed Test, Timed Free Nav, plus Review) allow free navigation to any question. Nothing is locked or greyed out. The "can't go forward in Untimed Learning until you submit Q5" flavour was rejected at §16.1 — Untimed Learning is fully free-nav.

Navigation-only — not action

The grid is a navigation tool, not an action tool. The student cannot mark, unmark, or change an answer from the grid — only navigate. This rule is what keeps cells uniformly simple.

16.7 Mobile variant

Most of the mobile shape is established by the dimensions above. Pulling it together, plus the few mobile-specific decisions:

Open control

Topbar grid icon (e.g. ⊞ / 9-dot square). Not a hamburger — that traditionally reads as "site nav menu." Final visual is Claude Design's call but the semantic should be "question grid," not "menu."

Sheet dismissal

  • Tap a cell (primary intent — navigation)
  • Tap the close control / chevron-down at the top of the sheet
  • Tap the backdrop above the sheet
  • (Optional, design's call) Swipe-down gesture — not v1-required

Sheet shape

Full-screen overlay. Covers the topbar entirely. Runner uses focused chrome (already minimal — no sidebar nav, no product switcher), so losing the topbar momentarily during a navigation interaction is fine. The student is task-focused on picking a cell.

Sheet header (sticky at top of sheet)

  • Filter toggle row (All / Marked / Unanswered / Wrong)
  • Close control on the right
  • "Q 14 of 75" counter on the left to anchor the student

In-wrapper open behaviour

Student on a case-child taps the grid icon → full-screen sheet covers case panel + question + chrome → student taps a cell → sheet closes → returns to runner. If the destination is another child of the same case, the case panel stays mounted; if outside the case, it unmounts. Same outcome as desktop, just with a sheet instead of an overlay.

Breakpoint

The sticky sidebar needs ~220px + room for the question + room for the case panel when one is showing. Practical floor: ~1024px (laptop-class). Below → bottom-sheet. Tablets in portrait probably also bottom-sheet; tablets in landscape might support sidebar. Exact breakpoint is Claude Design's call.
