What this covers

The navigation shape for TUTOR role users on MyNclex. Covers the global tutor workspace, the per-programme workspace, how the two relate, and the sub-navigation inside My Bank.

This does NOT cover student, admin, or super_admin navigation — those are separate specs in the same series.

Core model

A tutor has two distinct working contexts, each with its own sidebar:

  • Global context — cross-programme work. All programmes, their private question bank, all their students across every programme, payment records, profile.
  • Programme context — scoped to one programme. Curriculum build (programme layer), cohort management (the specific runs), live sessions, students, results.

Only one sidebar renders at any time. Entering a programme replaces the global sidebar with the programme sidebar. Leaving (back pill or logo) restores the global sidebar.

Why two sidebars? Tutor workflows genuinely split into "across all my work" and "inside this one programme." A single sidebar trying to cover both would either be too long or force awkward nesting. Two contexts keeps each view tight and scannable.

Notes on global behaviour

  • My Bank is global, not programme-scoped. A tutor's private questions belong to them, not to a programme — they can pull any question into any quiz on any programme.
  • My Students is a global roster. If a student is enrolled in multiple of the tutor's programmes, they appear once here. The per-programme Students view inside a programme is the scoped version.
  • Payments is a placeholder in v1. Tutor programme fees stay off-platform between tutor and student. This menu only reflects tutors' own subscription payments to QAcademy.

Programme context

Entered by clicking a programme row on the Programmes list. The sidebar replaces the global one with a programme-scoped set of items, and the topbar gains a back pill + programme title.

Topbar

Left side

  • QAcademy logo + wordmark — clicking returns the tutor to their Home (Programmes list with global sidebar). Works from any context.
  • Product label: · Tutor.
  • Back pill + programme title — shown only inside a programme. Clicking the pill returns to the global view.

Right side

  • Role chip: Tutor. If the user has other roles too (e.g. Sam is Super_admin + Tutor), the chip becomes a dropdown for role switching. (Pattern inherited from Slice 2.5 shell.)
  • User menu avatar: click opens dropdown → name, email, Sign out.

Layout composition

  • Global tutor/layout.tsx renders the global sidebar.
  • Nested programmes/[id]/layout.tsx replaces the sidebar for that subtree. Also injects the back pill into the shared topbar via context or a slot pattern.
  • The topbar itself lives on the (app) layout one level up — it's the same component across student, tutor, admin. Only the contents of the "product label" and "context pill" slots change.

Build order

  1. Tutor global layout + sidebar + Programmes page stub (list).
  2. My Bank sub-nav wiring. Point Case Studies / Trends to existing admin list components behind a surface="tutor" prop (the shared pattern from Slice 2.1).
  3. My Students, Payments (placeholder), Profile — page stubs.
  4. Programme-scoped layout + sidebar + Overview page stub.
  5. Cohorts page + cohort detail sibling subtree as cohort work lands (slice 9.2).
  6. Remaining programme pages as feature work lands (Curriculum, Sessions, Students, Results).
  7. Mocks + Assignments wait for their feature sprints — nav slots are reserved but render "coming soon" pages.

Out of scope for this spec

  • Student, admin, super_admin navigation — separate specs.
  • Public pages (tutor profiles as seen by prospective students) — sit outside (app).
  • Mobile-specific drawer/hamburger — companion spec after desktop lands.
  • Notifications, search, or other topbar additions — layout has room.
