1. Scope and what's out of scope settled

In scope: the create-attempt path for fixed-length modes (Untimed Learning, Untimed Test, Timed Free Navigation, Timed Sequential) when the source is Custom-built (the student configured filters in the builder).

Out of scope here:

  • CAT — fundamentally different selection model (one question at a time). Noted briefly in §13; full design in §16 of parent doc.
  • Programme-assigned and Readiness Pack source paths — flagged in §9, settled separately when those surfaces are planned.
  • Runner rendering, scoring, and review — separate planning tasks.
  • RLS policies, exact column types, exact RPC signatures — build-time concerns, not planning-time.

2. Architecture settled

Frontend sends to backend:

  • filters_json — the builder's pool + content + tags + topic state
  • mode — one of the 5 mode codes
  • requested_count — number

Backend does, in one transaction:

  1. Validate student access
  2. Validate filters, mode, count
  3. Build the candidate unit pool (the "what's eligible" query)
  4. Randomly select units to hit the count target
  5. Expand units into per-question attempt items (a case unit becomes 6 items)
  6. Snapshot question content, case context, and trend context — everything the runner needs to render and score
  7. Return attempt_id

Frontend hands attempt_id to the runner. The runner reads only from the snapshot tables, never from the live authoring tables.

Why this shape:

  • One transaction means the student can't end up with a half-created attempt.
  • The frontend never sees the candidate question list, so it can't be tampered with client-side.
  • Selection logic lives in SQL alongside the count RPC the builder uses for live counts (§17 of parent doc), so the two share their definition of "eligible." Live count and the actual quiz can never disagree.
  • The runner reading from snapshots means a curator editing a question, case, or trend mid-session does not change what the student is seeing.

3. Selection units settled

The selector does not pick raw questions. It picks units, then expands them into per-question attempt items.

3.1 Standalone question

  • parent_case_id = null AND trend_id = null
  • 1 unit produces 1 question

3.2 Trend-linked question

  • trend_id != null
  • 1 unit produces 1 question (Trends are not atomic — see §10 of parent doc)
  • A single Trend question can be selected on its own; the runner loads the linked Trend dataset snapshot beside it

3.3 Case Study

  • 1 case unit produces 6 questions, expanded in case_position order (Q1 → Q6)
  • Case Studies are atomic — the builder must never select individual children
  • Only complete, valid cases are eligible (all 6 children present and published)

Candidate pool example (after filters applied):

Unit typeUnit IDQuestions produced

QUESTIONNCLEX_TRD_Q011

QUESTIONNCLEX_SATA_0041
CASENCLEX_CS_0026

Random selection happens from this unit pool.

4. Count handling settled

Rule: target with drift.

The selector aims for requested_count questions. It picks units randomly with no preference for unit type. If the next pick would land within ±3 of target, take it. Stop when within ±3 of target.

If the pool can produce fewer than (requested_count − 3) questions, the create-attempt RPC fails with an actionable error: "Only N questions can be selected with these filters. Reduce count or loosen filters." The same condition disables Start in the builder (§17 of parent doc).

Why drift over the alternative ("never exceed requested_count, skip any case that doesn't fit"):

  • "Never exceed" systematically skips cases late in the selection because their slot_cost = 6 won't fit the remaining slots. Result: the final quiz under-represents cases relative to the matched pool. A pool that's 40% case-derived could end up 15% case-derived in the actual quiz. Misleading.
  • The breakdown preview line in the builder already says "Roughly N MCQ, N SATA…" — the student is trained to expect approximation.
  • Telling the student "27 questions for your 25-question quiz" is honest. The drift is small (±3 = ±12% on a 25-Q quiz).

The actual count delivered is recorded on the attempt row (column shape in §6). The breakdown preview RPC and the create-attempt RPC use the same selection logic, so what the preview promises is what the attempt delivers.

5. Snapshotting strategy settled

Snapshot at attempt creation, not at scoring time. Snapshot everything the runner needs to render and score:

  • Question stem, instruction, content payload (options, blanks, etc.), classification
  • Correct answer key
  • Per-option rationales and overall rationale
  • Marks/scoring config
  • For case-study children: the parent case's title, scenario summary, and all chart tabs (snapshot the case once per attempt, not once per child)
  • For trend questions: the trend dataset's title, scenario, kind, row labels, timepoints, rows (snapshot the dataset once per attempt, not once per question that uses it)

Why snapshot rationales and correct answers (not just stems):

  • Untimed Learning shows the rationale immediately after submit. If a curator edits the rationale mid-quiz, two consecutive submissions in the same session would render under different rules.
  • A correct-answer edit mid-session would mark one student right and another (who picked the same option) wrong if the runner re-fetches. Score against the snapshot — invariant per attempt.
  • The size cost of bundling rationales into the snapshot is trivial relative to the integrity benefit.
Resume implication: a Resume two days later renders exactly what the student started with, regardless of any curator edits in between.

6. Tables — the shape settled column lists open

Three core tables for the attempt itself, two snapshot tables for shared clinical context.

6.1 nclex_attempts

One row per quiz session.

Working column list (finalise at build time):

Identity:

  • attempt_id (pk) — UUID, server-generated, opaque. Build-time choice between v4 (native gen_random_uuid()) and v7 (pg_uuidv7 extension); v7 preferred for sortable PK / cheaper cursor pagination on the History page.
  • student_id

Source:

  • source — CUSTOM_BUILT / READINESS_PACK / PROGRAMME_ASSIGNED
  • readiness_pack_id — nullable FK to nclex_readiness_packs. Set when source = READINESS_PACK; NULL otherwise. See §6.1.1.
  • programme_activity_id — nullable FK to nclex_programme_activities. Set when source = PROGRAMME_ASSIGNED; NULL otherwise. See §6.1.1.

Configuration:

  • intent — STUDY / EXAM. Set at attempt creation. Drives Resume rules, cleanup rules, and runner timer behaviour. See §6.1.2.
  • mode — UNTIMED_LEARNING / UNTIMED_TEST / TIMED_FREE_NAV / TIMED_SEQUENTIAL / CAT. Combined with intent as a validated tuple — see §6.1.2.
  • duration_seconds — nullable. Set for timed modes (whether EXAM wall-clock or STUDY engagement-clock). NULL for untimed modes. Stored at attempt creation so per-mode default changes don't break in-flight attempts.
  • mode_overrides_json — nullable. NULL by default; populated only when a tutor or pack author overrode the standard rules for this attempt (e.g. extended-time accommodation).
  • filters_json — the builder config snapshot.

Status / lifecycle:

  • status — IN_PROGRESS / COMPLETED / TIMED_OUT / ABANDONED. See §6.1.3.
  • created_at — set automatically at row insert (builder Start click). Never overwritten. See §10.
  • started_at — set by the preflight-Start RPC. NULL until the preflight is confirmed. Drives Resume detection and timer-anchor for §11.
  • last_activity_at — touched by the runner on every student action (answer submit, save-progress, page navigation). Used by orphan-cleanup and STUDY-engagement-clock pause logic. Distinct from updated_at because admin-driven row changes shouldn't affect cleanup or pause timing.
  • ended_at — set when status transitions to a terminal state. Semantics differ by status: submit moment for COMPLETED; started_at + duration_seconds for TIMED_OUT (true expiry, not detection); cleanup-or-discard moment for ABANDONED. The status field differentiates.
  • updated_at — auto-bumped on any row change.

Counts:

  • requested_question_count — what the student asked for. Always counted in questions (the builder count box says "25 questions").
  • actual_question_count — number of nclex_attempt_items rows delivered. What the student actually answers.
  • actual_unit_count — number of selection units the selector picked. Cases counted as 1 unit. Differs from actual_question_count when cases are present (1 case unit = 6 question rows).

Result (non-CAT):

  • final_score — NUMERIC 0..1. The canonical session score, computed as the item-equivalent average across all attempt items (each item normalised to score_awarded / marks_snapshot, then averaged). Set when status transitions to COMPLETED or TIMED_OUT; NULL while IN_PROGRESS. Drives Trend (parent §3), Readiness Signal (parent §6), Slice labels (parent §13), and the headline number on the results screen. Display layer multiplies by 100 for percentage rendering. See bank-marks-and-scoring.html §7 for the aggregation reasoning and the two supplementary numbers (items-correct, total-points) that the results screen also displays — those are computed on read from nclex_attempt_answers rows, not stored.

CAT-specific result columns are settled in bank-consumption-cat.html (see §13 below for the architecture summary; full column list lives in cat.html §12.2 / accumulated across §9, §10, §17): cat_verdict, cat_final_theta, cat_final_se, cat_termination_reason, cat_items_administered. NULL for non-CAT attempts. final_score is NULL for CAT attempts (CAT has no raw score — verdict + theta + SE replace it).

6.1.1 Source-specific reference columns — rules

Two nullable typed FK columns rather than one polymorphic column. Sources are a closed enum of 3 (§15 of parent doc), so we get real FK constraints, clean joins, and a self-documenting schema. NULL columns in Postgres are effectively free.

Two edge cases settled:

  • Pack assigned via a programme activity. If a tutor's programme activity wraps a Readiness Pack, the attempt sets only programme_activity_id — NOT both. The activity row records which pack it wraps; the attempt knows its activity; the activity knows its content. Avoids representing the same fact twice (which would drift if the activity is later re-pointed).
  • No denormalised programme_id on the attempt. Tempting for fast "all attempts in Programme X" queries, but adds drift risk if an activity is moved between programmes. Query through the activity. Revisit only if measured perf actually hurts.

6.1.2 Intent + mode — the validated tuple

The intent and mode columns are partially independent: mode says what mechanically happens (timer present? free nav? adaptive?), intent says what frame the student is in (open-ended learning vs single-sitting exam simulation).

UX flow. Student picks intent first ("Study" vs "Exam"), then sees the modes available under that intent. Same mechanical mode (e.g. Timed Sequential) can appear under both intents with different framing — STUDY uses an engagement-clock and is resumable; EXAM uses a wall-clock and is single-sitting.

Valid (mode, intent) tuples — 8 of 10 combinations:

ModeSTUDYEXAM
Untimed Learning✅❌ — rationales after each submit defeats exam framing; would be Untimed Test instead
Untimed Test✅✅
Timed Free Navigation✅ engagement-clock✅ wall-clock
Timed Sequential✅ engagement-clock✅ wall-clock
CAT❌ — IRT model needs continuous engagement; pause/resume invalidates the estimate✅

Validation: the create-attempt RPC rejects invalid tuples ((UNTIMED_LEARNING, EXAM) and (CAT, STUDY)). The builder UI only surfaces valid combinations under each intent, so the rejection case shouldn't happen at the UI level — defence-in-depth for direct RPC calls.

Note for parent doc §15. The mode list needs intent annotations (which intents each mode supports) and the "Resume restricted to untimed modes" rule rewrites to "Resume restricted to STUDY intent." The §17 builder spec also gains an intent-picker step before the mode picker. Both flagged in §14.

6.1.3 Status enum + lifecycle

Four status values:

  • IN_PROGRESS — actively in the session, OR (for STUDY intent) paused and resumable.
  • COMPLETED — student submitted intentionally. Terminal.
  • TIMED_OUT — timer expired before submission (timed EXAM only). Terminal.
  • ABANDONED — orphan cleanup OR student-driven discard. Terminal.

TIMED_OUT is terminal, not transitional. No grace period — when the timer expires, any selected-but-unsubmitted answers auto-submit at the moment of expiry, and the row flips to TIMED_OUT immediately. Matches real NCLEX semantics (Pillar 2). Detection is lazy: the cleanup sweep or the runner-on-return notices now() > started_at + duration_seconds and flips the row, with ended_at = started_at + duration_seconds (the true expiry, not the detection moment).

Convention check. 4-state model maps closely to Moodle's quiz_attempts.state enum (inprogress / overdue / finished / abandoned) — same shape, clearer naming. Canvas merges time-out into a flag rather than a status; we follow Moodle's separation. NCLEX is pure auto-graded MCQ/SATA so we skip Canvas's pending_review split (no manual grading in v1).

EXAM re-entry — resumable mid-timer, with the wall-clock continuing during absence (revised 2026-05-09). If a student exits a timed EXAM at minute 15 of 60 and returns at minute 30, the runner resumes them at last-viewed Q with 30 minutes left on the clock — they lost the time they were away (no client/server pause logic), but they get back into the attempt. The wall-clock continues server-side throughout — elapsed time is always now() − started_at regardless of whether the student is at the screen. If the student returns after natural expiry (e.g. exits at 15, returns at 70 on a 60-min attempt), lazy detection on page mount notices now() > started_at + duration_seconds, flips status to TIMED_OUT, auto-submits any DRAFT rows as AUTO_SUBMITTED with submitted_at = ended_at = started_at + duration_seconds, and the page renders review.

Untimed EXAM (UT, EXAM) is also resumable — there's no timer to enforce single-sitting, and the orphan-cleanup TTL becomes the safety net for genuinely-abandoned attempts. Status taxonomy stays clean: TIMED_OUT specifically means "the timer ran out"; COMPLETED means deliberate Finish (or, for untimed EXAM, eventual deliberate Finish on a later return).

CAT is the only exception. Per §6.1.2, CAT cannot pause or resume — the IRT model needs continuous engagement and a 30-minute break invalidates the theta estimate. CAT exit = ABANDONED on the next detection (cleanup sweep or page mount), no review path. Detailed in bank-consumption-cat.html.

This is a revision of an earlier rule that said "exams cannot be resumed; the runner shows a read-only 'this exam ended' view." That over-applied the single-sitting principle — the wall-clock alone enforces no-time-gain (you cannot recover the minutes you were away), so the additional "no resume" rule was adding friction without adding integrity. Real NCLEX allows breaks (the timer continues during them), so the new rule matches both the actual exam mechanics and this doc's existing §11 wall-clock semantics. Detection of "did they actually leave or is this a soft page refresh?" uses a last_activity_at < now() − 60s heuristic — tunable at build.

6.2 nclex_attempt_items

One row per question delivered. Cases are expanded into 6 rows each, in case_position order.

Working column list (finalise at build time):

Identity:

  • attempt_item_id (pk)
  • attempt_id (fk to nclex_attempts)
  • position — order of this question within the attempt sequence (1, 2, 3…). Cases stay Q1→Q6 within their block per §8.

Source reference:

  • item_id — TEXT, no FK constraint. References either nclex_bank_items or nclex_tutor_questions depending on item_source. Polymorphic by design — no DB-level FK because the attempt must survive a source item being deleted (snapshot is the source of truth at runtime).
  • item_source — BANK / TUTOR. Discriminator that tells you which table item_id came from. Defaults to BANK. Required because both source tables use TEXT primary keys with no global uniqueness guarantee.
  • tutor_id — nullable FK to nclex_users. Populated only when item_source = TUTOR. Useful for tutor reporting ("how are this tutor's questions performing?") and for cascade behaviour if the tutor leaves.

Selection provenance:

  • selection_unit_type — QUESTION / CASE. Per §3, the selector picks units; this records which kind of unit produced this row.
  • selection_unit_id — the item_id (for QUESTION) or case_id (for CASE) the unit selector picked. Useful for debugging and for grouping case children to their parent unit.

Wrapper references — stable references, NOT snapshots:

These columns store the wrapper relationships at selection time. They're not "snapshot_*" columns because the values don't represent fields on the source item that could change — they're structural links the runner needs to render the case scenario or load the trend dataset.

  • parent_case_id (case children only) — joins to the matching row in nclex_attempt_case_snapshots (§6.4) to render scenario + chart tabs alongside the question.
  • case_position (case children only) — 1–6, fixes Q1→Q6 internal order.
  • cjmm_step (case children only) — Recognise cues / Analyse cues / etc. Drives the CJMM step label in the runner UI.
  • trend_id (trend questions only) — joins to nclex_attempt_trend_snapshots (§6.5) to render the dataset alongside the question.

Snapshot — granular columns (queryable / stable shape):

  • question_type — drives runner's choice of rendering component (MCQ vs SATA vs Bowtie etc.). Practically immutable per item; stored on the attempt row to avoid an item-table join at runtime.
  • stem_snapshot — the question text.
  • instruction_snapshot — "Select all that apply" / cloze instructions / etc.
  • rationale_snapshot — explanation text. Shown in Untimed Learning after each submit and in Review.
  • rationale_img_snapshot — image URL for the rationale (mirrors source rationale_img).
  • marks_snapshot — numeric. Frozen at selection so partial credit / total scoring is invariant per attempt.
  • classification_snapshot — JSONB blob containing all 9 classification axes: client_needs_category, client_needs_subcategory, nursing_subject, body_system, topic, subtopic, difficulty, bloom_level, tags. Single JSON column rather than 9 columns because the analytics queries already need to jsonb_extract_path across them, and adding a 10th axis later doesn't need a migration. Can still be indexed via expression indexes on the hot paths.

Snapshot — polymorphic blobs (shape varies by question_type):

  • content_snapshot_json — mirrors source content JSONB. Polymorphic shape: options for MCQ/SATA, blanks for Cloze, matrix-cells for Matrix, etc. Runner parses by question_type.
  • correct_answer_snapshot_json — mirrors source correct JSONB. The answer key. Drives scoring and Review's "right answer was…" rendering. Separate from content_snapshot_json because they're used at different times (rendering vs scoring).

Display state:

  • shuffle_seed — nullable. NULL means the source item had shuffle_options = false (no shuffle applied). Non-null means the seed used to produce the rendered order. The boolean shuffle_options from source is NOT stored separately — its state is encoded by the seed's nullability.
  • option_order_json — the exact rendered order of options/blanks as the student saw them. Required so Review re-renders the same arrangement and so answer indices align between submission and scoring.

Housekeeping:

  • created_at — when the row was inserted (= attempt creation moment for non-CAT; = item-administered moment for CAT).

6.3 nclex_attempt_answers

One row per question the student touched in the attempt. Created lazily — the row is inserted on first interaction (option click, blank typing, drag), not at attempt creation. Separate from attempt_items because items are immutable (the question delivered) and answers mutate as the student edits, submits, or auto-submits.

Working column list (settled — parent and child sections below cover the reasoning):

Identity:

  • answer_id — UUID, server-generated, primary key. Own ID column matches the rest of the schema (attempt_id, attempt_item_id, etc.) and gives future cross-table references a clean single-column FK target.
  • attempt_item_id — FK to nclex_attempt_items. The question this is an answer to.
  • attempt_id — FK to nclex_attempts. Denormalised for analytics rollups; derivable via attempt_item_id but most queries go directly through it.
  • student_id — FK to nclex_users. Denormalised for cross-attempt analytics (Readiness, Trend, Coverage, Per-question history all key by student).

The answer:

  • answer_json — JSONB, nullable. Polymorphic shape mirrors correct_answer_snapshot_json by question_type. Null when the row is a DRAFT before the student has selected anything, or a SKIPPED row at finalisation.
  • submission_status — DRAFT / SUBMITTED / AUTO_SUBMITTED / SKIPPED. See §6.3.1.

Scoring:

  • is_correct — BOOLEAN, nullable until graded. True iff full credit. Drives the 4-state per-question history (parent §10).
  • score_awarded — NUMERIC, nullable until graded. Output of the per-type scoring function (NCSBN-exact rules — bank.md §scoring; runner §11). The maximum possible score for the question is marks_snapshot on nclex_attempt_items, not stored on the answer row (it's a property of the question, not the answer).

Time:

  • time_spent_sec — INTEGER, runner-computed. See §6.3.2.

Answer-change tracking:

  • answer_changes_json — JSONB, default '[]'::jsonb. Append-only event log of selection changes. See §6.3.3.

Housekeeping:

  • submitted_at — TIMESTAMPTZ, nullable. Set when status crosses to SUBMITTED or AUTO_SUBMITTED.
  • created_at — TIMESTAMPTZ, default NOW(). When the row was first inserted, which by definition is the moment of first interaction with the question (no separate first_interaction_at — they would be the same value).
  • updated_at — TIMESTAMPTZ, default NOW(). Bumped on every save-progress write and on submission.

6.3.1 Lifecycle — submission_status enum

Four states. Every row is in exactly one at any time.

StatusMeaningHow it's reached
DRAFT Save-progress has written the row; student has interacted but not pressed Submit. Insertion path. STUDY intent only — EXAM modes don't draft because they have no save/resume (see §6.1.2 cleanup rules).
SUBMITTED Student pressed Submit on the question. From DRAFT (per-Q submit in Untimed Learning) or directly on insert (batched submit in Untimed Test, Timed Free Nav, Timed Sequential, CAT).
AUTO_SUBMITTED Timer expired; runner force-finalised whatever was selected. EXAM-timed only. Whatever answer_json held (including null) at expiry is locked in. Visible in honest reporting on timed mocks.
SKIPPED Student moved past the question without answering; finalised at quiz end. Free-nav modes (Untimed Test, Timed Free Nav). answer_json is null. Counts toward the "answered fraction" denominator but scores 0.

No DISCARDED state. Mid-case auto-discard from parent §10 doesn't happen anymore in the intent-split world: STUDY can be left and resumed (children persist), EXAM times out to AUTO_SUBMITTED. Explicit student-initiated discard (runner §16) hard-deletes the rows rather than soft-marking — "discard" semantically means "as if it never happened", and we have no audit / compliance reason to keep dead rows around.

Effect on parent §10: the "abandoned mid-case sessions are discarded" rule (parent bank-consumption.html §10, line 1 of "Three follow-up rules locked") is superseded by the intent split. Case-level history-state under STUDY/EXAM intent is its own design problem — flagged for a follow-up pass.

6.3.2 Time per question — the per-question time engine design settled 2026-07-12

The number is stored, not derived from submitted_at − created_at. Two reasons Postgres can't derive it:

  1. Active time excludes screen-away gaps. Wall-clock subtraction would over-count the time a student spent with the tab backgrounded, the phone locked, or otherwise away from the question.
  2. Free-nav modes (Untimed Test, Timed Free Nav) allow re-visits. "Time on Q1" is the sum of multiple visit durations — Postgres has no concept of these visits.
Status (2026-07-12): the column has existed since slice 2.1 but was never populated — the runner writes null (runner.tsx), and the obsolete p_time_spent_sec submit-RPC parameter was dropped in 20260509130000 precisely because nothing computed it. This section specifies the engine that fills it. It is a runner / attempt-level capability — bank practice, readiness sittings, and future CAT all get honest per-question time, and the readiness results report (readiness-packs.md §11.5) is merely its first reader. This is not a readiness feature.

The capture mechanic — engaged segments

The runner always has exactly one question on screen. It keeps a per-question running total of engaged seconds, added to in segments. An engaged segment is a continuous stretch where both are true: this question is the active one and the document is visible. A segment ends — banking its elapsed seconds onto the active question — on any of:

  • moving to another question (Next / Prev / jump);
  • the screen going away — the browser's Page Visibility signal fires hidden (tab switch, app switch, phone screen-lock, minimise);
  • submitting the question;
  • the page closing (a final flush via navigator.sendBeacon, so the last question isn't lost).

A new segment starts on arriving at a question, or when the document becomes visible again. The stretch between "screen went away" and "screen came back" is simply never counted — that is what makes this active (engagement) time, not wall-clock. It is a proxy for attention ("the question was on-screen and in front"), not literal attention; it catches the distortions that actually wreck the data (walked away, phone locked) and lets small on-screen zone-outs wash out.

Only whole-screen departures pause the clock — never anything inside the question. Flipping between a case study's wrapper tabs (Nurses' Notes / Vital Signs / Labs), scrolling, expanding an image, or opening the calculator all stay on the same page, so the visibility signal never fires and the timer keeps running. Reading the stimulus is working on the question. We also do not pause on stillness (no idle / mouse-movement detection): a student reading a long case stimulus for 90 seconds without touching anything is engaged, not idle, and pausing there would corrupt the number. In a case study, time is measured per child question, so stimulus reading done on child 1 lands on child 1 and children 2–6 may then read fast — expected and honest.

Two independent clocks — they do not sum, by design

This engine is independent of the attempt clock (the topbar countdown / stopwatch, runner §8) and does not touch it — not duration_seconds, the countdown, the auto-submit, or how the exam is governed. They answer different questions and obey opposite rules:

Attempt clock (exists)Per-question engine (this)
Question it answers"How much exam time is left?""Where did attention go?"
Counts screen-away time?Yes — unforgiving wall-clock (the exam rule; walking away burns real exam time, exactly like the real NCLEX; pausing it would be a cheat)No — forgiving engagement time (a diagnostic; counting a break as think-time would be a lie)
PurposeGoverns the exam / auto-submitAnalytics · pacing · the report

Consequence: the per-question active times will not add up to the wall-clock elapsed — Σ(engaged seconds) ≤ total exam time, and usually strictly less, because away-time lives in the attempt clock and nowhere in the per-question numbers. This is correct and must never be "reconciled": forcing them to total the exam time would mean stuffing away-time into some question, corrupting the diagnostic. Where the report shows both (e.g. "you used 2h50m of your 3h20m" alongside "here's where your engaged time went"), they are two distinctly-labelled readings; the per-question sum is never presented as the student's exam time.

Trust — durations, not clock readings

The runner measures each segment with the browser's monotonic timer (performance.now()), which is immune to the device clock being wrong or changed mid-sitting, and sends the server a duration delta ("+14 s"), never an absolute timestamp. So there is nothing to spoof by changing the date, and a misset clock distorts nothing. The persist RPC sanity-clamps each delta (≥ 0, and caps a single delta at the attempt's own duration_seconds as a stuck-timer guard).

Persistence — additive, and it survives a skip

Because time accumulates across revisits and across visibility gaps, the write is additive (time_spent_sec = COALESCE(time_spent_sec, 0) + delta), not an overwrite. These tables accept writes only through SECURITY DEFINER RPCs (students can't write them directly), so this is a small new RPC in the same shape as the rest of the attempt write-path — the runner calls it on each segment end, coalescing sub-second deltas to avoid chatter.

Skipped-but-read is captured (decision 2026-07-12). time_spent_sec lives on the answer row, which is otherwise created lazily on first interaction — but a student can read a question for 40 seconds and skip it without ever clicking, leaving no row to hang the time on. Time spent on a question you skipped is real pacing data (often where the clock is burned), so the persist RPC ensures the row exists (inserting a blank DRAFT row if needed) before adding the delta. One consequence: created_at on such a row is the moment time was first flushed, not a click — noted in §6.3.4.

Settled 2026-07-12 — meaning + storage (after the Slice-1 test)

The meaning is "total engaged time on the question while the attempt is live." It accrues while the question is on screen and visible, and the whole engine goes dead the instant the attempt is finished — reopening a completed attempt to review it records nothing (the runner tracks only while isLive). In Untimed Learning, going back to an already-submitted question mid-sitting (e.g. to re-read the rationale) does keep adding to that question's total. This is by design, not an anomaly: it's untimed study mode, we run no pacing on it, and "total time invested in this question during the sitting" is the honest meaning. Where decision-time would matter — Timed Sequential / readiness — the runner is forward-only with no mid-sitting rationale, so the number is already clean decision-time there. The two never overlap.

Storage is the single time_spent_sec integer (the running sum) — NOT a per-visit segment log. Considered and rejected a JSONB segment log (the answer_changes_json pattern): it would have preserved revisit counts and a decision-vs-review split, but no built consumer needs that yet, and both named consumers — the runner's review-mode time-spent + scoring-rule display, and future bank pacing — read the total. Consciously accepted trade-off: per-visit granularity is not retained and cannot be reconstructed from the sum.

Future trigger. If bank pacing is ever built and specifically wants strict decision time (time until first commit, excluding post-submit rationale study), that is a separate capture added at that point — it starts collecting from then, having not kept the earlier breakdown. For everything currently planned, the total is sufficient.

Supersedes the earlier server-derive gesture

An earlier draft of this section suggested subtracting idle gaps server-side from last_activity_at. That is superseded: last_activity_at is one coarse timestamp for the whole attempt and cannot attribute idle time to a specific question, whereas the runner knows the exact moment the screen leaves which question. The client-measured engaged-segment model above is the mechanism of record.

Mode note for analytics

Now that away-gaps are excluded, the number is cleanest in sequential modes (Timed Sequential — i.e. readiness sittings — and CAT), where one question = one continuous visit. Free-nav modes still record a real, gap-excluded number, but revisits make "time on Q1" a sum of stretches, so pacing surfacing (parent §14) leans on sequential sittings. The column is captured for all modes; the analytics layer owns any mode filter.

6.3.3 answer_changes_json — full event log, not counts

An append-only event log, not a count. Every material change to the student's selection produces an entry. Schema: 

[
  { "at": "2026-05-04T12:30:14Z", "from": null,        "to": ["A"]       },
  { "at": "2026-05-04T12:30:31Z", "from": ["A"],       "to": ["A","C"]   },
  { "at": "2026-05-04T12:30:48Z", "from": ["A","C"],   "to": ["B","C"]   }
]

One entry per material change — not every keystroke. SATA / Bow-tie / Drag-drop fire one event per option toggle; Cloze blanks fire per-blank commit; the runner debounces incremental edits.

Why log, not counts. Parent §11 surfaces R→W and W→R counts ("you changed 14 correct answers to wrong") — but counts are derivable from the log + the correct-key snapshot. The log additionally unlocks future analytics that need toggle timing (e.g. "students who flip-flop in the last 30 seconds of a timed quiz") without losing historical data. Counts can never be reconstructed back into a log.

7. Student-state tables — deferred to view-first settled

Tables like nclex_student_question_state and nclex_student_case_state would cache per-student-per-question state (last attempt, attempt count, last-correct flag, marked flag) so the builder's pool filters (Unseen / Seen / Correct / Incorrect / Marked) and live counts are fast.

Plan: start with materialised views over nclex_attempt_answers (and the marking table). Refresh on attempt completion. Promote to physical tables only if the view becomes a measurable perf bottleneck. Less to keep consistent — fewer write paths to remember to update.

Marking itself (whether a student has flagged a question or case) is a real table from day one — that's user state, not derived data.

8. Order of presentation settled

Cases as contiguous blocks. The student experiences a case as one connected chunk, then moves on.

Why blocks (not interleaved, not end-only):

  • Real NCLEX presents cases as blocks. Pillar 2 (authentic exam mechanics) makes this the default.
  • Chart tabs progressively unfold via visible_from (§10 of parent doc). A standalone wedged between Q2 and Q3 of a case would either hide the chart panel (jarring) or leave irrelevant context on screen (confusing). Blocks avoid the issue entirely.
  • Clinical reasoning is continuous — pulling the student out for an unrelated standalone breaks immersion.
  • Cleaner runner UX: clean transitions between "case mode" (chart panel + question) and "standalone mode" (just question) instead of constant context-switching.

Sub-rules locked:

8.1 Position of case blocks in the overall sequence — random

Case blocks are scattered through the quiz, mixed with standalones. Not "all cases first" and not "all cases last." Matches real NCLEX. In Timed Sequential, a wall of cases at the end would feel punishing; random distribution keeps pacing varied.

8.2 Multiple case blocks — separated where possible

When the quiz contains two or more case blocks, the selector inserts at least one standalone between them where possible. Two case blocks back-to-back means 12 questions inside scenario context with no break — too much.

If the quiz has insufficient standalones to honour the separation rule (e.g. 4 cases and 1 standalone), case blocks butt up against each other. Best effort, not strict.

8.3 Trend questions — scattered, not clustered

Per §10 of parent doc, trend questions are explicitly per-question-independent. The shared dataset is a display element, not a narrative arc. Clustering trend questions together would make them feel like a mini-case, which is the wrong category. Trend questions are placed like standalones; the dataset snapshot re-displays each time the student lands on a trend question that uses it.

8.4 Within a case, Q1 → Q6 in case_position order

Already locked by §10 of parent doc. Confirmed here for completeness.

8.5 Tutor/curator override for pack and programme sources — out of scope, flagged

A tutor configuring a programme activity may want explicit narrative ordering. Custom-built source uses the rules above; pack and programme behaviour is part of §9 when those surfaces are planned.

Runner-side implications (foreshadowing, not deciding now):

  • "You're inside a case" indicator + case summary accessible throughout the block.
  • Visual transition cue when entering and exiting a case block ("Case complete. Continuing with practice questions.").
  • Chart panel mounts at case-block start, unmounts at end.

10. When does the attempt row get created settled

The attempt row is created on the Start Quiz click in the builder. From the moment the runner mounts, attempt_id exists for everything (timer state, answer-changes tracking, save progress) to attach to.

But the runner does not jump straight to Q1. A preflight screen sits between the builder and the first question. The preflight shows:

  • Quiz title / configuration summary (e.g. "Pharm · Hard · Unseen · 25 Q")
  • Question count + duration chip (timed modes)
  • Mode-specific note ("rationales after each submit" for Untimed Learning; "75-second budget per question, no going back" for Timed Sequential; etc.)
  • A Start button (labelled "Start Exam" / "Start Quiz" depending on mode)
  • A "skip preflight next time" checkbox — pattern carried over from mynmclicensure (stored in localStorage per-mode)

10.1 Two timestamps on the attempt row

ColumnSet whenMeaning
created_at Row insert (builder Start click) When the student committed to this quiz. Never overwritten.
started_at Preflight Start click (set by RPC) When the timer / answer-tracking officially begins. NULL until the preflight is confirmed.

The "is the timer running yet?" check is started_at IS NULL. Resume detection: NULL means "not yet started — show preflight as Start"; non-null means "already started — show preflight as Resume, then re-enter the quiz."

10.2 Cleanup rules — intent-driven (build-time TTLs)

Cleanup logic keys off intent, not mode. STUDY-intent attempts with engagement (at least one answer submitted) are never auto-expired — the student paid for the bank and can return whenever. Only orphans (zero engagement) and EXAM time-outs get cleaned up automatically.

IntentConditionOutcome
Any started_at IS NULL, older than ~24h ABANDONED (orphan: clicked Start in builder, never confirmed preflight)
STUDY started, zero answers, older than ~24h ABANDONED (orphan: confirmed preflight, never answered Q1)
STUDY started, with at least one answer Stays IN_PROGRESS indefinitely. Always resumable.
EXAM (timed) started, now() > started_at + duration_seconds TIMED_OUT, with ended_at = started_at + duration_seconds
Any student manually discards from UI ABANDONED, with ended_at = now()

UI-clutter handling. A student who accumulates many unfinished STUDY attempts over months should not be expired automatically; the Practice page's "unfinished session" check (§17 of parent doc) instead surfaces only the most recent N, with a "see all unfinished" / "discard this quiz" path that lets the student manually flip rows to ABANDONED.

10.3 Reference and improvement

This mirrors the existing mynmclicensure pattern (spawnBuilderAttempt at builder Start → markTimedAttemptStarted at preflight Start). Mynmclicensure overloads a single column (ts_iso) for both creation and timer start, overwriting the creation timestamp at preflight confirmation. Mynclex uses two separate columns (created_at and started_at) so the creation moment is preserved for analytics like "how long do students typically sit on the preflight screen?"

11. Timer start settled

Timer is anchored to the preflight Start click, recorded server-side in started_at. Backend timestamp (not frontend), invariant per attempt. Clock value at any moment = now() − started_at.

This pre-decision came naturally out of §10: the preflight screen sitting between row creation and Q1 means the timer can't start at row creation (would punish the student for reading the preflight) and can't start at Q1 first render (the runner has no preflight-confirmation signal yet). Anchoring to the preflight Start RPC is the only honest answer.

For untimed modes the field is still set — useful as the "answer-tracking officially begins" mark for analytics like time-per-question (§12 of parent doc). No countdown logic uses it.

EXAM (wall-clock) vs STUDY-timed (engagement-clock). For timed EXAM, elapsed time = now() − started_at — the clock keeps running whether the student is at the screen or not. For STUDY-timed (a v2-leaning combination kept architecturally open by §6.1.2), the clock only counts active engagement; pause-on-inactive logic uses last_activity_at to subtract idle gaps from the elapsed total. v1 ships only EXAM-timed combinations, so the wall-clock formula is the only one in production.

Skip-preflight flag (carry-over from mynmclicensure): a per-mode localStorage flag lets repeat users bypass the preflight screen — Start Quiz in the builder leads straight into Q1, and the timer-start RPC fires automatically. Defaults off (preflight shown). Per-mode so a student can dismiss the routine untimed prompt while still seeing the timed-mode warning every time.

Hybrid escalation if we ever care about the network-lag (~1–3s) on the timer-start RPC: the runner could send a preflight_confirmed_at timestamp in the request, and the backend uses the lesser of client-time and server-receive-time. Not for v1 — surface only so we know the door is open.

12. Re-roll behaviour settled

Same builder configuration tomorrow → fresh random selection. No question caching tied to filter sets.

Implication for Recent Quizzes (§17 of parent doc): restoring a prior config restores the filters / mode / count, NOT the same questions. The label "Pharm · Hard · Unseen · 50 Q" promises a quiz with that shape, not a re-run of that exact quiz.

13. CAT — separate flow, noted only backreference

CAT does not use the create-attempt path designed here. Two RPCs instead, both atomic:

  • create_cat_attempt — opens an attempt row with mode = CAT, picks and snapshots the first question only.
  • cat_next_item(attempt_id, last_answer_payload) — called repeatedly: scores the last answer, updates theta/SE, checks termination, picks and snapshots the next item (or terminates and writes verdict).

Shared with this plan: the nclex_attempts row, nclex_attempt_answers, and the snapshot tables (nclex_attempt_items, plus trend/case snapshot tables when applicable). Items are added one at a time as the IRT engine picks them.

Full CAT design lives in bank-consumption-cat.html — RPC contracts in §10.2, runner-server transition pattern (pessimistic UI with graceful degradation) in §10.1, error handling in §10.3, snapshot rules in §11. This section is now a backreference; all CAT-specific decisions are settled there.
