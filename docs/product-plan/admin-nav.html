MyNclex — Admin & Super_admin Navigation

Living document. Locked in session 2026-04-24 (Claude Web). Part of mynclex/docs/product-plan/ set — sibling to main.md, bank.md, student-nav.md, tutor-nav.html.

What this covers

The navigation shape for ADMIN and SUPER_ADMIN role users on MyNclex. Covers the shared sidebar, permission-driven visibility, the one super-only item, and the Bank sub-navigation pattern inherited from the tutor spec.

This does NOT cover student or tutor navigation — those are separate specs in the same series.

Core model

Admin and super_admin use the same sidebar. What differs is which items each person sees, driven by the permissions granted to them.

  • SUPER_ADMIN — Sam and any future platform owners. Implicitly holds every permission. Sees every sidebar item including the super-only Admin Permissions page.
  • ADMIN — trusted helpers. No default powers. A super_admin grants specific permission buckets per admin, so two admins can have non-overlapping responsibilities (e.g. one handles payments, another manages the bank).
Design principle: an admin sees only the items they can actually use. No greyed-out links. This makes the nav scannable for each admin's actual job, and avoids tempting anyone to click something they'll just bounce off.

Why flat (for now)

The sidebar has 15 items. Borderline long, but flat is easier to scan than grouped until we know which items a typical admin uses together. If it ever grows beyond ~18 we group by function (Content / People / Business / System).

Permission model (light touch)

Permissions are data, not code. The nav renders off the database — the UI itself holds no rules about who sees what, only how to render based on a given permission set.

  • Admin permissions live in a database table (schema deferred to the auth / admin sprint — out of scope here).
  • Super_admin status comes from nclex_user_roles; the permission check treats it as an implicit wildcard.
  • The sidebar component takes the current user's permission set and filters items. Adding a new permission bucket to the database makes it available in the Admin Permissions UI for super_admin to grant.
  • Each page also checks permission on load. Sidebar filtering prevents showing the link; page-level check prevents access via pasted URL.
  • Automation (rule 4): adding a new admin area = add its page, add its sidebar entry tagged with a permission key, and (if new) add the permission bucket as a row. No hardcoded lists to keep in sync.
Full schema — table shape, RLS policies, permission-check helpers — is out of scope for this nav spec. It lands in the admin / auth sprint documentation at build time.

Topbar

Left side

  • QAcademy logo + wordmark — clicking returns the admin to their Dashboard. Works from any admin page.
  • Product label: · Admin.

Right side

  • Role pill — shows Super_admin (warning-tone) or Admin (info-tone). If the user has other roles too (e.g. Sam is Super_admin + Tutor), the pill becomes a dropdown for role switching.
  • User menu avatar: click opens dropdown → name, email, Sign out.

Build order

  1. Admin global layout + sidebar + Dashboard page (with permission filtering).
  2. Admin Permissions page (super_admin only) — must come early, it's what grants every other bucket.
  3. Bank sub-nav wiring. Point Case Studies / Trends at existing admin list components directly (no surface parameter needed — this is the admin surface).
  4. Remaining pages in whatever order matches build priority. Nav slots exist; each page arrives when ready.

Out of scope for this spec

  • Permission table schema, RLS, RPCs — defer to admin / auth sprint.
  • The exact permission bucket list at launch — this doc shows an initial set; real buckets surface during build.
  • Cross-role UI for users holding multiple roles (e.g. Sam as Super_admin + Tutor) — role switching handled by the shared topbar pattern from Slice 2.5.
  • Mobile drawer behaviour — companion spec after desktop lands.
