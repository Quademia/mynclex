1. Why we're rebuilding

The current authoring system works. It ships nine question types and two wrappers (case study and trend), with atomic transactional saves and full RLS coverage. It's a successful build — but it has architectural limits that get in the way of what we want to do next.

The editors today are partially component-shaped. They render inputs with name= attributes and rely on an outer <form> to collect their values via FormData on submit. Three of them reach into the DOM directly (document.getElementById('bank-stem')) to read the stem. The wrappers had to bolt on a snapshot-and-remount dance to bridge between FormData-uncontrolled editors and atomic saves. None of this is broken, but all of it makes the editors hard to mount anywhere except the contexts they were designed for.

This rebuild is scoped to authoring only. The student runner — the component tree that students use to actually answer questions in a session — is a separate concern with its own state model, persistence flow, and interaction logic. It will be built independently. Authoring and answering share the visual shape of a question (an MCQ has options, a Matrix has rows × columns, etc.) but they are different jobs and will be different code. Any sharing between them happens at a much lower level than the editor — small visual primitives at most.

This rebuild also gives us freedom to redesign UX choices that were locked in by the original build's constraints — like vertical accordions in narrow editor columns, like wrapper-level fields that mirror question-level fields without justification, like wrappers that own their own URLs and pages instead of being mountable anywhere.

The goal: a foundation where the question editor and the wrapper editors are genuine, independently mountable React components for authoring. The bank pages become navigators. Modals become thin hosts. The student runner is a separate concern, built separately.

Scope: authoring only

This rebuild covers authoring: the components and modals curators use to create, edit, save, and publish questions and wrappers. It does not cover the student runner — the component tree students will use to answer questions in a quiz or attempt session.

Authoring and answering look visually similar (both render an MCQ as a question with four options, both render a Matrix as a grid, etc.) but they are fundamentally different code:

  • Authoring manages curator state — stem text being typed, correct answers being marked, classification dropdowns, dirty tracking, save flows to the bank tables.
  • Answering manages student state — the question is frozen at session start, the student picks answers, those answers are persisted to attempt tables, scoring runs, rationale reveals at the right moment, attempt history accumulates.

The "preview pane" inside each authoring component is a curator-facing tool — a rough rendering of how the question will look so the curator can see what they're building. It is not the runner. It runs no scoring, has no session, has no answer persistence. Its job is to help the curator see the shape of their work.

If, when the runner is eventually built, certain visual primitives (e.g. the layout of an MCQ option list, the structure of a Bow-tie's three wings) turn out to be worth sharing between authoring preview and runner display, those primitives can be extracted at that time. They are not designed for in advance. The QuestionEditor / CaseStudyEditor / TrendEditor components themselves stay scoped to authoring.

2. Architectural principles

Components own their shape

Each editor renders its own two-view layout (editor + preview). Containers control sizing, never internal structure.

Containers control space

Modals decide how much room a component gets. The component renders into whatever space it's given, gracefully.

State lives in JavaScript

No DOM scraping, no FormData submission for state collection, no getElementById. Every component takes value + onChange.

One save per thing

Questions save independently. Wrappers save independently. Publishing is a separate action with its own check.

Integrity at the session layer

Student session snapshots questions on start. Curators edit freely; students answer from frozen copies.

Build new beside old

Don't migrate the existing system in place. Build the new components from scratch, swap when complete, delete the old.

3. The three components

The new system is built around three independent React components, each one a controlled component (takes a value, reports changes via onChange):

ComponentWhat it editsWhere it's used
QuestionEditor One question of any of the 9 types Standalone modal, inside CaseStudyEditor, inside TrendEditor
CaseStudyEditor One case study (header + chart tabs + question list) Case study modal; potentially future programme tools
TrendEditor One trend (header + dataset + question list) Trend modal; potentially future programme tools

Each component follows the same internal pattern: a two-view layout, with editor controls on the left and a live student-perspective preview on the right. The two views update together as the curator types.

The QuestionEditor inside a wrapper is the same component as the QuestionEditor in the standalone modal. Same code, same props, same behaviour. The only thing that differs is how much space the host gives it.

4. Layout: standalone vs wrapper

The same QuestionEditor renders differently depending on the space it's given. The standalone modal gives it the full modal body. The wrapper modal gives it only the bottom half — the wrapper component takes the top half.

Standalone modal

QuestionEditor takes the entire modal. Editor view on the left, preview on the right, both with comfortable padding. The component breathes. This is the normal authoring experience for individual questions.

Wrapper modal — case study and trend

Two components stacked: the wrapper component takes the top half, the QuestionEditor takes the bottom half. Each component is independently a two-view block. The modal itself is just topbar + pill-strip + two stacked components.

Top row is the wrapper (case-study or trend) — its own editor on the left, its own preview on the right. Bottom row is the active question — same paired layout. A curator scans horizontally to compare authoring with student view, vertically to move between case-level and question-level concerns.

The trend modal follows the exact same pattern — TrendEditor on top with its dataset and timepoints, QuestionEditor on the bottom for the active attached question.

Behaviour notes

  • Wrapper preview position. The case-study preview can auto-follow the active question pill (click Q3 → preview shows the case at position 3), with a manual override so the curator can preview any position independently of authoring.
  • Trend preview is simpler. Trends don't unfold per position — students see the whole chart. So the trend preview just shows the dataset as a student would see it (no flags, no ref-range column).
  • Modal sizing. Wrapper modals are near-fullscreen (~1100px wide × ~85vh tall) so each component has comfortable space.

5. Inside the question editor: top tabs

Today the question editor stacks Content, Classification, and Housekeeping as vertical accordions. Curators expand one, edit, collapse, expand the next. In a narrow editor column (especially in the wrapper context), this becomes a long scroll.

The new design replaces the vertical accordions with top tabs. The active tab fills the editor body. Most authoring happens in Content; Classification and Housekeeping are infrequent. Tabs eliminate scroll for the common case.

The preview pane never moves. It's about "what does this question look like to a student" and that's independent of which authoring tab the curator is on. The type selector (MCQ ▾) sits at the right end of the tab bar — it's question-level metadata, not Content-section metadata.

Per-type body adapts within Content

The Content tab's body changes shape based on the question type:

  • Option-list types (MCQ, TF, SATA, SELECT_N): stem, options list, rationale
  • MATRIX: stem, rows × columns grid, rationale
  • HIGHLIGHT: instruction, passage with marked chunks (correct vs distractor)
  • CLOZE: stem with inline numbered blanks, per-blank option lists
  • DRAG_DROP: subtype picker (Ordered / Sentence), stem, ordered tokens, distractors
  • BOWTIE: stem, three-wing token panel (Actions / Condition / Monitor) with 2/1/2 correctness

Classification and Housekeeping have the same shape regardless of type — six classification axes in a 2-column grid; ID, status, marks, batch, author, last-edited, internal notes in Housekeeping.

The option-list family (MCQ, TF, SATA, SELECT_N) is omitted because they all follow the same structure as MCQ shown above — the bespoke types are where the design has to flex.

Honest observations under stress

  • Matrix and Bow-tie hold up well in both contexts. The grid shape and three-wing shape compress cleanly without losing structure.
  • Highlight gets visibly cramped in the wrapper. Long passages with marked chunks need vertical room. The Content tab will need internal scroll in the wrapper case.
  • Cloze with ≤3 blanks works in both; 5+ blanks would need scroll in wrapper.
  • Drag-drop is naturally compact — list-shaped tokens fit in either context.

7. Saving, publishing, and integrity

The new system separates three concepts that the current build conflates: saving (persisting to DB), publishing (making visible to students), and session integrity (protecting in-flight student attempts).

Saving — per-thing, independent

  • Each QuestionEditor has its own Save button. A question saves alone, regardless of whether it's standalone or inside a wrapper. Saving requires only minimum-shape validity (e.g. a stem).
  • Each wrapper editor has its own Save button on the topbar. A wrapper saves its own header fields independently of its child questions.
  • The atomic save-everything RPC may still exist as a convenience, but it's no longer the only path.

Publishing — separate action with check

  • Wrappers have a separate Publish action (alongside Save) on their topbar.
  • Publishing a wrapper checks that all linked questions are saved and individually valid. If any are missing or invalid, the system tells the curator what's blocking and refuses to publish.
  • Publishing a wrapper publishes its child questions as part of the action — questions inside a published wrapper become published.
  • Standalone questions have their own is_published flag and can be published individually.

Editing published things — always allowed

Once published, questions and wrappers remain freely editable. There's no unpublish-edit-republish ceremony. The curator can fix a typo on a published case study without taking it offline.

Session integrity — snapshot at start

Student session stability is solved at the session layer, not the editor layer. When a student starts a quiz, the system copies each question's full content (stem, options, correct, rationale, etc.) into a session-scoped row. The student answers from those copies. Any subsequent curator edit affects future sessions only — in-flight sessions are unaffected.

This means: editors edit, saving persists, publishing makes visible, session snapshots protect students. Four jobs, four layers, no conflation. A typo fix on a published question doesn't disrupt the student answering it right now; their session has its own copy.

Unsaved changes warning

Universal pattern: any unsaved edit triggers a confirm-on-close, confirm-on-navigate dialog. The dirty-tracking is local to each editor — the wrapper modal aggregates dirty flags from itself and its open child editor to decide whether to warn.

8. Schema posture

The existing database schema is good and stays untouched during the rebuild.

What stays exactly as it is

  • All nine question types' JSONB shapes on disk
  • nclex_bank_items, nclex_case_studies, nclex_trends, all their columns, all their RLS
  • The seven RPCs — nclex_save_case_with_children, nclex_save_trend_with_children, etc. (the new system may use them less, but they don't break)
  • The classification axes, difficulty enums, CJMM steps
  • The ID prefixes (NCLEX_MCQ_, NCLEX_CS_, NCLEX_TRD_)

What may be added

The new wrapper editors will likely have different section structures than the current Content / Classification / Housekeeping at the wrapper level. Section names and their contents are not predetermined — they'll be designed around what case-study and trend authoring genuinely need.

If new wrapper-level fields emerge during the build that don't have a column yet, we'll add nullable columns alongside the existing schema. The old wrapper code is untouched and continues using its old columns. The new wrapper code reads its mix of relevant existing columns plus any new ones it needs. The two systems share tables without conflict because they touch different columns.

Principle: the new wrapper editors include only the sections their content actually needs. Don't carry forward Classification or Housekeeping at the wrapper level by default — add wrapper-level metadata only if it genuinely benefits both case-study and trend.

The question editor keeps its three sections

The QuestionEditor's three tabs (Content / Classification / Housekeeping) are locked. They map to existing columns and existing JSONB shapes that the new editor will read and write directly — same data, different UI shell.

9. Build approach

Parallel build, no in-place migration

The current authoring system stays in place and keeps shipping. The new components are built from scratch in a separate folder. Once the new system is feature-complete and verified, the routes flip to point at the new code, then the old code is deleted.

Use the current build as a reference, not a template

The current build is a teacher — its parsers, its JSONB shapes, its validation rules, its tab editors (narrative-tab, structured-tab, vf-segmented), its RPCs. All of these are good and worth copying when needed. But the new build is not obligated to mirror the current UI structure. Where the current design was constrained by FormData-driven editors or page-level routing, the new design is free to redesign.

What stays untouched in the current build

  • Database schema, RLS, RPCs (we may add columns; we don't change existing ones)
  • The current lib/bank/ code remains in place until the swap
  • The current routes (/admin/bank, /admin/bank/cases/[id], /admin/trends/[id]) keep working

What's new

  • A new folder for the new components (folder name to be decided when build starts)
  • Fresh QuestionEditor, CaseStudyEditor, TrendEditor as controlled components
  • New modal hosts (StandaloneQuestionModal, CaseStudyModal, TrendModal)
  • New per-thing save server actions; existing RPCs reused where appropriate
  • New routes, or modified existing routes that launch modals instead of navigating to editor pages

Cutover and cleanup

Once the new system is verified end-to-end, the routes get pointed at the new code. The old lib/bank/ folder stays in place briefly as insurance. After a short grace period, it's deleted in a cleanup slice.

The slice plan itself isn't part of this document — it'll be drafted separately when we're ready to start building.
