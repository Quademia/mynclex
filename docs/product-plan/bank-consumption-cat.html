Why this doc exists

Sub-plan for the CAT (Computer Adaptive Testing) mode — the adaptive, IRT-driven runner that simulates the real NCLEX exam. CAT is in scope for v1 per parent doc bank-consumption.html §16.

Splits off because CAT is structurally different from every other mode in MyNclex: it has no upfront question list, items arrive one at a time from an ability estimator, the test terminates on confidence rather than count, the result is a verdict (not a score), and the runner UX has to handle "we don't know how many questions you'll answer." None of those shapes fit cleanly inside the fixed-length attempt-creation and runner sub-plans.

This doc is mostly a skeleton at creation time. Each section below has a placeholder describing what it covers; content fills in as planning conversations land. Status pills: settled = decision locked, open = decision identified, not yet made, skeleton = section defined, content not yet started, deferred = own planning topic later.

2.10 Settled in this doc's seed conversation (2026-05-04)

  • Snapshots are non-negotiable for CAT. Per-question snapshot at administration time, identical to the fixed-length snapshot strategy. Skipping snapshots — whether by reading from live tables, or by snapshotting retroactively at end-of-session — was rejected on integrity grounds: a curator editing a question mid-attempt would change the rules under the student's feet, and post-hoc snapshots capture state at end-of-session, not state at administration. See §11 for the full reasoning.
  • One set of attempt tables for all modes. CAT uses the existing nclex_attempts, nclex_attempt_items, nclex_attempt_answers. CAT-specific columns are nullable additions, NULL for non-CAT attempts. Splitting CAT into separate tables would force every History page query, every analytics rollup, every Review render to UNION across two sets of tables for zero gain. NULL columns in Postgres are effectively free.
  • Review IS available for CAT. Industry-standard (UWorld, Archer both offer review-after-CAT) and consistent with parent §15 ("Review is a session state available for every finished session regardless of source/mode"). Review surfaces the rationales for the questions the student saw — the educational value is the rationales, not a per-question benchmark against peers (since two CAT-takers see different questions). See §14 for what review looks like specifically.

3. v1 honesty constraints settled

Three constraints commit us to honesty about what we can and can't deliver. Settled 2026-05-04.

3.1 Calibration approximation — disclosed via help page, not per-attempt

Day-one difficulty values are curator labels mapped to numbers. Until empirical recalibration kicks in (§5.3), our "Hard" item is a reasoned guess, not a measurement. We're honest about that — but we tell the student once, in a help page, not on every CAT result.

Three options were considered:

  • Don't expose it — UWorld and Archer don't tell students about their calibration internals. Black box. Rejected: dishonest by omission for a product whose Promise is "practise on the real thing" with Pillar 4 being honest feedback.

3.5 Two different "probabilities" — one we give now, one we defer revised 2026-07-15

Revised 2026-07-15 (Sam). The earlier stance ("no probability talk of any kind until v3+") conflated two different quantities. We now separate them:

  • Probability of being above OUR standard — GIVEN from day one. The Rasch model produces this natively: from the final ability estimate and its uncertainty (SE), we compute the probability that the student's true ability is above the 0.0 line (the normal-curve area above 0). It is a real, honest statistic, computable on launch day. Example: estimate 0.5, SE 0.40 → ~89% likely above standard; estimate 0.1, SE 0.40 → ~60%; estimate −0.3, SE 0.40 → ~23%. This is readiness confidence against our own bar — see §9.5 / §13.1. Setting 0.0 as our standard is our prerogative; measuring against it and stating the confidence is not dishonest.
  • Probability of passing the REAL NCLEX — still deferred (v3+). A number like "78% chance of passing the actual NCLEX-RN" requires real outcome data we don't have: students who took our CAT and then the real NCLEX, with pass/fail outcomes, in volume. Without that link we literally cannot compute it, and printing an invented one risks the product's credibility (Archer can claim "99% pass" only because they validated it against thousands of real outcomes). So we hold the phrase "chance of passing the NCLEX" until we have outcome data — at which point the same machinery gets re-labelled, no rebuild.

The guardrail, restated: we show a confident readiness probability, always framed as "confidence you're above our standard," never as a real-NCLEX pass prediction. Vetting our content raises its quality (and trust) but is a separate thing from difficulty calibration (§5) and outcome validation — it does not by itself license a real-NCLEX probability.

4. IRT model choice settled

Rasch (1PL) for v1. Implemented in TypeScript inside the existing stack (Cloudflare Workers / Supabase edge). Settled 2026-05-04.

4.1 Why Rasch and not 2PL

Rasch uses one parameter per item: difficulty. 2PL adds a second parameter, discrimination — "how well does this question separate strong students from weak students." Discrimination can only be calculated from real student response patterns. Day one, all we have is the curator's Easy / Medium / Hard label, which gives us a difficulty proxy but says nothing about discrimination. Picking 2PL on day one would force us to assign a fake discrimination value (probably 1.0 = "average") to every question — which is mathematically equivalent to just using Rasch.

Rasch is also the simplest, most studied, most stable IRT model. Easier to implement, easier to debug, easier to explain to ourselves and others.

4.2 Live engine implementation

TypeScript implementation in our existing stack. Our backend is Supabase Edge Functions and Cloudflare Workers — neither runs Python natively. Two paths were considered:

  • Path A — Python service. Spin up a small Python service running a library like catsim or pyirt. CAT RPCs call it for ability estimation and item selection. Adds one moving piece to the stack (deployment, monitoring, latency).
  • Path B — TypeScript Rasch directly. Re-implement the core Rasch math in TypeScript. The math is small (~30 lines for ability estimation, less for selection). No new infrastructure.

Path B chosen. Rasch math is well-documented and one-time work. Adding a Python service for what is fundamentally a small calculation introduces deployment complexity, latency, and error surfaces for little benefit.

4.3 Empirical recalibration uses heavier tooling — separate concern

The live CAT engine is the small Rasch implementation in TypeScript. Empirical recalibration (§5.2) is a different beast — fitting Rasch parameters to a corpus of student responses is a heavier statistical job, and that's the place where Python tooling (pyirt or similar) makes sense. The recalibration job is offline, periodic, batch — not in the live CAT path. See §17 for the audit pipeline.

4.4 2PL upgrade — when

Once empirical recalibration has been running for some time and we have substantial response data per item, we can revisit fitting 2PL parameters. v2 decision, driven by data — not a v1 commitment.

4.5 Partial-credit items — how they feed the ability estimate settled 2026-07-16

The gap this closes. Rasch (1PL) is a right/wrong model — it expects each administered item to come back as a clean 1 (right) or 0 (wrong) to update the ability estimate. But most NGN types (SATA, SELECT_N, MATRIX, MATRIX_MR, CLOZE, HIGHLIGHT, BOWTIE, DRAG_*) produce a partial result — e.g. a SATA scored 3 out of 5. Until now the plan said "update theta with Rasch" (§10.2) without specifying what a partial answer feeds in. This section settles that.

Three approaches (the staircase framing): picture a partial-credit item as a staircase from 0 correct (bottom) to all-correct (top).

  • Option 1 — all-or-nothing. Only a 100%-correct answer counts as "right"; 4-of-5 is treated identically to 0-of-5. Simplest and keeps pure 1PL, but rejected: NGN items are hard to ace, so most partial answers would score 0, systematically biasing every student's estimate downward and making the exam feel brutally unfair. It is also not what the real NCLEX does.
  • Option 2 — partial credit as a fraction (CHOSEN for v1). Feed the proportion correct into the update instead of a hard 0/1: 4-of-5 → 0.8. Every step of the staircase is treated as equal height. Uses all the information, avoids the downward bias, needs no extra per-item data (works from launch day), and is a modest extension of the 1PL update rather than a new model. The proportion is already computed by the scoring engine (score_awarded / marks).
  • Option 3 — full partial-credit model (deferred to v2). Measures the real height of each staircase step from response data — i.e. it learns which parts of a question actually separate strong students from weak ones (the "tricky" checkbox vs the "obvious" one) and weights them accordingly. This is what the real NCLEX uses. Deferred because it needs substantial per-item response data we don't have on day one — the same data-dependency reason 2PL is deferred (§4.4).

What the real NCLEX does: it gives partial credit (its test plan names three methods — plus/minus, zero/one, and rationale scoring) and feeds those partial scores into a polytomous (partial-credit) IRT model — i.e. Option 3. It does not use all-or-nothing. Our own scoring engine already computes SATA partial credit the NCLEX "plus/minus" way (+1 per correct pick, −1 per wrong pick, floored at 0).

Decision (2026-07-16, Sam): Option 2 for v1, growing into Option 3 as data accumulates. Option 2 and Option 3 are the same idea (partial credit counts) at two levels of sophistication; Option 2 is the launch-day version and upgrades into Option 3 through the same recalibration pipeline (§5) — nothing is thrown away. Only Option 1 is a different philosophy, and we reject it.

Two consistency requirements this creates:

  • Recalibration (§5) must define a "response" the same way. If the live estimate consumes a fraction (0.8), the weekly empirical recalibration must use the same fractional response, not a dichotomised one — otherwise the difficulty values drift against a different definition than the engine scores against.
  • Display vs. estimate mismatch (§13.2). The summary page reports per-category "correct" as full-credit-only (the is_correct flag). That is a legitimate study stat, but it differs from how the engine credited the student (fractional). A one-line footnote on the summary page should acknowledge this so a student who sees "3/5 SATAs fully correct" doesn't think the engine ignored their partials.

Build note: the cat_next_item RPC (§10.2) uses score_awarded / marks as the item outcome in the Rasch update (MCQ/TF are simply 1 or 0, the degenerate case). For a fully-correct answer this is 1.0 and for a fully-wrong answer 0.0, so dichotomous items are unaffected.

5. Difficulty calibration plan settled

How we get from curator-assigned Easy / Medium / Hard labels to numeric IRT difficulty values, and how we improve those values over time as student response data accumulates. Settled 2026-05-04.

5.1 Day-one mapping — curator label → numeric proxy

Three numeric values on the IRT logit scale, where 0 = average ability:

Curator labelRasch difficultyPlain-English meaning
Easy−1.0A 50/50 student gets this right ~73% of the time.
Medium0.0A 50/50 student gets this right ~50% of the time.
Hard+1.0A 50/50 student gets this right ~27% of the time.

The middle three values on the standard IRT logit scale. Wide enough that the three labels are meaningfully different (the engine picks differently for a Medium-leaning student vs a Hard-leaning student); tight enough that no question is treated as extreme.

5.2 Where the numeric value lives — schema decision

The existing nclex_bank_items.difficulty column is a TEXT column with a CHECK constraint that restricts values to 'Easy' / 'Medium' / 'Hard'. It cannot hold a number like 0.34 — that would violate the constraint. So the numeric value the CAT engine reads must live in a separate column.

Add a new column: difficulty_irt (NUMERIC). The text column stays exactly as it is; the numeric column lives in parallel.

Column on nclex_bank_itemsTypePurposeSource
difficulty (existing, unchanged) TEXT Curator's label — displayed in admin UI, edited by curator Curator selects on save
difficulty_irt (new) NUMERIC The number the CAT engine reads for selection Initialised from difficulty via the §5.1 mapping; updated by the recalibration job
difficulty_source (new) TEXT Provenance flag for difficulty_irt 'CURATOR_LABEL' on insert; flipped to 'EMPIRICAL' by the recalibration job once the threshold is crossed

Rules of access:

  • Curator UI never touches difficulty_irt. The curator picks Easy / Medium / Hard; the system writes the corresponding number to difficulty_irt automatically on save.
  • CAT engine never touches difficulty. It reads difficulty_irt only.
  • Recalibration job writes only to difficulty_irt and difficulty_source. Never touches the curator's label.
  • This preserves the curator's original judgement as a stable field. Once recalibration runs, we can still see "this question was originally labelled Hard, but the data shows it's actually Medium-difficulty" by comparing the two columns.

5.3 Empirical recalibration trigger

When does an item's difficulty_irt get recomputed from response data instead of staying at its curator-derived starting value?

5.3.1 Threshold — 30 responses per item

An item must have accumulated at least 30 student responses before its difficulty_irt can be recalibrated empirically. Below that, the empirical estimate is too noisy — one strong student getting an item wrong (or one weak student guessing right) can swing the difficulty value too far. 30 is the standard industry rule-of-thumb floor; above it, the estimate stabilises meaningfully.

5.3.2 Cadence — weekly batch (v1)

Recalibration runs once a week — Sundays at 02:00 UTC (low-traffic window). Plus a manual trigger button in the curator dashboard for testing and edge cases.

Why weekly, not nightly:

  • Early on, response volume per item is low. A given item might get 3–5 responses per day. Nightly mostly produces no-op recalculations.
  • Empirical estimates are more stable when computed on a larger window of responses.
  • Weekly is operationally simpler — one scheduled run, easier to monitor.
  • Matches the reality that early-stage recalibration is provisional anyway.

Revisit cadence when the platform has enough volume that items routinely accumulate 20+ new responses between weekly runs. At that point, switch to nightly. v2 decision, data-driven.

5.3.3 Transition smoothing — 70/30 dampened blend

When the recalibration job produces a new value for an item, the new difficulty_irt is a weighted blend of the previous value and the freshly computed one — 70% new, 30% previous. So if an item was at difficulty 0.0 last week and the new empirical estimate is 0.7, the stored value becomes 0.49 (≈ 0.7 × 0.7 + 0.0 × 0.3).

Why dampen. Without smoothing, an item's difficulty can lurch between weekly runs in ways that make consecutive CATs feel arbitrary. A student who took CAT #1 with this item at difficulty 0.0 and CAT #2 with the same item suddenly at 0.7 is exposed to large psychometric shifts mid-prep that have nothing to do with their own ability. Dampening keeps the trajectory smooth across recalibration cycles.

The blend converges to the empirical value over multiple weekly runs — fast enough that calibration moves the needle within a month or two of accumulating data, slow enough that no single week's noise dominates.

5.3.4 First crossover — special case

When an item crosses the 30-response threshold for the first time, difficulty_source flips from 'CURATOR_LABEL' to 'EMPIRICAL'. The 70/30 blend still applies — the previous value is the curator-derived starting number, the new value is the first empirical estimate.

5.4 Confidence display

Each item's difficulty_source column tells the curator dashboard whether the value is curator- derived or empirically calibrated. The dashboard can show: "X% of bank items are now empirically calibrated" and per-item flags. Admin/curator-side only for v1; not surfaced student-facing.

6. Starting-difficulty rule settled

Every CAT starts at theta = 0.0 (Medium), with high SE, for every student, every time. First question served = Medium. Settled 2026-05-04.

Why fixed, not personalised: a returning student who's done 3 prior CATs has a known prior theta — but starting CAT #4 at that prior estimate would bias the test toward confirming the prior result. The engine would spend fewer questions exploring whether the student has actually changed since CAT #3, and more questions confirming what it already thought. That's bad measurement. Real NCLEX doesn't do this; every candidate starts at medium every time. We mirror that.

What we DO use prior CAT data for: History / Analytics. The student sees their CAT trajectory across attempts ("you went from theta 0.5 → 0.7 → 0.65"). That's useful information. It just doesn't seed the next CAT's starting position.

7. Item selection strategy settled

Given the current ability estimate, the eligibility filters, and the bank pool — how does the engine pick the next item? Settled 2026-05-04.

7.1 The selection rule

Pick the unseen question whose difficulty is closest to the student's current ability, with category as a tiebreaker among equally-good difficulty matches.

The engine, on each pick:

  1. Calculates the student's current ability estimate (theta).
  2. Finds the set of unseen, eligible questions closest to theta — nearest-neighbour, not a fixed window (revised 2026-07-19; see below).
  3. Within that set, checks if any are in an under-represented Client Needs Category (running count of categories so far in this attempt).
  4. If yes → picks one at random from the under-represented-category subset.
  5. If no under-represented matches → picks any from the closest-difficulty set at random.

The engine never widens the difficulty match to find an under-represented question. Difficulty match is sacred. Category is a thoughtful tiebreaker only.

Nearest-neighbour, not ±0.1 — revised 2026-07-19 (Sam), before Slice 4. This step previously read "within a small difficulty tolerance (provisional: ±0.1) of theta." That assumes difficulty is a smooth continuum. It is not, and will not be until Slice 10 runs. Every difficulty_irt is seeded from the curator's Easy/Medium/Hard label (§12.7.1), so the entire eligible pool sits on exactly three values: −1.0, 0.0, +1.0.

A ±0.1 window would therefore find nothing for any theta that is not almost exactly on a rung — a student at theta 0.35 has its nearest questions at 0.0 and 1.0, both far outside the window. Implemented literally, the engine would hit the §7.5 fallback on nearly every pick and the "exposure relaxed" signal built to detect a thin pool (§15.3) would fire constantly and meaninglessly.

The rule is therefore: rank by distance from theta and take the closest available rung, then apply the category tiebreaker among everything tied at that distance. This is identical in behaviour to a tolerance window once empirical recalibration spreads difficulties into real numbers, and it degrades gracefully on today's three-rung ladder instead of failing. No tolerance constant is needed, so there is no provisional number left to be implemented literally.

7.2 Why this rule (and why not stronger category enforcement)

Three options were considered: (A) pure difficulty match (soft category), (B) hard category enforcement that overrides difficulty when needed, (D) a per-category floor with late-test override. All three were rejected in favour of the locked rule (option E in the planning conversation):

  • A (pure difficulty) — sound on measurement but no protection against severely lopsided category mixes when the bank itself is unbalanced.
  • B (hard enforcement) — overriding difficulty for category degrades the engine's measurement accuracy, can break entirely on a small bank when no question exists at the right difficulty in the under-represented category, and hides bank-balance signals that should be addressed by curation, not engine compensation.
  • D (floor with override) — better than B but still pays measurement cost when the floor activates late in the test, and adds engine complexity (running floor checks, fallback logic).
  • E (tiebreaker) — costs nothing in measurement quality (engine never picks a wrong-difficulty question), gives the engine a small natural lean toward balance when free choices exist, doesn't pretend to enforce what the bank can't deliver.

7.3 Eligibility filters

The next item must be:

  • Not already administered in this attempt (no within-attempt repeats).
  • Not seen in the student's last 3 CAT attempts (cross-CAT exposure window — settled in §15.2).
  • is_published = TRUE.
  • is_builder_visible = TRUE (keeps readiness-pack reserved questions out of CAT, same rule as everywhere else).
  • Standalone questions AND wrappers (case studies, trend-linked) are both eligible — direction reversed 2026-07-14; wrapper administration mechanics are open build decisions (see §7.4).

7.4 Cases and trends in CAT — INCLUDED in v1 mechanics settled 2026-07-16

Direction reversed 2026-07-14 (Sam). Wrappers — case studies and trend-linked questions — are IN scope for v1 CAT. Real NCLEX includes case studies in its adaptive exam, and MyNclex's promise is "practise on the real thing"; a CAT that never serves a wrapper is not the real thing. The original standalone-only default (settled 2026-05-04) is superseded.

The original deferral reasons stand as costs we're accepting, not as reasons to wait — recorded here so the build slice designs around them deliberately:

  • Case-study children aren't psychometrically independent — the 6 questions correlate heavily because they're built on the same scenario, which strains IRT's local-independence assumption. (UWorld/Archer-class products accept the same compromise.)
  • A case study delivers as an atomic ~6-question block, which locks the engine out of item-by-item difficulty adaptation for the duration of the block.
  • Trend-linked questions carry shared dataset context that has to travel with them into the adaptive sequence.

The mechanism. It has two layers. First, a set of administration decisions that hold regardless of how a case is scored (how many cases, where they fall, exposure) — settled 2026-07-16. Second, the scoring method: how a case moves the student's ability. On the scoring method there are two designs that reach essentially the same result, and the chosen build is the "hybrid" (2026-07-18, Sam); the "testlet" model it grew out of is retained below as the documented alternative. Both enforce the same safeguard — a 6-question case counts as fewer than six independent measurements — so the engine is never made falsely over-confident by one correlated block.

Chosen scoring method — the hybrid (2026-07-18, Sam). When a case is served, the engine stops difficulty-picking and delivers the 6 children in their fixed clinical-judgment order, but each child updates the main ability level directly, counting as HALF a normal question. "Counts as half" applies to both jobs an answer does — it moves the level half as much and tightens the engine's certainty half as much (stating it as "each case question counts as half a question, full stop" guarantees both halve together). So a 6-child case contributes about three questions' worth of evidence, not six — the local-independence safeguard, applied inline. Why this is the build choice over the testlet:

  • Simpler and more robust. One ability track — no separate case estimate, no merge step. It reuses the existing standalone level-update path with a single "half-weight" setting; fewer moving parts, fewer places to get it wrong.
  • No noisy from-scratch estimate. The testlet measures the case from a fresh theta = 0.0 using only 6 questions (inherently noisy). The hybrid keeps building on the student's already-established main level.
  • Certainty is handled automatically. The testlet's most error-prone step is computing the case's own certainty, inflating it, and merging it into the main certainty. The hybrid needs no separate case certainty — the half-weight folds certainty in one child at a time, so "count as ~three, not six" happens for free.
  • The "half" is a starting default, not a magic number. It encodes an assumption about how much the 6 children overlap (they share one scenario, so are worth fewer than six independent questions). It is tuned from real response data later through the same recalibration pipeline (§5 / §17) that refines difficulty — if cases overlap more, the weight drops toward "count as ~one"; if less, toward "~six". Equivalent framings: a case counts as effective ≈ 6 ÷ (1 + 5 × overlap) questions; half-weight corresponds to ~three.
  • Clinical-judgment read still available. The testlet produced a standalone "case level" as a by-product (feeding the §13 clinical-judgment read). The hybrid doesn't feed one into the engine, but the same number can be computed display-only from the 6 answers for the results page — it never touches the exam.

Retained alternative — the "testlet" model (settled 2026-07-16; superseded as the build choice 2026-07-18). A case is treated as its own self-contained mini-estimate that runs alongside the main exam and hands back a single combined result — the recognised "testlet" technique for a bundle of items sharing one stimulus. Its five parts below; note that parts 1, 3 and 5 (administration, no new difficulty field, exposure) are common to the hybrid too — only parts 2 and 4 (the separate estimate + the merge) are what the hybrid replaces with its simpler inline half-weight update. Five parts:

  1. Administration — fixed count, fixed-ish positions, never first. Exactly 3 case studies per CAT, mirroring the real NCLEX (18 case items = 3 sets, delivered to every candidate regardless of exam length). They are served on a schedule, not difficulty-matched for selection. All three fall within the first 85 questions (the minimum length) so every student receives all three before the earliest possible finish, and they are spread out. Never at position 1 (settled 2026-07-16): a case is a single correlated block, so leading with one gives the engine a weak first fix and a slow start — the exam takes several standalone questions first (start no earlier than ~Q8) to get a rough footing, then drops in the first case. Real NCLEX likewise does not open with a case.
  2. The case runs its own internal estimate. The 6 children are fixed and in fixed clinical-judgment order (we cannot choose them adaptively), but the engine still runs the normal Rasch level-update maths across them — i.e. adaptive estimation over a fixed sequence, not adaptive selection. The case estimate starts fresh at theta = 0.0 (high uncertainty) and each child, scored at its own difficulty_irt, nudges the case level up/down. Getting the hard children right moves the case level more than the easy ones — so it uses more information than a bare "X of 6 correct" would.
  3. Case difficulty is not a new field. Because cases are not difficulty-matched for selection (part 1) and the internal estimate uses each child's own difficulty_irt, there is no need for a separate "wrapper difficulty" value. The earlier open question dissolves.
  4. The merge — one combined measurement, not six. When the block finishes, the case's final level merges into the main exam level as a confidence-weighted average (the more confident of the two estimates gets more say). Crucially, the case's uncertainty is deliberately inflated before merging so the whole 6-question block counts as roughly one independent measurement, not six — this is the knob that enforces local independence and stops the engine becoming falsely over-confident. Effect: a case moves the main level meaningfully but only tightens certainty a little. A case landing early (when the main estimate is still unsure) has large influence; one landing late (main estimate well-established) only nudges it. The exact inflation factor is a build-time dial, seeded with a sensible default and refined from data later (how much a case's children actually move together).
  5. Exposure is wrapper-level. The last-3-CATs window (§15.2) applies to the whole case — if the student saw this scenario in their last 3 CATs, the entire case (all children) is skipped. The scenario is the memorable leak, not the individual child. Same for trends (the shared dataset is the leak).

Trends are ALWAYS single questions in CAT — never testlets (settled 2026-07-16, Sam). A real NGN trend is a single-question item type (one question over a data-table / flowsheet); the Maryland specimens confirm it. The ability to attach multiple questions to one trend wrapper is a MyNclex authoring convenience (mint more bank questions from one dataset), not a real-exam construct. So in CAT:

  • The engine serves exactly ONE of a trend's linked questions, treated as an ordinary adaptive standalone item — normal difficulty-match, normal single level update. No internal estimate, no merge, no block delivery. A trend is an item, full stop.
  • The extra questions on a trend are an interchangeable pool on the same dataset. This is a quiet benefit: because the pool can span difficulties, the engine gets a small selection choice — it picks the one whose difficulty best fits the student. The others are simply not served in that attempt.
  • Exposure: serve at most one question from a given trend within an exam (so the same flowsheet is never shown twice in one CAT). Cross-CAT, normal item-level exposure applies.

This collapses the engine's world to exactly two shapes: items (every MCQ/SATA/bow-tie… and every trend) and case blocks (case studies only — the 3-per-exam blocks above, scored by the hybrid half-weight method). The engine never has to ask "how many questions does this trend have?" — it always serves one. If a bank trend was ever authored as a genuinely sequential multi-question set, that is structurally a case, not a trend, and should be authored as a case; CAT does not treat any trend as a block.

Clinical-judgment read: either scoring method lets the results page surface a distinct "clinical judgment" read (case performance as its own skill signal) on top of the overall verdict — matching how the real NCLEX treats clinical judgment as a separately-measured competency. Under the testlet it fell out of the case's standalone level; under the chosen hybrid it is computed display-only from the case's 6 answers (it does not feed the engine). See §13 for where this lands on the summary page.

Schema implication (for §12 build handoff): under the hybrid, each child's main-track level and uncertainty before its half-weight update already live on the child nclex_attempt_items rows (cat_theta_before / cat_se_before) — no separate case-estimate columns are needed for the engine. (The testlet alternative would instead need to persist each case's final case level + merge.)

Resolved 2026-07-19 — see §12.7.12. The floated optional per-case "clinical judgment" column is dropped: it is display-only and computable on read from the six stored answers, so storing it would only create a value that can drift from its own formula. Two different columns are added instead, both serving the "tune the half from data later" commitment: cat_weight on nclex_attempt_items (the weight each answer actually carried — 1.0 standalone, 0.5 case child) and cat_engine_version on nclex_attempts (which update formula ran). The case linkage needed for tuning — parent_case_id, case_position, cjmm_step, selection_unit_type — already exists on nclex_attempt_items and needed nothing new.

§11's snapshot design already anticipated wrappers: case/trend snapshot behaviour for CAT is specified there and needs no rework — only activation. Two worked examples of the whole flow (a case mid-exam, and three cases across a full exam) are folded in below (§7.4.1).

How the merge is computed — the method (settled). After a case, the engine holds two estimates of the student's ability, each with its own uncertainty: the main exam level (built from every standalone so far) and the case level (built fresh across the 6 children). They combine as a confidence-weighted average — each estimate's weight is how tight its uncertainty is, so the more confident estimate pulls harder; it is not a naive 50/50 split. Crucially, before merging, the case's uncertainty is deliberately widened ("inflated"): its 6 children lean on one scenario, so they are worth only ~1–2 independent questions, not 6. That widening (a) lowers the case's weight so it nudges rather than dominates, and (b) keeps the combined certainty from jumping as if six independent questions had landed — the local-independence safeguard against false over-confidence. Settled principle: confidence-weighted average, with the case's uncertainty inflated so it counts as ~one measurement. Build-time dial: the exact inflation amount (how correlated we assume the 6 children are) — seed a sensible default, refine from real data later.

7.5 Bank-exhaustion fallback

Edge case: student is at ability 0.5, the engine wants a question at difficulty ~0.5, all candidates have been seen in their last 3 CATs.

Rule: relax exposure before relaxing difficulty.

  1. First try: unseen questions within difficulty tolerance, not seen in last 3 CATs → ideal pick.
  2. If empty: questions within difficulty tolerance, even if seen in last 3 CATs → fall back to allowing repeat.
  3. Never: serve a wrong-difficulty question to avoid a repeat.

Fallbacks are logged so the curator dashboard can flag "X% of CAT picks fell back to repeats — bank may be too small or too thinly distributed at this difficulty band."

Until empirical calibration kicks in (§5.2), the bank only has three difficulty values: −1 (Easy), 0 (Medium), +1 (Hard). The student's ability is continuous (could be 0.1, 0.34, −0.62, anything), but every question sits at one of three values. So the rule effectively becomes:

7.7 The three-rung difficulty ladder — observed consequences open — Sam 2026-07-19

Found by Sam driving a real CAT in the browser on 2026-07-19, not by testing. Every difficulty_irt is currently seeded from the curator's Easy/Medium/Hard label, so the entire eligible pool sits on three values: −1.0, 0.0, +1.0. §7.1 already anticipated this and switched selection to nearest-neighbour so it degrades gracefully. It does. But two consequences show up in a live exam that "degrades gracefully" undersold.

1. The exam stops visibly responding to a strong student

Sam reached theta 2.14 while the hardest item we own is 1.0. Every question was then over a logit too easy — ~76% correct on ability alone, and each answer carrying ~27% less information than a matched one. He then answered five in a row deliberately wrong; theta fell correctly (2.24 → 1.65) but the served difficulty could not change, because Hard remains the nearest rung until theta drops below 0.5 — the midpoint. From 2.24 that is roughly ten more wrong answers before the engine can appear to react.

Nothing is broken; there is simply nothing between 1.0 and 0.0 to serve. But a student reads it as an exam that has stopped listening, which is the opposite of what an adaptive test is meant to feel like.

2. The readiness probability saturates — and §9.5 promises otherwise

§9.5 offers the readiness probability as "the honest, native Rasch output, available from launch day," with worked values of 89% / 60% / 23%. Those illustrations quietly assume a bank with spread difficulty. On a three-rung bank it pins at ~100% for anyone clearly above the line and ~0% below, and only says anything useful for a student sitting almost exactly on the boundary. Measured against the built engine: 

20 Hard, all correct     theta 2.85  SE 0.509   P(above) 100.0%
60 Hard, all correct     theta 3.55  SE 0.311   P(above) 100.0%
60 right THEN 60 wrong   theta 0.97  SE 0.180   P(above) 100.0%
Sam's live run @ Q35     theta 1.65  SE 0.369   P(above)  99.999%

The maths is right — we genuinely are that confident. But §13 plans to show this number to students, and a "readiness" figure reading 100% for most passing candidates is not the honest, informative signal §9.5 describes.

Two things this run also CONFIRMED as correct

  • theta does not run away. It asymptotes — 20 → 60 → 120 all-correct answers give 2.85 → 3.55 → 3.80. Once a student is well above an item's difficulty, getting it right is expected and barely updates the estimate; the prior and the ±4 grid bound the rest.
  • A high estimate cannot be banked. The estimator recomputes from the whole history, so "60 right then 60 wrong" and "alternating 60/60" both give theta 0.97 — identical. There is no coasting on early success. (Slice 2 asserts this order-independence explicitly.)

A student who scores 50% on Hard items landing at 0.97 — a pass — is the model working, not a loophole: where you score is as meaningful as how much.

Capping theta at the hardest item — considered and REJECTED

Sam's question (2026-07-19): if the hardest item is 1.0, should theta be capped there? It would genuinely help the symptom — from a capped 1.0 a student needs ~6 wrong answers to reach the Medium switch instead of ~15 from 2.14. Rejected anyway, on two grounds.

  • It would poison Slice 10. Recalibration estimates an item's difficulty from the abilities of the students who answered it. Feed it capped thetas and every strong student looks identical, so the job would systematically under-estimate how hard the hard items are — and the ladder would never widen. The cap would sabotage the very thing that fixes the problem.
  • It discards real information. A student at 3.5 and one at 1.5 would both flatten to 1.0, so the cross-CAT trajectory §15.4 shows students stops meaning anything at the top end.

The estimate is not wrong at 2.14 — it correctly says "at least this good, and we cannot tell how much better." The imprecision is already reported honestly in the SE (0.45 where a matched bank would give ~0.19).

Clarification worth keeping: 1.0 is not a design ceiling. difficulty_irt is an unbounded NUMERIC with no CHECK. Nothing exceeds 1.0 only because §12.7.1 seeded three curator labels to three numbers. An item can sit at 2.5; none does yet.

Two routes to widen the ladder — recalibration (Slice 10, self-maintaining but needs response data), or curator authoring beyond the range (immediate, needs no data, but requires either a finer authoring scale or letting difficulty_irt be set directly for outliers). The second is the faster of the two and does not touch the engine.

The honest caveat: even with a well-spread bank the strongest student always outruns the pool — that is inherent to adaptive testing, not something to engineer away. What is fixable is the degree: today the ceiling bites at theta 0.5, barely above average. It should bite somewhere like 2.5, where almost nobody lives.

What this changes

Slice 10 is no longer only a post-launch nicety. §19.4 files it as "trails; not needed to launch CAT," which is true of the engine but not of the plan's promises: meaningful difficulty tracking for strong students and an informative readiness probability both depend on difficulty having real spread, which is exactly what recalibration produces. Open — decide before Slice 7 builds the results display whether to show the probability as planned, reshape it, or gate it until recalibration has run. A curator-side alternative worth weighing: authoring items deliberately above +1.0 and below −1.0 would widen the ladder without waiting for response data.

8.1 The rule

Category influences selection only as a tiebreaker among equally-good difficulty matches — see §7.1 for the full mechanic.

When the engine is choosing between two unseen questions both within the difficulty tolerance of the student's current ability, it prefers the one in an under-represented category. When no equally-good difficulty match exists in an under-represented category, the engine picks by difficulty alone. Category never overrides difficulty; it just decides between equally-good options.

8.2 Why not stronger enforcement

Hard enforcement (forcing a pull from any under-represented category regardless of difficulty fit) was considered and rejected. Reasoning lives in §7.2 in full; the short version: hard enforcement degrades measurement quality, can break on a small bank when no question exists at the right difficulty in the under-represented category, and hides bank-balance signals that should be addressed by curating more questions, not by engine compensation.

8.3 Monitoring

Each CAT attempt logs the actual category distribution achieved. Specifically, per attempt we record:

  • Count of items delivered per category.
  • Percentage of items per category vs total delivered.
  • Gap vs the NCLEX blueprint targets.
  • Tiebreaker activation rate (how often the under-represented preference influenced a pick).

Aggregated across attempts, this surfaces in a curator dashboard as: average distribution across recent CATs, consistent gaps from blueprint, count of questions per category at each difficulty level. If a category is consistently underweight in delivered CATs, the fix is to curate more questions in that category, not to add engine enforcement. The dashboard itself is a separate piece of work; this section just specifies what gets logged so the dashboard has data to read.

8.4 Hard enforcement deferred to v2 — when

Revisit if monitoring shows the soft tiebreaker rule produces persistently lopsided category mixes that curation alone cannot fix. Specifically: if after curating to a balanced bank, we still see CATs delivering <3 items in a category 20%+ of the time, that's the signal to consider stronger enforcement. Until then, the tiebreaker rule + bank curation is the v1 answer.

9. Termination logic settled

Real NCLEX terminates a CAT under one of three conditions: (1) confidence reached, (2) max questions reached (150), (3) time limit reached. We mirror the same shape with our own thresholds. All four sub-decisions locked 2026-05-04; min/max counts corrected 2026-07-14 (see §9.2).

9.1 Confidence threshold

The engine terminates when both are true at the same time:

  • Standard error of the ability estimate ≤ 0.40. The margin of error has shrunk to the point where the engine is confident in the estimate.
  • Ability estimate is clearly above (or clearly below) the passing standard of theta = 0.0. "Clearly" means the 95% confidence interval around the estimate — theta ± 1.96 × SE — lies entirely on one side of zero. Revised 2026-07-19; see the multiplier note below.
    • Estimate 0.5, SE 0.40 → band −0.28 to 1.28 — crosses zero, keep going.
    • Estimate 0.9, SE 0.40 → band 0.12 to 1.68 — entirely above zero, terminate, ABOVE_STANDARD.
    • Estimate 0.5, SE 0.20 (later in the exam, evidence accumulated) → band 0.11 to 0.89 — terminate, ABOVE_STANDARD.

The multiplier is 1.96, and it must be stated explicitly (settled 2026-07-19, Sam). This section previously defined the rule as "the SE band doesn't cross zero" and illustrated it with estimate 0.5, SE 0.40 → band 0.1 to 0.9. That worked example is a ±1 SE band — roughly 68% confidence — which nobody appears to have chosen deliberately; it fell out of writing the example with a single SE. Under it, a student would be told "you're ready" on about 84% one-sided confidence, i.e. roughly one such verdict in six would be wrong.

Why 95%. The real NCLEX's core stopping rule is the 95% confidence-interval rule — it serves questions until it is 95% confident the candidate sits on one side of the standard. This doc's stated north star is to match the real exam (the same principle that corrected 75/145 → 85/150 in §9.2), and the verdict is high-stakes: students use it to decide whether to book a real exam sitting. ~84% is too loose for that decision.

What it costs, stated honestly. A wider band takes longer to clear zero, so fewer CATs stop early and more run toward the 150 ceiling — precisely what §9.1's SE ≤ 0.40 choice was hedging against. At SE 0.40 the old rule needed |theta| > 0.40; the new one needs |theta| > 0.78. This lengthens exams rather than stranding students, because SE keeps shrinking as evidence accumulates: by SE 0.20 the 95% rule only needs |theta| > 0.39. Watch the 150-ceiling rate once real CATs run. If too many students hit it, the honest lever is the SE ≤ 0.40 threshold, not weakening the confidence rule back toward a coin-flip.

The two conditions are not redundant. SE ≤ 0.40 is a precision floor (the estimate must be sharp); the 95% band is a separation rule (it must be far enough from the line). A sharp estimate sitting at theta = 0.05 fails the second; a distant estimate with a huge SE fails the first. Both are required.

Why theta = 0.0 as the passing standard: the real NCLEX standard is set by NCSBN's standard- setting committee from outcome data we don't have, so we can't copy them. theta = 0.0 means "measurably above average ability" — honest and defensible without outcome data. Once empirical calibration matures and we have student outcome data, we can revisit.

Why SE ≤ 0.40: standard CAT systems use 0.30–0.50. 0.40 sits in the middle — confident enough to give a meaningful verdict, loose enough that we don't push too many students to the 150 ceiling.

9.2 Min and max question counts

  • Min: 85. The engine cannot terminate before this even if SE converges fast.
  • Max: 150. The engine forces termination at this count regardless of SE.

Both match real NCLEX exactly. No reason to deviate — students practising for NCLEX should experience NCLEX's range.

Corrected 2026-07-14 (Sam): earlier drafts of this doc used 75/145 — the pre-NGN NCLEX-RN range. The NGN test plan (live since April 2023) uses 85 minimum / 150 maximum, and since our rationale is "match real NCLEX exactly," the numbers are corrected throughout this doc.

9.3 Time limit

4 hours. Real NCLEX gives 5; 4 hours is enough to feel real and build stamina, short enough not to be punishing for practice. Behaviour at time expiry: auto-terminate, score against current theta + SE, mark termination reason as TIME.

9.4 Termination reasons

Each terminated CAT records why it ended. Four values, and they are exactly the four the cat_termination_reason CHECK constraint allows (§12.7.3). Revised 2026-07-19 — this list previously named five, splitting the confidence case into PASS/FAIL; see the note below.

  • CONFIDENCE_REACHED — the 95% band (±1.96 SE) cleared zero with SE ≤ 0.40, at ≥ 85 items (§9.1). Verdict = whichever side it cleared on.
  • MAX_ITEMS_HIT — 150 questions reached. Revised 2026-07-15: the confidence requirement is dropped and the verdict is resolved by which side of 0.0 the final estimate sits — final theta ≥ 0 → ABOVE_STANDARD, < 0 → BELOW_STANDARD (mirrors the real NCLEX Maximum-Length rule). No longer INCONCLUSIVE.
  • TIME_LIMIT_HIT — 4-hour time limit reached. If ≥ 85 items answered → verdict by final-estimate side (as MAX_ITEMS_HIT). If fewer than 85 answered → BELOW_STANDARD (mirrors the real NCLEX Run-Out-Of-Time rule). Never INCONCLUSIVE.
  • ABANDONED — student manually discarded mid-CAT, or browser-close. No verdict produced — cat_verdict stays NULL.

Why the reason does NOT carry the direction (settled 2026-07-19, Sam). Earlier drafts split the confidence case into CONFIDENCE_PASS / CONFIDENCE_FAIL. Dropped, for three reasons. (1) It duplicates a fact. The direction already lives in cat_verdict; two columns holding one fact can disagree, and nothing would catch a CONFIDENCE_PASS row sitting next to a BELOW_STANDARD verdict. (2) It is asymmetric. Max-items and time-out produce a direction too, so consistency would demand MAX_ITEMS_PASS, MAX_ITEMS_FAIL, TIME_PASS, TIME_FAIL as well — eight values to express what four plus the verdict column already express. (3) They are different questions. "Why did it stop" and "how did it turn out" are distinct; ABANDONED is the proof, having a reason but deliberately no verdict.

Mapping from the old five, for anyone reading older notes: CONFIDENCE_PASS → CONFIDENCE_REACHED + cat_verdict = 'ABOVE_STANDARD'; CONFIDENCE_FAIL → CONFIDENCE_REACHED + cat_verdict = 'BELOW_STANDARD'; MAX_ITEMS → MAX_ITEMS_HIT; TIME → TIME_LIMIT_HIT. The longer schema names are kept — they read more precisely and are already applied.

9.5 Verdict resolution — always a side, plus a readiness probability revised 2026-07-15

Decision (2026-07-15, Sam): every completed CAT resolves to ABOVE_STANDARD or BELOW_STANDARD. The INCONCLUSIVE verdict is retired. Two reasons: (1) the real NCLEX never returns "inconclusive" — at maximum length it drops the confidence rule and calls the exam by the final estimate, and our north star is to match the real exam; (2) a student who fought through 150 questions deserves a real read, and the readiness probability below lets us stay honest about boundary cases without a non-answer.

How the side is decided:

  • Confidence reached (SE ≤ 0.40, the estimate's 95% band (±1.96 SE) clears 0, ≥ 85 items) → that side. (§9.1)
  • Maximum length (150) → confidence requirement dropped; decided by which side of 0.0 the final estimate sits (≥ 0 → above, < 0 → below). Mirrors the NCLEX Maximum-Length rule.
  • Time-out (4 h) → same as max length if ≥ 85 answered; BELOW_STANDARD if fewer than 85 answered. Mirrors the NCLEX Run-Out-Of-Time rule.

Every verdict carries a readiness probability. From the final estimate + its uncertainty we compute P(true ability > 0) — the normal-curve area above the 0.0 line. This is the honest, native Rasch output, available from launch day. Examples: estimate 0.5 / SE 0.40 → ~89%; 0.1 / 0.40 → ~60%; −0.3 / 0.40 → ~23%. It is derivable from cat_final_theta + cat_final_se, so no new stored column is strictly required. Build note 2026-07-19: the optional cat_readiness_probability column was considered and NOT added in Slice 1 — a recomputable value should not also be stored, because the copy can drift from the formula that produces it (§12.7.12).

This probability and the §9.1 stopping rule are the same statement. A 95% interval (±1.96 SE) clearing zero is exactly the condition P(true ability > 0) ≥ 97.5% — or ≤ 2.5% on the below side. So the termination check can be read either way, which makes a useful implementation cross-check in Slice 2: the band test and the probability test must always agree.

It also explains the examples above. Estimate 0.5 / SE 0.40 gives ~89% — short of 97.5%, so the engine does not stop there, matching §9.1's worked example where that band (−0.28 to 1.28) still crosses zero. Estimate 0.9 / SE 0.40 gives ~98.8%, which clears the bar, matching §9.1's terminating example. A student can therefore see a confident-looking readiness probability on a CAT that ran to the 150 ceiling — the number and the verdict are consistent, the exam simply never reached the stricter stopping bar. Worth keeping in mind for the §13 results copy.

Honesty guardrail (see §3.5): this probability is framed as "how confident we are you're above our standard," NOT as a probability of passing the real NCLEX. Same number, honest label; the real-NCLEX label waits for outcome data.

Boundary students (the old "inconclusive" case) now get a near-50% probability plus the per-Client-Needs-Category breakdown, which does the actionable work. We never say "you failed" or "you'll pass the NCLEX"; the honest framing is e.g. "Below standard — ~40% likely above our bar; this was close, here's where to push."

Readiness Signal weighting: with INCONCLUSIVE gone, every CAT contributes an above/below signal. A near-boundary verdict simply carries a mid-range probability; the old "weight as zero" rule is no longer needed (§13.4).

10. Architecture — the two-RPC flow settled

Per attempt-creation §13 (already settled): CAT does not use the same create-attempt RPC as fixed-length modes. Two RPCs instead. Settled 2026-05-05.

10.1 Transition pattern between questions

Pessimistic UI with graceful degradation. The current question stays visible during the wait (dimmed, inputs disabled) — psychologically faster than a blank loading screen even when the wait is identical. Specifically:

  • 0–300ms after Submit: current question stays visible, inputs disabled, very subtle fade or shimmer on the question area. No spinner. This is the happy path and will be the experience the vast majority of the time.
  • 300ms–3s: spinner appears in the question area, current question still dimmed underneath.
  • 3s+: "Still loading..." text appears next to the spinner.
  • 10s+: error state with a "Retry" button.

Rationale: pessimistic is the only honest choice for CAT — the engine genuinely has to score before picking the next item, so there's nothing real to optimistically render. Optimistic UI in this context would mean faking content we don't yet have.

10.2 The two RPCs and what each one does

create_cat_attempt(student_id, intent='EXAM', mode='CAT'):

  • Inserts a row into nclex_attempts with starting theta = 0.0, SE at the initial high value, status = IN_PROGRESS.
  • Picks the first item using §7 selection rules (closest to theta = 0.0, category as tiebreaker, eligibility filters).
  • Snapshots the picked item into nclex_attempt_items with cat_theta_before = 0.0 and cat_se_before = <initial>.
  • Returns { attempt_id, first_item_payload }.

cat_next_item(attempt_id, last_answer_payload):

  • Scores the last answer using the existing per-question scoring functions (reused unchanged from bank-marks-and-scoring.html).
  • Writes the answer into nclex_attempt_answers.
  • Updates theta and SE using Rasch (1PL) update math per §4. The item outcome fed to the update is score_awarded / marks — a fraction for partial-credit types (Option 2, §4.5), which is 1.0 / 0.0 for fully-correct / fully-wrong and for dichotomous MCQ/TF.
  • Checks termination conditions per §9: if SE ≤ 0.40 and items ≥ 85, OR items = 150, OR time ≥ 4 hours → terminate, write cat_verdict, cat_final_theta, cat_final_se, cat_termination_reason, cat_items_administered, return { status: 'COMPLETE', verdict_payload }.
  • Otherwise: pick next item per §7, snapshot into nclex_attempt_items with the pre-update theta/SE captured in cat_theta_before/cat_se_before, return { status: 'CONTINUE', next_item_payload }.

Both RPCs are atomic — score + theta update + select + snapshot run in a single transaction. If anything fails, nothing partial gets written.

10.3 Error handling

  • Network failure on the browser side: browser auto-retries silently up to 2 times with exponential backoff (1s, 2s) before showing the error UI.
  • RPC throws a server-side error: browser shows the error UI immediately, no auto-retry (the problem isn't transient).
  • The attempt row is never left in a half-updated state because the RPC is transactional — either the answer is recorded and the next item is snapshotted, or neither happens.
  • If the student gives up after the error UI appears: they can close the browser → status becomes ABANDONED per §16.

10.4 Why these specific numbers

  • 300ms / 3s / 10s thresholds sourced from standard UX latency research: under ~400ms feels instantaneous, 1–3s feels like a brief wait, 3s+ requires reassurance, 10s+ requires acknowledgement that something is wrong.
  • 2-retry cap is conservative — fewer than 3 to avoid masking a real outage as a long wait, more than 0 to handle transient Wi-Fi blips.

  • Engine runtime location — RESOLVED 2026-07-19, see §10.6. The split is: TypeScript computes (Rasch math + scoring), the RPC persists and selects.
  • Exact wording of the error UI ("Connection lost" / "Couldn't load next question" / etc.).

10.6 Engine runtime — where each half runs settled 2026-07-19

§10.5 left the engine's runtime location open, and §19.4 scheduled the decision for the top of Slice 2. It was brought forward to before Slice 1 because it changes the RPC stub signatures that Slice 1 ships (§12.7.6) — deferring it would have meant stubbing the wrong shape and rewriting it.

First, a framing correction. This was initially posed as a conflict between §4.2 ("TypeScript Rasch") and §10.5 ("recommendation: Supabase RPC"). It is not one. §4.2 chose a language — TypeScript over standing up a separate Python service; PL/pgSQL was never a candidate there. §10.5 chose a location. The two sections are answering different questions.

The deciding fact. lib/scoring/README.md describes the scoring engine as "pure TypeScript, no DB calls, deterministic," and §10.2 specifies that cat_next_item "scores the last answer using the existing per-question scoring functions (reused unchanged)." Both cannot be true if cat_next_item is PL/pgSQL — reusing TypeScript functions from inside a Postgres function is not possible. A pure-PL/pgSQL engine would require reimplementing all five scoring functions plus the 13-type dispatch in SQL and maintaining them in lockstep forever. That is the exact failure mode already seen with the marks bug (one place computing a value, another validating it against a different rule, blocking submission across 547 questions). Duplicating the scoring engine is the most expensive duplication available in this codebase.

Decision — the work splits along the line the codebase already uses: TypeScript computes, the database persists.

  • Rasch math → pure TypeScript (lib/cat/), Vitest-tested. This is how §19.4 already describes Slice 2 ("Rasch math, pure + unit-tested") — a description that only makes sense for a testable pure module. PL/pgSQL math would have to be tested through SQL fixtures instead.
  • Scoring → @/lib/scoring, reused unchanged, exactly as §10.2 requires.
  • Item selection → stays in SQL, deliberately. "Closest to theta, category tiebreaker, minus everything seen in the last 3 CATs, eligible only" (§7.1/§7.3/§15.2) is a query over thousands of rows. Doing it in TypeScript would mean dragging candidate rows over the wire to sort them.
  • cat_next_item stays PL/pgSQL but receives the already-computed score and updated theta/SE rather than a raw answer payload. It performs the atomic write, the selection, and returns the next payload.

What this protects:

  • Atomicity (§10.3) survives intact. Every write still happens inside the one RPC; the TypeScript half is pure computation with no side effects, so if it throws, nothing was written. "Either the answer is recorded and the next item is snapshotted, or neither" still holds.
  • Trust. The TypeScript runs server-side (Server Action), never in the browser, so a student cannot post a fabricated theta. This is stated explicitly because the practice runner does score client-side with the RPC range-checking the result — an arrangement that is not good enough for a high-stakes verdict.

The honest cost: two places to look when debugging a single CAT step, and a wider RPC signature than §10.2's prose implies.

10.7 Creating a CAT is one atomic act — no create/start split settled 2026-07-19

Decision (Sam, 2026-07-19): nothing exists until the student confirms at the preflight. The preflight is the last honest moment to change their mind, so it is where the attempt row is created, the clock starts, and the allowance is spent — all in the one call, all in one transaction. Before that button there is no attempt row, no snapshotted item, and nothing counted.

This deliberately does NOT mirror the readiness pattern. Do not "fix" it to match. Readiness splits creation from starting — nclex_create_readiness_attempt leaves started_at NULL and spends nothing, then nclex_start_readiness_attempt stamps used_at and starts the clock together. Both designs put the spend at the confirm, so both satisfy the requirement; the split was weighed and rejected for CAT on two grounds:

  • The reason readiness splits does not apply to CAT. The readiness preflight renders content off the created row — "You're about to sit a {itemCount}-question readiness exam" — so the attempt has to exist before the gate can be drawn. A CAT preflight has nothing equivalent: its length is 85–150 and unknowable in advance (§9.2), so every word on the screen is static. The split buys something CAT cannot use.
  • An unstarted attempt row is a standing hazard. Under a split, a row exists that looks like a CAT attempt but is not one, and every query about a student's CAT attempts must remember to exclude it — the §15.5 allowance count, history and results lists, analytics, and most dangerously §15.2 exposure exclusion. An abandoned preflight would leave a snapshotted question 1 attached to a row that never became an exam; if the exposure query omits the started_at filter, that question is treated as "seen" and withheld from the student's next three real CATs. Nothing errors, nothing looks wrong — the pool quietly narrows and measurement degrades. Collapsing creation and start makes created and started the same event, so the bug has nowhere to live.

The cost, stated plainly: two patterns in the codebase for one-shot exams instead of one. That is a real price and it is paid knowingly — the divergence is principled (readiness has pack content to render, CAT has none), not an oversight.

Consequences for the build:

  • Idempotency is not optional. One call now creates, starts and spends, so a double-click or a retried request must return the existing attempt rather than opening a second exam. This single guard protects everything, because every consequence lives in that one call.
  • The CAT preflight is its own surface, not a branch of the shared one. The existing preflight (app/(app)/(focused)/session/[attempt_id]/preflight.tsx) renders only when attempt.started_at === null and is addressed by an attempt id — neither is available before the attempt exists. The CAT gate therefore lives on the CAT entry page, ahead of /session. Its copy and styling should still borrow from ReadinessPreflight, which is the right visual language for a full-stop gate.
  • The shared runner needs no change. A CAT arrives at /session/[attempt_id] already started, so the started_at === null condition is false and the shared preflight correctly skips itself.
  • A read-only allowance check should run before the preflight renders, so a student who is out of CATs sees that instead of a Start button that fails. The authoritative guard stays inside the RPC — the precheck is courtesy, not security.

10.7.1 Exactly one place can spend a CAT — the Builder hands off settled 2026-07-19

The practice Builder already offers EXAM → CAT, and selecting it collapses the filters, pool and count (parent bank-consumption.html §17). So a student could in principle start a CAT from there, and the question arose (Sam, 2026-07-19) whether both surfaces should launch one.

Decision: no. The Builder becomes a doorway, not a launcher. Choosing CAT there shows a short explanation and a "Go to CAT" button that navigates to the CAT home. It creates nothing, spends nothing, and shows no preflight.

  • Because §10.7 puts the spend at the preflight, a second launcher would need its own preflight — meaning two places that must each get the full-stop warning, the allowance guard and idempotency right. Two paths that spend an entitlement will drift, and the failure mode is a student burning a CAT through whichever path forgot the gate. Same duplication objection as §10.6 (scoring), §19.4.2 (the source column) and the engine-version constant.
  • The Builder's CAT mode has nothing to build. Filters, pool and count all collapse, so it is a configuration screen with nothing left to configure — a mode selector wearing a builder's clothes.
  • Arriving at a dedicated page is the point (Sam): it is what teaches a student that CAT is its own kind of assessment rather than a practice variant.
  • The extra click is real, but for a 4-hour one-shot commitment a deliberate step is a feature — the same reasoning that justifies having a preflight at all.

Consequence for §19.4 Slice 9: "the Builder's CAT option under EXAM intent" remains an entry point, but is a handoff. Do not wire it to create_cat_attempt.

11. Snapshot strategy for CAT settled

Per-question snapshot at administration time, identical to the fixed-length snapshot strategy.

Specifically:

  • Each time create_cat_attempt or cat_next_item picks an item, it inserts a row into nclex_attempt_items with the full snapshot — stem, instruction, content JSONB, correct JSONB, rationale, classification, marks. Same column shape as fixed-length attempts.
  • If the item is trend-linked, the linked dataset is snapshotted into nclex_attempt_trend_snapshots (if not already there for this attempt) at the moment the trend item is picked.
  • If the item is a case-study child (active — §7.4 settled "include cases" on 2026-07-14), the case is snapshotted into nclex_attempt_case_snapshots at the moment the first child is picked, and all 6 children get queued.

11.1 Why snapshot, restated for CAT context

Three reasons settled in the seed conversation:

  1. Integrity. CAT exams take 85–150 questions. The window during which a curator might edit a question while the student is mid-exam is bigger than for any other mode. CAT's whole legitimacy depends on the ability estimate being a coherent measurement against a fixed answer key — if question 47's correct JSONB changes between when the student answered it and when the engine reads it, the entire ability trajectory is corrupt.
  2. Review depends on it. Review state (§14) renders rationales for the questions the student saw. Without snapshots, by the time the student opens Review, those rationales might have been edited or deleted. Snapshots are how Review survives curator changes.
  3. Calibration depends on it. Empirical recalibration (§5) needs to know what the item actually said when the student answered it. If a curator rewrote the stem after the student answered, the response data isn't a valid signal about the new stem's difficulty.

11.2 Why NOT alternative approaches

Two alternatives were considered and rejected in the seed conversation:

  • "Pull from live tables, just record IDs" — fails all three reasons above. Doesn't actually save anything because per-question snapshotting is already cheap.
  • "Snapshot at end-of-session, not per-question" — captures the wrong thing. State at end-of-session is not state at administration. If the curator edits item 12 after the student answered Q12 but before exam end, the end-of-session snapshot captures the edited version. Worse than skipping snapshots, not better.

11.3 Cost

A typical CAT exam administers ~85 items. Each nclex_attempt_items row carries the snapshot payload (stem, content, correct, classification — already shaped). Per-attempt snapshot storage cost is roughly the same order as a 75-item fixed-length quiz. Negligible.

12.7.12 Why cat_weight and cat_engine_version exist settled 2026-07-19

Both columns exist for one reason: §7.4 commits to tuning the "half" from real response data later, and that future analysis has to be able to read what actually happened. This subsection records why they are not redundant, because at first glance both look derivable.

What is already captured — most of it. nclex_attempt_items has carried the case linkage since the original attempt-tables migration: selection_unit_type ('QUESTION' | 'CASE'), parent_case_id, case_position (1–6) and cjmm_step. So "group the children by case," "which position within the case," and "which clinical-judgment step" all come for free. No new columns are needed for any of that.

The gap — the weight actually applied. Nothing recorded which weight was in force at the time. Ship at 0.5, move to 0.4 next year, and every historical row becomes ambiguous.

It is partly derivable, and the honest version matters: cat_theta_before is on every row, so item N's theta-after is item N+1's theta-before — the delta is recoverable, and with difficulty and the score fraction both stored you could algebraically solve for the weight. But that only holds while the update formula is unchanged. Once §4.4 (2PL) or §4.5 (Option 3) lands, back-solving old deltas with the new formula returns wrong weights quietly — plausible numbers, no error. That is the worst failure mode for a calibration input, and it is why an explicit stored value beats a reconstruction. cat_engine_version is the same argument one level up: it makes the formula-of-record explicit for every attempt instead of inferred from dates.

Deliberately NOT added — a stored clinical-judgment figure. §7.4 floated an optional per-case column holding the display-only clinical-judgment number "to be specified in the build slice." It is dropped. The figure is display-only, never touches the engine, and all six case answers are already stored — so it is computable on read. Storing it creates a value that can drift out of sync with the formula that produces it, for no benefit. The results page computes it (§13.2).

What the student sees when a CAT exam ends, and what they see when they open a finished CAT from History. Settled 2026-05-04. Same surface used in both contexts: the CAT summary page. 13.1 Verdict copy revised 2026-07-15

Two verdicts only (INCONCLUSIVE retired, §9.5). Each headline is paired with a readiness probability — "how confident we are you're above our standard" — from §9.5. A boundary student lands here too, just with a mid-range percentage.

ABOVE_STANDARD

  • Headline: "Above standard" · sub-line: "We're ~[NN]% confident you're performing at a passing level on our exam."
  • Body: "Your performance suggests you're tracking ready. Keep practising to maintain it — consistent CAT performance is what matters most."

BELOW_STANDARD

  • Headline: "Below standard" · sub-line: "We're ~[NN]% confident you're above our standard — more practice recommended."
  • Body: "Use the category breakdown below to see where to focus, then come back for another CAT in a few days."

Near-boundary framing. When the probability sits close to 50% (typically a max-length or time-out finish), the sub-line acknowledges it: "This was close — your ability sat right around our standard. The category breakdown below is where to focus." Honest and actionable, never a non-answer, and never "chance of passing the NCLEX."

ABANDONED (no verdict)

  • Per §16.5 — abandoned CATs never reach a result state. The History page shows them as "CAT — Abandoned"; opening the row goes to a minimal summary that explains the attempt was ended early and offers "Start a new CAT".

13.2 Summary page layout

In order from most prominent to least:

  1. The verdict itself — top of page, large headline + body copy from §13.1.
  2. Items administered — small fact line under the verdict. Example: "You answered 92 questions. The engine reached confidence at question 92." Honest, factual.
  3. Trajectory graph (see §13.3 below) — the most important visual on the page. Shows how the student's ability estimate moved across the test, plotted against a 0.0 reference line.
  4. Per-Client-Needs-Category breakdown — for each of the four categories: questions seen, questions correct (full credit only — see bank-marks-and-scoring.html §6 for the is_correct definition), per-category percentage. The most actionable text content on the page. Footnote required (§4.5): this "correct" count is full-credit-only, which differs from how the engine credited partial answers (fractionally); a one-line note should say so, so a student doesn't think their partials were ignored.
  5. Clinical judgment read (added 2026-07-16, from the §7.4 testlet model) — a distinct skill signal derived from the student's case performance (each case produces its own standalone level). Shown as its own line/badge separate from the overall verdict — e.g. "Clinical judgment: strong (you handled the case scenarios well)." Matches how the real NCLEX treats clinical judgment as a separately-measured competency. The finer per-reasoning-step detail (Recognise cues → … → Evaluate) is a v2 enhancement (§13.6).
  6. Compared to your previous CATs — only shown if the student has prior CATs. Plots theta + verdict per CAT across attempt history.
  7. Primary CTA: "Review answers" — opens the shared runner Review surface (per §14) for the per-question walk-through.

13.3 The trajectory graph + per-item marker

Single line chart. X-axis = question number (1 → N items administered). Y-axis = theta (ability estimate after that question's answer). A horizontal reference line is drawn at theta = 0.0 (the passing standard).

What the shape tells the student:

  • Steady upward trace settling above 0.0 — consistent strong performance, ability climbed and stabilised above the passing standard.
  • Steady downward trace settling below 0.0 — consistent weak performance, ability climbed down and stabilised below the passing standard.
  • Up-and-down trace not settling — inconsistent answering, the engine couldn't pin down their ability cleanly. Typically produces a near-boundary verdict (a readiness probability close to 50%), the case that used to be labelled INCONCLUSIVE (§9.5).

Per-item marker. If the summary page renders a per-question breakdown alongside the graph (e.g. a scrollable list of the questions they answered), the trajectory graph shows a marker indicating which question is currently focused. As the student scrolls or clicks a different question, the marker on the trajectory updates. This lets the student see, for any individual question they answered: where on the ability curve was I when this question was served?

What this replaces. An earlier draft proposed a per-item "At your level / Above your level / Below your level" chip. The trajectory + marker delivers the same context more richly — the student can see not just whether one question was at their level, but how their level was moving over time.

13.4 Connection to Readiness Signal

CAT verdict and Readiness Signal stay separate on the dashboard — they are NOT blended into a single number.

The dashboard surfaces two distinct cards:

  • CAT card. Shows the latest CAT verdict, a count of CATs taken, the date of the last CAT, and a link to that summary page. Copy: "Latest CAT verdict: Above standard. (CAT #3 of 3 taken)".
  • Readiness Signal card. Cross-history practice signal per parent bank-consumption.html §6. Independent of CAT.

Why separate, not blended:

  • Combining them forces a weighting algorithm we cannot validate without outcome data.
  • Students should see CAT as one snapshot, Readiness as the longer-term cross-history signal. Different products, different cards.
  • If a student takes one CAT, gets ABOVE_STANDARD, and the Readiness Signal still says "Approaching," the honest framing is "one CAT is one data point; cross-history sees more." Two cards make this conversation possible.

Superseded 2026-07-15: INCONCLUSIVE is retired (§9.5), so the old "weight as zero" rule no longer applies — every CAT now contributes an above/below verdict with a readiness probability. If a future v2 decision blends signals, it can weight each CAT by its readiness probability (confidence), not by a discarded verdict class.

15. Re-take rules settled

How often can a student take CAT? What about question exposure across CATs? Does prior CAT data influence the next CAT's selection? Settled 2026-05-04.

15.1 Frequency

Revised 2026-07-19 — this is now the default, not a constant. Unlimited remains what every tier grants unless configured otherwise; §15.5 adds the policy lever that can cap or withdraw it per product. Nothing below changes for a student on an unlimited tier.

Unlimited re-takes within the student's active subscription window. Matches industry standard — UWorld and Archer both offer unlimited CAT practice. Students under exam pressure want to drill; capping hurts the learning. The engine doesn't degrade with repeated use, so there's no technical cost.

No hard cooldown. The student can start another CAT immediately after finishing one. A soft warning appears if a student starts a CAT within 1 hour of finishing one: "CAT works best with rest between sessions — continue anyway?" Soft nudge only; not a block.

15.2 Question exposure across CATs

Exclude questions seen in the student's last 3 CAT attempts. Cross-CAT exposure window only — questions seen in non-CAT modes (Custom builder, Readiness Packs, Programme assignments) do not contribute to the exclusion list.

Why "last 3 CATs":

  • Forever exclusion is too strict for a young bank. A student doing 6 CATs in their final exam prep would burn through the strongest difficulty-matched questions; by CAT #4 the engine would be picking from increasingly thin pools.
  • No exclusion is too lax. Memory effects are real — if a student saw a question 3 days ago in CAT #1, they might remember the answer in CAT #2 and contaminate the engine's measurement.
  • Last 3 CATs is roughly 2–3 weeks of practice for a typical student, which is enough time for memory of a specific question to fade for most.

Why CAT-only (not other modes):

  • CAT and non-CAT are different contexts — a student who did Q47 in a Pharmacology custom quiz two months ago can still see it in CAT today without strong memory contamination.
  • If we excluded all non-CAT exposure too, the eligible pool for CAT would collapse for any student who's used the platform for a while.
  • Only cross-CAT exposure represents the same psychometric context (timed exam-style adaptive sequence) where memory effects materially degrade measurement.

15.3 Bank-exhaustion fallback

Edge case: student is at ability 0.5, engine wants a Medium-to-Hard question, all of those at the right difficulty have been seen in their last 3 CATs.

Rule: relax the exposure rule before relaxing the difficulty rule.

  1. First try: unseen Medium-to-Hard not seen in last 3 CATs → ideal pick.
  2. If empty: Medium-to-Hard seen in last 3 CATs → fall back to allowing repeat.
  3. Never: serve a wrong-difficulty question to avoid a repeat.

Difficulty match is sacred (§7). Exposure is a soft preference, so it's the one that bends. Fallbacks are logged so the curator dashboard can flag "X% of CAT picks fell back to repeats — bank may be too small or too thinly distributed at this difficulty band."

15.4 Theta carry-over — none

Each CAT starts at theta = 0.0 regardless of the student's prior CATs. Already settled in §6. Cross-CAT theta IS shown in History / Analytics ("your last 3 CATs landed at theta 0.5, 0.6, 0.65 — improving") but doesn't seed the next CAT's starting position.

15.5 CAT allowance — how many CATs a tier grants settled 2026-07-19

§15.1 settled frequency as "unlimited within the active subscription window." That is the right default, but it is currently an implicit one — unlimited means no gate exists at all. This section makes the ceiling a configurable property of the product so the answer can eventually differ per tier ("this tier gets one CAT," "this tier gets none," "this tier is unlimited") without re-opening the engine.

Why now rather than later (Sam, 2026-07-19). The enforcement point belongs at the top of create_cat_attempt — a function Slice 3 writes anyway. Adding one guard while writing that function is minutes. Retrofitting a gate into a live RPC afterwards means re-testing every path that opens a CAT plus every surface offering a "Start a CAT" button that must now handle refusal. The storage is free now and the gate is nearly free now; both get materially more expensive once CAT is live.

The build splits into three parts, and only two are cheap:

  1. The policy value — where the allowance lives (§12.7.5b). Built now.
  2. The enforcement point — one guard in create_cat_attempt. Built at Slice 3.
  3. The surfaces — admin UI to edit the value, student-facing counts ("2 of 3 CATs left"), the exhausted-state card and its upsell. Deliberately deferred — not needed to launch CAT. This follows the standing rule of capturing the mechanism now and building the readout when it is actually wanted.

15.5.1 Shape — a ceiling, not a balance

The instinct is to copy readiness credits, and it is the wrong model. A readiness credit is a consumable object the student owns — minted, claimed, spent, expired — which is why it needs a real table with rows. A CAT allowance is a ceiling, and §15.1 already anchors it to the subscription window, which means the consumed count is derivable: how many CATs has this student started inside this window? No balance table, no minting, and the entire double-spend class of bug never arises.

  • cat_allowance on nclex_products — the SKU's grant. NULL = unlimited, 0 = none, N = N per window.
  • Snapshotted onto nclex_subscriptions at activation, inside the grantProductEntitlement path that already inserts that row.
  • Consumption counted from nclex_attempts (CAT mode, within the window). Nothing to keep in sync.
  • One guard at the top of create_cat_attempt.

15.5.2 Stacked subscriptions — most-generous-wins

nclex_subscriptions documents its own stacking rule: "two active rows → access runs to max(end_at)." So a student may hold more than one ACTIVE bank row (buy 30 days, top up 60), and "read the allowance off the subscription" has to say which row.

Rule: a student may start a CAT if any currently-active row still has headroom; NULL on any active row means unlimited. Counting is per-row, from that row's started_at.

Summing the allowances was considered and rejected: it re-frames the ceiling as a balance (dragging back the double-spend problem this shape avoids) and has no sensible answer when one row says unlimited. The deciding argument for most-generous-wins is consistency — max(end_at) already resolves overlapping purchases in the student's favour, and having the allowance resolve restrictively would be an inconsistency someone eventually hits and reasonably reads as a bug.

15.5.3 An abandoned CAT burns the attempt

§16.5 makes a browser-close an ABANDONED attempt. Under unlimited this never mattered; under a ceiling it is a real policy. Decision (Sam): it burns. We cannot distinguish a genuine laptop failure from a student abandoning a CAT that is going badly, so the honest design is to say so before they start rather than adjudicate afterwards — the one-shot preflight warning states plainly that starting spends the attempt regardless of how it ends. The readiness one-shot preflight is the existing model to follow.

This gives the deferred per-user admin grant a defined purpose: it is the remedy path for a student who contacts support, not a speculative feature. It stays deferred and is safely deferrable — the read already routes through the entitlement row, so it later costs a column and one condition at a point the code already touches.

15.5.4 CAT is bank-family

Decision (Sam): CAT is a Bank capability, not a Programme one. A programme student without bank access cannot take a CAT regardless, so no programme-side concept is needed. CAT therefore sits behind the same requireActiveBankSubscription gate as the other five bank consumption surfaces, and the allowance rides on the bank entitlement row. No new access concept is introduced.

Consequence worth stating explicitly: a readiness-only student — someone who bought packs but holds no bank subscription — has no bank entitlement to carry an allowance, and so cannot take a CAT. That follows correctly from the decision, but it is exactly the kind of thing that surfaces as a confused student hitting a wall. The reason-aware /no-access wall already exists for this case; CAT needs to route through it rather than dead-end.

First real use of the column is likely TRIAL — a BANK_DURATION pack type where 0 or 1 is the sensible grant, well before any paid tier gets capped.

16. Runner UX specifics settled

Once a CAT answer is submitted, the student cannot return to the question. Same shape as the existing Timed Sequential mode in the fixed-length runner — no previous-question button, no answer re-edits.

Required by the engine's design as much as by the test feel: the IRT estimate updates after each answer; allowing answer changes mid-test would corrupt the trajectory. Matches real NCLEX exactly.

Behaviour:

  • Browser-tab-close attempt → custom warning prompt: "Closing this tab will abandon your CAT exam. Your progress will not be saved." Confirms before exit.
  • If confirmed → attempt status flips to ABANDONED, termination reason = ABANDONED, no verdict generated.
  • Accidental refresh → same warning, same outcome if confirmed.

16.6 No pause

Per parent §15: "CAT — IRT model needs continuous engagement; pause/resume invalidates the estimate." Already settled. No pause button. The 4-hour timer never stops. The session is start-to-finish.

Real-world breaks (bathroom, food, etc.) are the student's own choice; the timer keeps running. If the student needs a real break, they abandon and start a new CAT later. Matches real NCLEX (where breaks are permitted but the timer doesn't pause for them).

17.4 Why a separate table, not JSONB on the bank row

An alternative considered: stuff the calibration history into a JSONB array column on nclex_bank_items itself, with the engine reading the latest entry. Rejected for three reasons:

  • Engine performance. CAT picks an item by querying the bank for the closest-difficulty match. With difficulty_irt as NUMERIC, that's a fast indexed query. With JSONB, the engine has to pull every candidate's array, parse it, and extract the latest entry — per-item work on every single pick. A 92-item CAT does this 92 times per student. We'd turn a fast indexed query into a slow scan.
  • Snapshots break. §12.3 snapshots difficulty_irt into nclex_attempt_items.cat_item_difficulty at administration time. With NUMERIC that's a clean copy of one number; with JSONB you'd snapshot the whole array (which then grows over time — defeating "frozen at administration"), or you'd extract the latest value at snapshot time (which means the parse-and-extract dance happens on writes too).

17.5 Retention — keep forever for v1

Both the audit table and the per-attempt response data are kept indefinitely in v1.

  • Audit table: small data — one row per item per week. Even at 10,000 items running for 5 years, that's ~2.6M rows. Trivial for Postgres.
  • Trimming defeats the audit's purpose. The whole value is being able to ask "what did this look like in the past."
  • If storage ever becomes a real concern (it won't at v1 scale), revisit then.

19.4.1 Slice 2 build decisions settled 2026-07-19

Recorded here because they were taken during the build and would otherwise live only in the code. §19.4 listed the estimation method as an open decision; this closes it.

The estimator — EAP with a Normal(0, 1) prior

§4.2 settled the language ("~30 lines of TypeScript") but never named the algorithm, and the obvious choice does not work. Maximum likelihood has no answer when a student has got everything right or everything wrong — the estimate runs to infinity. That is not an edge case: it is the state after question 1 of every single CAT.

Chosen: Expected A Posteriori (EAP) over a quadrature grid, anchored to a mild prior — before any answers, assume the student is near average. Each answer moves the estimate; the prior only keeps it finite. Concretely: grid −4…+4 in 0.05 steps, prior Normal(mean 0, SD 1), posterior = prior × likelihood of every response, estimate = posterior mean, SE = posterior SD.

  • It answers §6's unquantified "high SE". With no responses the posterior is the prior, so a fresh CAT starts at exactly theta = 0.0, SE = 1.0. The starting position and the starting uncertainty are one decision, not two.
  • The honest cost: a mild pull toward average. With the 85-item minimum (§9.2) it is swamped by real evidence long before any verdict is issued — but it is an assumption, not a neutral stance.
  • Recomputed from the full response history rather than nudging a running value, so replaying an attempt always reproduces the same trajectory. 150 responses over 161 grid points is trivial work. The TypeScript layer therefore loads the attempt's prior responses before calling cat_next_item.

The half-weight is applied to the log-likelihood

§7.4 requires that "counts as half a question" halve both the level move and the certainty gain, and warns that stating it as two separate rules invites halving one without the other. Scaling the response's log-likelihood by the weight makes it structurally automatic — there is no separate theta adjustment and no separate SE adjustment to keep in step. Asserted exactly in the tests: two half-weight answers equal one full-weight answer, and a 6-child case equals 3 standalone questions, to 10 decimal places.

Termination precedence when conditions collide

A student can reach question 150 at the same moment the estimate becomes confident. Confidence is checked first, because it is the more informative reason — it says the engine measured the student rather than running out of room. The verdict is identical either way (both resolve by side), so this affects only the reason recorded, never the result.

Observed behaviour

Simulated students of known ability, run through the built module with difficulty-matched selection: true ability ±1.5, ±0.8 and −0.3 all terminated at the 85-item minimum with the correct verdict, while the borderline student (true 0.3) took 107 items. None reached the 150 ceiling. That is the §9.1 95% rule behaving as predicted — clearly-placed students finish fast, genuinely borderline students earn more evidence. Idealised: a real pool cannot always supply a perfectly matched item, so expect somewhat longer.

19.4.2 Slice 3 & 4 build decisions settled 2026-07-19

Recorded here for the same reason as §19.4.1 — these were taken during the build and would otherwise live only in the code.

No CAT value is added to nclex_attempts.source

source permits only CUSTOM_BUILT / READINESS_PACK / PROGRAMME_ASSIGNED. A CAT is stored as CUSTOM_BUILT, deliberately: CAT is launched from the Builder under EXAM intent (parent bank-consumption.html §17), so it genuinely is student-built; the source_refs CHECK is satisfied (all four reference columns NULL); and Exit resolves correctly to /student/bank/practice. mode = 'CAT' already identifies a CAT uniquely — the intent_mode_tuple CHECK pairs EXAM+CAT — so a second column saying the same thing would duplicate a fact, the same reasoning that kept the direction out of cat_termination_reason (§9.4).

No migration was needed for the attempt shape at all, which was checked rather than assumed: CAT mode, the EXAM+CAT tuple and the ABANDONED status were already permitted.

The engine version has one home

nclex_cat_engine_version() (currently rasch-1pl-eap-v1) rather than a literal repeated in SQL and TypeScript. Bump it when the update formula changes (§4.4 2PL, §4.5 Option 3); the Slice 10 recalibration job reads the same value.

requested_question_count carries the 150 ceiling

The column is NOT NULL with a > 0 CHECK, and a CAT's true length (85–150) is unknowable in advance, so the ceiling is the only honest fixed number available.

Four schema names in §12 prose did not match the live tables

Caught while writing Slice 4, by checking rather than by a failed migration: nclex_attempt_answers uses submission_status (DRAFT / SUBMITTED / AUTO_SUBMITTED / SKIPPED), not a status column with an 'ANSWERED' value; it carries its own student_id; it stamps submitted_at, not answered_at; and nclex_attempts ends at ended_at, not completed_at. Same class of error as the §12.7.5 bank_item_id mistake — treat the live schema, not this doc's prose, as authoritative when writing SQL.

answer_changes_json is deliberately NOT touched on conflict. It is the second-guessing log the results report reads, and a retried turn must not erase it.

19.4.3 Slice 5 build decisions + the Slice 6 runner survey settled 2026-07-19

The case schedule is randomised within windows, and derived not stored

§7.4 asks for "fixed-ish positions," spread within the first 85, never first. Built as one case randomised inside each of three windows — Q8–20, Q30–45, Q55–75. Fully fixed positions would be learnable: a student sitting several CATs would know a case always lands on Q8. Windows keep the required spread without the predictability.

The positions are derived deterministically from attempt_id (nclex_cat_case_positions()) rather than stored on the attempt. Deterministic on the id means the schedule is stable across replays and re-deriving mid-exam always yields the same three positions — so no column is needed. Same technique as the embed-player option shuffle.

Case children are snapshotted ONE PER TURN, not six upfront

Readiness snapshots every question at creation. CAT cannot copy that for a case block: cat_theta_before records the estimate the student faced each question with, and children 2–6 have not happened yet — snapshotting all six upfront would mean writing that column with values that do not exist. Per-turn preserves the trajectory record that makes an attempt replayable.

Two robustness rules

  • A case can never be cut short by confidence. CONFIDENCE_REACHED requires ≥ 85 items and every case sits inside the first 85, so only a 4-hour timeout can land mid-block — acceptable, since the answered children have already contributed their half-weight evidence.
  • A missing case degrades to a standalone pick. If no eligible unseen case exists, the schedule slot silently falls through rather than stalling the exam.

Verified by driving real exams, including a full-length one

  • 60-turn drive: cases landed at exactly the scheduled 18 / 31 / 58, each running six consecutive children in correct CJMM order (Recognise cues → Analyse cues → Prioritise → Generate solutions → Take action → Evaluate outcomes), cat_weight 0.5 throughout, three distinct cases with three snapshots, and standalone selection resuming cleanly after each block. Schedule proven deterministic.
  • Full-length drive: 150 items — the pool sustains a max-length exam (the §19.4 Slice 4 pool sanity check). Exactly 3 cases. One trend item served with its dataset snapshot written, proving the trend branch live.
  • The evidence maths, confirmed end to end: 150 items administered, 141.0 total weight — the 18 case items carrying 9 questions' worth, exactly as §7.4 designs.

Note on the trend path: it took a full-length exam to observe one. Trend-linked items are ~6.6% of a difficulty rung and sit in only 2 of the 4 Client Needs categories, so the balanced category rotation (§8.1) makes them genuinely rare per pick. This was checked to be thin probability rather than a bug. If trends should appear more often, the lever is authoring more trend datasets across more categories, not weakening the category tiebreaker.

Slice 6 runner survey — what is already free, and what is not

Surveyed 2026-07-19 so Slice 6 is scoped from fact rather than assumption.

Reusable unchanged: the 9 question renderers · the option shuffle (already observed firing on a CAT snapshot) · the four-table snapshot loader with its answer-key sealing · the timer · save-on-tap · the case-exit warning gate. And no back-navigation comes free: getArchetype() already maps CAT → SEQUENTIAL, which blocks it — a defensive default left in place months ago ("create-attempt rejects CAT mode until slice 3.x, and Sequential is the closest defensive default") that turns out to be exactly right.

What genuinely does not work: the runner is built around a fixed array. It loads data.items upfront and sets total = data.items.length, navigating by index. A CAT's array holds ONE item at the start and grows by one per turn, so it would render "Question 1 of 1", then "2 of 2". Two pieces follow:

  • Progress display — current-question-only, already specified by §16.1, so a spec'd change rather than a surprise.
  • The fetch-next loop — submit, ask the server for the next question, append it, advance. Every other mode knows all its questions in advance, so this mechanism does not exist anywhere yet. It is the real work in Slice 6.

Revised sizing: smaller than the slice list implies on rendering (all the hard question-display work is free), but with one genuinely new mechanism. Net neutral rather than a saving — and contained: a new mode branch in the runner, not a rewrite.

19.4.4 Slice 6a / 6b — decisions, bugs found on screen, and the first full CAT settled 2026-07-19

Slice 6 was split into 6a (CAT home + preflight), 6b (the turn loop) and 6c (transition escalation) so the risky middle piece could be tested alone. 6a and 6b are built; 6c remains.

Bugs found by looking at the screen, not by review

Every one of these passed tsc, eslint and the test suite first.

  1. The preflight's confirm button was above the cancel on mobile. column-reverse put "Start my CAT" — irreversible, spends the attempt, starts a 4-hour clock — as a full-width red button exactly where the thumb lands after reading. Now stacks in DOM order: the safe option is met first.
  2. Backdrop click did nothing, though CLAUDE.md UI #2 requires it to map to the safe option. Now dismisses, and is ignored while a start is in flight.
  3. "No questions in this attempt." flashed between questions. The stub meant for a broken attempt, shown mid-exam. Cause: current was stored state and the turn handler advanced it before the new question arrived, so for one round-trip the index pointed past the end of the array. ~100ms on localhost; a second or more on mobile data, which is the audience. Fix in §19.4.4 below.
  4. The footer told CAT students the wrong thing — "pick an option, Submit to see the rationale, then Next →". There is no rationale mid-exam and no Next button; it described controls that do not exist.

The derive-don't-store fix (and why it was the right shape)

For CAT the current index is now derived from items.length - 1, never stored. There is no navigation, so "which question am I on" was always a computed value — storing it is what let it drift. Scoped to CAT deliberately: every other mode needs the stored index for Prev/Next and grid clicks.

It also delivers §10.1 for free: during the wait the index still points at the last item of the old array, so the answered question stays on screen rather than vanishing — which is exactly the specced "current question stays visible."

The dim was mis-filed, and moved back

The dim and disabled inputs were originally put in 6c as "polish." That was wrong: §10.1 describes one behaviour — "stays visible during the wait (dimmed, inputs disabled)" — so shipping half of it and deferring the rest left the fix incomplete. Disabled inputs is not polish either; without it a student can click options on a question already submitted and scored, with nothing explaining why nothing happens. inert does the disabling, not pointer-events, which leaves controls keyboard-reachable. Only the timed escalation (spinner 300ms / "Still loading…" 3s / Retry 10s) genuinely belongs in 6c — it needs timers and an error path.

Turn idempotency — and an overload trap

cat_next_item assumed the newest item is always the one being answered. False on a retry: if the server commits and the response is lost, the newest item is by then the NEW question, and the old answer would be recorded against it — marking a student on a question they never saw. Over 150 turns on flaky connections that will happen. The caller now passes p_expected_item_id; if it is no longer newest the RPC replays instead of advancing.

Trap worth remembering: adding a DEFAULTed parameter creates a new overload rather than replacing the function. The database briefly held three cat_next_item signatures, which would have made 8-argument calls ambiguous. The stale 6-arg stub and 8-arg body were dropped; exactly one signature remains.

Sam sat a full exam in the browser on 2026-07-19. It is the end-to-end proof the engine had not previously had.
