Why this doc exists

Sub-plan for the CAT (Computer Adaptive Testing) mode — the adaptive, IRT-driven runner that simulates the real NCLEX exam. CAT is in scope for v1 per parent doc bank-consumption.html §16.

Splits off because CAT is structurally different from every other mode in MyNclex: it has no upfront question list, items arrive one at a time from an ability estimator, the test terminates on confidence rather than count, the result is a verdict (not a score), and the runner UX has to handle "we don't know how many questions you'll answer." None of those shapes fit cleanly inside the fixed-length attempt-creation and runner sub-plans.

This doc is mostly a skeleton at creation time. Each section below has a placeholder describing what it covers; content fills in as planning conversations land. Status pills: settled = decision locked, open = decision identified, not yet made, skeleton = section defined, content not yet started, deferred = own planning topic later.

3. v1 honesty constraints settled

Three constraints commit us to honesty about what we can and can't deliver. Settled 2026-05-04.

3.1 Calibration approximation — disclosed via help page, not per-attempt

Day-one difficulty values are curator labels mapped to numbers. Until empirical recalibration kicks in (§5.3), our "Hard" item is a reasoned guess, not a measurement. We're honest about that — but we tell the student once, in a help page, not on every CAT result.

Three options were considered:

  • Don't expose it — UWorld and Archer don't tell students about their calibration internals. Black box. Rejected: dishonest by omission for a product whose Promise is "practise on the real thing" with Pillar 4 being honest feedback.
  • Per-attempt caveat — small note on every CAT summary page reminding the student that calibration is approximate. Rejected: undermines the verdict every time, makes us look unconfident in our own product, probably confuses more than it informs.
  • One-time help page (chosen). Honest, but not pestering. Students can know if they want to.

4. IRT model choice settled

Rasch (1PL) for v1. Implemented in TypeScript inside the existing stack (Cloudflare Workers / Supabase edge). Settled 2026-05-04.

4.1 Why Rasch and not 2PL

Rasch uses one parameter per item: difficulty. 2PL adds a second parameter, discrimination — "how well does this question separate strong students from weak students." Discrimination can only be calculated from real student response patterns. Day one, all we have is the curator's Easy / Medium / Hard label, which gives us a difficulty proxy but says nothing about discrimination. Picking 2PL on day one would force us to assign a fake discrimination value (probably 1.0 = "average") to every question — which is mathematically equivalent to just using Rasch.

Rasch is also the simplest, most studied, most stable IRT model. Easier to implement, easier to debug, easier to explain to ourselves and others.

4.2 Live engine implementation

TypeScript implementation in our existing stack. Our backend is Supabase Edge Functions and Cloudflare Workers — neither runs Python natively. Two paths were considered:

  • Path A — Python service. Spin up a small Python service running a library like catsim or pyirt. CAT RPCs call it for ability estimation and item selection. Adds one moving piece to the stack (deployment, monitoring, latency).
  • Path B — TypeScript Rasch directly. Re-implement the core Rasch math in TypeScript. The math is small (~30 lines for ability estimation, less for selection). No new infrastructure.

Path B chosen. Rasch math is well-documented and one-time work. Adding a Python service for what is fundamentally a small calculation introduces deployment complexity, latency, and error surfaces for little benefit.

4.3 Empirical recalibration uses heavier tooling — separate concern

The live CAT engine is the small Rasch implementation in TypeScript. Empirical recalibration (§5.2) is a different beast — fitting Rasch parameters to a corpus of student responses is a heavier statistical job, and that's the place where Python tooling (pyirt or similar) makes sense. The recalibration job is offline, periodic, batch — not in the live CAT path. See §17 for the audit pipeline.

4.4 2PL upgrade — when

Once empirical recalibration has been running for some time and we have substantial response data per item, we can revisit fitting 2PL parameters. v2 decision, driven by data — not a v1 commitment.

5. Difficulty calibration plan settled

How we get from curator-assigned Easy / Medium / Hard labels to numeric IRT difficulty values, and how we improve those values over time as student response data accumulates. Settled 2026-05-04.

5.1 Day-one mapping — curator label → numeric proxy

Three numeric values on the IRT logit scale, where 0 = average ability:

Curator labelRasch difficultyPlain-English meaning
Easy−1.0A 50/50 student gets this right ~73% of the time.
Medium0.0A 50/50 student gets this right ~50% of the time.
Hard+1.0A 50/50 student gets this right ~27% of the time.

The middle three values on the standard IRT logit scale. Wide enough that the three labels are meaningfully different (the engine picks differently for a Medium-leaning student vs a Hard-leaning student); tight enough that no question is treated as extreme.

5.2 Where the numeric value lives — schema decision

The existing nclex_bank_items.difficulty column is a TEXT column with a CHECK constraint that restricts values to 'Easy' / 'Medium' / 'Hard'. It cannot hold a number like 0.34 — that would violate the constraint. So the numeric value the CAT engine reads must live in a separate column.

Add a new column: difficulty_irt (NUMERIC). The text column stays exactly as it is; the numeric column lives in parallel.

Column on nclex_bank_itemsTypePurposeSource
difficulty (existing, unchanged) TEXT Curator's label — displayed in admin UI, edited by curator Curator selects on save
difficulty_irt (new) NUMERIC The number the CAT engine reads for selection Initialised from difficulty via the §5.1 mapping; updated by the recalibration job
difficulty_source (new) TEXT Provenance flag for difficulty_irt 'CURATOR_LABEL' on insert; flipped to 'EMPIRICAL' by the recalibration job once the threshold is crossed

Rules of access:

  • Curator UI never touches difficulty_irt. The curator picks Easy / Medium / Hard; the system writes the corresponding number to difficulty_irt automatically on save.
  • CAT engine never touches difficulty. It reads difficulty_irt only.
  • Recalibration job writes only to difficulty_irt and difficulty_source. Never touches the curator's label.
  • This preserves the curator's original judgement as a stable field. Once recalibration runs, we can still see "this question was originally labelled Hard, but the data shows it's actually Medium-difficulty" by comparing the two columns.

5.3 Empirical recalibration trigger

When does an item's difficulty_irt get recomputed from response data instead of staying at its curator-derived starting value?

5.3.1 Threshold — 30 responses per item

An item must have accumulated at least 30 student responses before its difficulty_irt can be recalibrated empirically. Below that, the empirical estimate is too noisy — one strong student getting an item wrong (or one weak student guessing right) can swing the difficulty value too far. 30 is the standard industry rule-of-thumb floor; above it, the estimate stabilises meaningfully.

5.3.2 Cadence — weekly batch (v1)

Recalibration runs once a week — Sundays at 02:00 UTC (low-traffic window). Plus a manual trigger button in the curator dashboard for testing and edge cases.

Why weekly, not nightly:

  • Early on, response volume per item is low. A given item might get 3–5 responses per day. Nightly mostly produces no-op recalculations.
  • Empirical estimates are more stable when computed on a larger window of responses.
  • Weekly is operationally simpler — one scheduled run, easier to monitor.
  • Matches the reality that early-stage recalibration is provisional anyway.

Revisit cadence when the platform has enough volume that items routinely accumulate 20+ new responses between weekly runs. At that point, switch to nightly. v2 decision, data-driven.

5.3.3 Transition smoothing — 70/30 dampened blend

When the recalibration job produces a new value for an item, the new difficulty_irt is a weighted blend of the previous value and the freshly computed one — 70% new, 30% previous. So if an item was at difficulty 0.0 last week and the new empirical estimate is 0.7, the stored value becomes 0.49 (≈ 0.7 × 0.7 + 0.0 × 0.3).

Why dampen. Without smoothing, an item's difficulty can lurch between weekly runs in ways that make consecutive CATs feel arbitrary. A student who took CAT #1 with this item at difficulty 0.0 and CAT #2 with the same item suddenly at 0.7 is exposed to large psychometric shifts mid-prep that have nothing to do with their own ability. Dampening keeps the trajectory smooth across recalibration cycles.

The blend converges to the empirical value over multiple weekly runs — fast enough that calibration moves the needle within a month or two of accumulating data, slow enough that no single week's noise dominates.

5.3.4 First crossover — special case

When an item crosses the 30-response threshold for the first time, difficulty_source flips from 'CURATOR_LABEL' to 'EMPIRICAL'. The 70/30 blend still applies — the previous value is the curator-derived starting number, the new value is the first empirical estimate.

5.4 Confidence display

Each item's difficulty_source column tells the curator dashboard whether the value is curator- derived or empirically calibrated. The dashboard can show: "X% of bank items are now empirically calibrated" and per-item flags. Admin/curator-side only for v1; not surfaced student-facing.

6. Starting-difficulty rule settled

Every CAT starts at theta = 0.0 (Medium), with high SE, for every student, every time. First question served = Medium. Settled 2026-05-04.

Why fixed, not personalised: a returning student who's done 3 prior CATs has a known prior theta — but starting CAT #4 at that prior estimate would bias the test toward confirming the prior result. The engine would spend fewer questions exploring whether the student has actually changed since CAT #3, and more questions confirming what it already thought. That's bad measurement. Real NCLEX doesn't do this; every candidate starts at medium every time. We mirror that.

What we DO use prior CAT data for: History / Analytics. The student sees their CAT trajectory across attempts ("you went from theta 0.5 → 0.7 → 0.65"). That's useful information. It just doesn't seed the next CAT's starting position.

7. Item selection strategy settled

Given the current ability estimate, the eligibility filters, and the bank pool — how does the engine pick the next item? Settled 2026-05-04.

7.1 The selection rule

Pick the unseen question whose difficulty is closest to the student's current ability, with category as a tiebreaker among equally-good difficulty matches.

The engine, on each pick:

  1. Calculates the student's current ability estimate (theta).
  2. Finds the set of unseen, eligible questions within a small difficulty tolerance (provisional: ±0.1) of theta.
  3. Within that set, checks if any are in an under-represented Client Needs Category (running count of categories so far in this attempt).
  4. If yes → picks one at random from the under-represented-category subset.
  5. If no under-represented matches → picks any from the difficulty-tolerance set at random.

The engine never goes outside the difficulty tolerance to find an under-represented question. Difficulty match is sacred. Category is a thoughtful tiebreaker only.

7.2 Why this rule (and why not stronger category enforcement)

Three options were considered: (A) pure difficulty match (soft category), (B) hard category enforcement that overrides difficulty when needed, (D) a per-category floor with late-test override. All three were rejected in favour of the locked rule (option E in the planning conversation):

  • A (pure difficulty) — sound on measurement but no protection against severely lopsided category mixes when the bank itself is unbalanced.
  • B (hard enforcement) — overriding difficulty for category degrades the engine's measurement accuracy, can break entirely on a small bank when no question exists at the right difficulty in the under-represented category, and hides bank-balance signals that should be addressed by curation, not engine compensation.
  • D (floor with override) — better than B but still pays measurement cost when the floor activates late in the test, and adds engine complexity (running floor checks, fallback logic).
  • E (tiebreaker) — costs nothing in measurement quality (engine never picks a wrong-difficulty question), gives the engine a small natural lean toward balance when free choices exist, doesn't pretend to enforce what the bank can't deliver.

7.3 Eligibility filters

The next item must be:

  • Not already administered in this attempt (no within-attempt repeats).
  • Not seen in the student's last 3 CAT attempts (cross-CAT exposure window — settled in §15.2).
  • is_published = TRUE.
  • is_builder_visible = TRUE (keeps readiness-pack reserved questions out of CAT, same rule as everywhere else).
  • Standalone questions AND wrappers (case studies, trend-linked) are both eligible — direction reversed 2026-07-14; wrapper administration mechanics are open build decisions (see §7.4).

7.4 Cases and trends in CAT — INCLUDED in v1 mechanics open

Direction reversed 2026-07-14 (Sam). Wrappers — case studies and trend-linked questions — are IN scope for v1 CAT. Real NCLEX includes case studies in its adaptive exam, and MyNclex's promise is "practise on the real thing"; a CAT that never serves a wrapper is not the real thing. The original standalone-only default (settled 2026-05-04) is superseded.

The original deferral reasons stand as costs we're accepting, not as reasons to wait — recorded here so the build slice designs around them deliberately:

  • Case-study children aren't psychometrically independent — the 6 questions correlate heavily because they're built on the same scenario, which strains IRT's local-independence assumption. (UWorld/Archer-class products accept the same compromise.)
  • A case study delivers as an atomic ~6-question block, which locks the engine out of item-by-item difficulty adaptation for the duration of the block.
  • Trend-linked questions carry shared dataset context that has to travel with them into the adaptive sequence.

Open build mechanics — settle when the CAT slice is built, not before:

  • Block administration rule — when the engine picks a case, it commits to the whole wrapper as an atomic block, then resumes item-level adaptive selection after the block. Exact rule for when a case is pickable (theta band? cadence? max cases per attempt?) is undecided.
  • Theta updates inside a block — update per child answer, or once at end-of-block (dampened for the correlation)? Undecided.
  • Wrapper difficulty — a case needs an effective difficulty for selection (children's mean? curator label on the wrapper?). Undecided.
  • Exposure rules for wrappers — the last-3-CATs window (§15.2) should apply at wrapper level (seeing the same scenario again is the leak, not the individual child). To confirm.

§11's snapshot design already anticipated this: case/trend snapshot behaviour for CAT is specified there and needs no rework — only activation.

7.5 Bank-exhaustion fallback

Edge case: student is at ability 0.5, the engine wants a question at difficulty ~0.5, all candidates have been seen in their last 3 CATs.

Rule: relax exposure before relaxing difficulty.

  1. First try: unseen questions within difficulty tolerance, not seen in last 3 CATs → ideal pick.
  2. If empty: questions within difficulty tolerance, even if seen in last 3 CATs → fall back to allowing repeat.
  3. Never: serve a wrong-difficulty question to avoid a repeat.

Fallbacks are logged so the curator dashboard can flag "X% of CAT picks fell back to repeats — bank may be too small or too thinly distributed at this difficulty band."

7.6 Day-one effective behaviour with curator-labelled difficulty

Until empirical calibration kicks in (§5.2), the bank only has three difficulty values: −1 (Easy), 0 (Medium), +1 (Hard). The student's ability is continuous (could be 0.1, 0.34, −0.62, anything), but every question sits at one of three values. So the rule effectively becomes:

Student abilityQuestion served
Below −0.5Easy
−0.5 to +0.5Medium
Above +0.5Hard

Coarse, but the math handles it — Rasch doesn't need a question at exactly the student's ability, just questions in roughly the right region. As empirical calibration matures and each question gets its own specific difficulty, the engine gets finer-grained choices automatically.

8. Content-blueprint constraints settled

Real NCLEX enforces a content blueprint — minimum percentages of each Client Needs Category in the test the candidate sees. The question for us was how strictly to enforce the same. Settled 2026-05-04.

NCLEX-RN's official blueprint (approximate, as of 2023 NGN test plan), for reference:

8.1 The rule

Category influences selection only as a tiebreaker among equally-good difficulty matches — see §7.1 for the full mechanic.

When the engine is choosing between two unseen questions both within the difficulty tolerance of the student's current ability, it prefers the one in an under-represented category. When no equally-good difficulty match exists in an under-represented category, the engine picks by difficulty alone. Category never overrides difficulty; it just decides between equally-good options.

8.2 Why not stronger enforcement

Hard enforcement (forcing a pull from any under-represented category regardless of difficulty fit) was considered and rejected. Reasoning lives in §7.2 in full; the short version: hard enforcement degrades measurement quality, can break on a small bank when no question exists at the right difficulty in the under-represented category, and hides bank-balance signals that should be addressed by curating more questions, not by engine compensation.

8.3 Monitoring

Each CAT attempt logs the actual category distribution achieved. Specifically, per attempt we record:

  • Count of items delivered per category.
  • Percentage of items per category vs total delivered.
  • Gap vs the NCLEX blueprint targets.
  • Tiebreaker activation rate (how often the under-represented preference influenced a pick).

Aggregated across attempts, this surfaces in a curator dashboard as: average distribution across recent CATs, consistent gaps from blueprint, count of questions per category at each difficulty level. If a category is consistently underweight in delivered CATs, the fix is to curate more questions in that category, not to add engine enforcement. The dashboard itself is a separate piece of work; this section just specifies what gets logged so the dashboard has data to read.

8.4 Hard enforcement deferred to v2 — when

Revisit if monitoring shows the soft tiebreaker rule produces persistently lopsided category mixes that curation alone cannot fix. Specifically: if after curating to a balanced bank, we still see CATs delivering <3 items in a category 20%+ of the time, that's the signal to consider stronger enforcement. Until then, the tiebreaker rule + bank curation is the v1 answer.

9. Termination logic settled

Real NCLEX terminates a CAT under one of three conditions: (1) confidence reached, (2) max questions reached (150), (3) time limit reached. We mirror the same shape with our own thresholds. All four sub-decisions locked 2026-05-04; min/max counts corrected 2026-07-14 (see §9.2).

9.1 Confidence threshold

The engine terminates when both are true at the same time:

  • Standard error of the ability estimate ≤ 0.40. The margin of error has shrunk to the point where the engine is confident in the estimate.
  • Ability estimate is clearly above (or clearly below) the passing standard of theta = 0.0. "Clearly" means the SE band around the estimate doesn't cross zero. If the estimate is 0.5 and the SE is 0.40, the band is 0.1 to 0.9 — entirely above zero, confident pass. If the estimate is 0.2 and the SE is 0.40, the band is −0.2 to +0.6 — crosses zero, keep going.

Why theta = 0.0 as the passing standard: the real NCLEX standard is set by NCSBN's standard- setting committee from outcome data we don't have, so we can't copy them. theta = 0.0 means "measurably above average ability" — honest and defensible without outcome data. Once empirical calibration matures and we have student outcome data, we can revisit.

Why SE ≤ 0.40: standard CAT systems use 0.30–0.50. 0.40 sits in the middle — confident enough to give a meaningful verdict, loose enough that we don't push too many students to the 150 ceiling.

9.2 Min and max question counts

  • Min: 85. The engine cannot terminate before this even if SE converges fast.
  • Max: 150. The engine forces termination at this count regardless of SE.

Both match real NCLEX exactly. No reason to deviate — students practising for NCLEX should experience NCLEX's range.

Corrected 2026-07-14 (Sam): earlier drafts of this doc used 75/145 — the pre-NGN NCLEX-RN range. The NGN test plan (live since April 2023) uses 85 minimum / 150 maximum, and since our rationale is "match real NCLEX exactly," the numbers are corrected throughout this doc.

9.3 Time limit

4 hours. Real NCLEX gives 5; 4 hours is enough to feel real and build stamina, short enough not to be punishing for practice. Behaviour at time expiry: auto-terminate, score against current theta + SE, mark termination reason as TIME.

9.4 Termination reasons

Each terminated CAT records why it ended. Five values:

  • CONFIDENCE_PASS — SE ≤ 0.40 with theta clearly above 0.0. Verdict = ABOVE_STANDARD.
  • CONFIDENCE_FAIL — SE ≤ 0.40 with theta clearly below 0.0. Verdict = BELOW_STANDARD.
  • MAX_ITEMS_INCONCLUSIVE — 150 questions reached, SE still too wide for a confident verdict. Verdict = INCONCLUSIVE.
  • TIME — 4-hour time limit reached. Scored against current theta. Verdict follows the same rule as CONFIDENCE_* (above/below 0.0) if SE is acceptable, otherwise INCONCLUSIVE.
  • ABANDONED — student manually discarded mid-CAT, or browser-close. No verdict produced.

9.5 Inconclusive verdict — framing

When the verdict is INCONCLUSIVE, the engine asked 150 questions and still couldn't confidently call it. This isn't a fail and isn't a pass — it's "the data we got doesn't give a clear picture." Three honest causes:

  1. The student's ability is near the boundary. Sitting right around theta = 0.0. Most common cause.
  2. Inconsistent answering. Right on hard ones, wrong on easy ones — answers don't track ability, engine can't form a coherent estimate.
  3. Test-taking factors: rushing, fatigue, second-guessing, distracted environment.

Result-screen copy (provisional, finalised in §13): Headline "Inconclusive." Body: "After 150 questions, your performance didn't give us a clear above-or-below standard read. This usually means your ability is sitting right around the boundary, or your answers were inconsistent (mixing strong and weak performance). More practice will help — focus on the categories where you scored lowest, then try another CAT in a few days."

What we deliberately do NOT say: not "you failed" (no grounds), not "you might pass" (no grounds), not "the engine couldn't decide" framed as the engine's failure (sounds like a product bug — the honest framing is the student's performance was on the boundary).

For Inconclusive verdicts, the per-Client-Needs-Category breakdown does most of the work — when the verdict itself is unclear, the breakdown is what gives the student something actionable.

Readiness Signal weighting: INCONCLUSIVE verdicts weight as zero (no evidence either way), not as a fail. Captured here for §13.3 when we get there.

10. Architecture — the two-RPC flow settled

Per attempt-creation §13 (already settled): CAT does not use the same create-attempt RPC as fixed-length modes. Two RPCs instead. Settled 2026-05-05.

10.1 Transition pattern between questions

Pessimistic UI with graceful degradation. The current question stays visible during the wait (dimmed, inputs disabled) — psychologically faster than a blank loading screen even when the wait is identical. Specifically:

  • 0–300ms after Submit: current question stays visible, inputs disabled, very subtle fade or shimmer on the question area. No spinner. This is the happy path and will be the experience the vast majority of the time.
  • 300ms–3s: spinner appears in the question area, current question still dimmed underneath.
  • 3s+: "Still loading..." text appears next to the spinner.
  • 10s+: error state with a "Retry" button.

Rationale: pessimistic is the only honest choice for CAT — the engine genuinely has to score before picking the next item, so there's nothing real to optimistically render. Optimistic UI in this context would mean faking content we don't yet have.

10.2 The two RPCs and what each one does

create_cat_attempt(student_id, intent='EXAM', mode='CAT'):

  • Inserts a row into nclex_attempts with starting theta = 0.0, SE at the initial high value, status = IN_PROGRESS.
  • Picks the first item using §7 selection rules (closest to theta = 0.0, category as tiebreaker, eligibility filters).
  • Snapshots the picked item into nclex_attempt_items with cat_theta_before = 0.0 and cat_se_before = <initial>.
  • Returns { attempt_id, first_item_payload }.

cat_next_item(attempt_id, last_answer_payload):

  • Scores the last answer using the existing per-question scoring functions (reused unchanged from bank-marks-and-scoring.html).
  • Writes the answer into nclex_attempt_answers.
  • Updates theta and SE using Rasch (1PL) update math per §4.
  • Checks termination conditions per §9: if SE ≤ 0.40 and items ≥ 85, OR items = 150, OR time ≥ 4 hours → terminate, write cat_verdict, cat_final_theta, cat_final_se, cat_termination_reason, cat_items_administered, return { status: 'COMPLETE', verdict_payload }.
  • Otherwise: pick next item per §7, snapshot into nclex_attempt_items with the pre-update theta/SE captured in cat_theta_before/cat_se_before, return { status: 'CONTINUE', next_item_payload }.

Both RPCs are atomic — score + theta update + select + snapshot run in a single transaction. If anything fails, nothing partial gets written.

10.3 Error handling

  • Network failure on the browser side: browser auto-retries silently up to 2 times with exponential backoff (1s, 2s) before showing the error UI.
  • RPC throws a server-side error: browser shows the error UI immediately, no auto-retry (the problem isn't transient).
  • The attempt row is never left in a half-updated state because the RPC is transactional — either the answer is recorded and the next item is snapshotted, or neither happens.
  • If the student gives up after the error UI appears: they can close the browser → status becomes ABANDONED per §16.

10.4 Why these specific numbers

  • 300ms / 3s / 10s thresholds sourced from standard UX latency research: under ~400ms feels instantaneous, 1–3s feels like a brief wait, 3s+ requires reassurance, 10s+ requires acknowledgement that something is wrong.
  • 2-retry cap is conservative — fewer than 3 to avoid masking a real outage as a long wait, more than 0 to handle transient Wi-Fi blips.

10.5 Build-time deferrals (not blocking the plan)

  • Exact NUMERIC precision on theta/SE columns (lives in §12 polish, not §10).
  • Engine runtime location — Supabase RPC (PL/pgSQL) vs Edge Function vs Cloudflare Worker. Recommendation: Supabase RPC for v1 because it keeps the transaction atomic and avoids a network hop between scoring, theta update, and item selection. Confirm at build time when we can measure actual Rasch math performance in PL/pgSQL.
  • Exact wording of the error UI ("Connection lost" / "Couldn't load next question" / etc.).

11. Snapshot strategy for CAT settled

Per-question snapshot at administration time, identical to the fixed-length snapshot strategy.

Specifically:

  • Each time create_cat_attempt or cat_next_item picks an item, it inserts a row into nclex_attempt_items with the full snapshot — stem, instruction, content JSONB, correct JSONB, rationale, classification, marks. Same column shape as fixed-length attempts.
  • If the item is trend-linked, the linked dataset is snapshotted into nclex_attempt_trend_snapshots (if not already there for this attempt) at the moment the trend item is picked.
  • If the item is a case-study child (active — §7.4 settled "include cases" on 2026-07-14), the case is snapshotted into nclex_attempt_case_snapshots at the moment the first child is picked, and all 6 children get queued.

11.1 Why snapshot, restated for CAT context

Three reasons settled in the seed conversation:

  1. Integrity. CAT exams take 85–150 questions. The window during which a curator might edit a question while the student is mid-exam is bigger than for any other mode. CAT's whole legitimacy depends on the ability estimate being a coherent measurement against a fixed answer key — if question 47's correct JSONB changes between when the student answered it and when the engine reads it, the entire ability trajectory is corrupt.
  2. Review depends on it. Review state (§14) renders rationales for the questions the student saw. Without snapshots, by the time the student opens Review, those rationales might have been edited or deleted. Snapshots are how Review survives curator changes.
  3. Calibration depends on it. Empirical recalibration (§5) needs to know what the item actually said when the student answered it. If a curator rewrote the stem after the student answered, the response data isn't a valid signal about the new stem's difficulty.

11.2 Why NOT alternative approaches

Two alternatives were considered and rejected in the seed conversation:

  • "Pull from live tables, just record IDs" — fails all three reasons above. Doesn't actually save anything because per-question snapshotting is already cheap.
  • "Snapshot at end-of-session, not per-question" — captures the wrong thing. State at end-of-session is not state at administration. If the curator edits item 12 after the student answered Q12 but before exam end, the end-of-session snapshot captures the edited version. Worse than skipping snapshots, not better.

11.3 Cost

A typical CAT exam administers ~85 items. Each nclex_attempt_items row carries the snapshot payload (stem, content, correct, classification — already shaped). Per-attempt snapshot storage cost is roughly the same order as a 75-item fixed-length quiz. Negligible.

13. Result presentation — the CAT summary page settled

What the student sees when a CAT exam ends, and what they see when they open a finished CAT from History. Settled 2026-05-04. Same surface used in both contexts: the CAT summary page. Per the §14 separation, this page holds everything CAT-specific; the per-question Review walk-through reuses the shared runner Review surface used by every other quiz type.

13.1 Verdict copy

ABOVE_STANDARD

  • Headline: "Above standard"
  • Body: "Your performance suggests you're tracking ready. Keep practising to maintain it — consistent CAT performance is what matters most."

BELOW_STANDARD

  • Headline: "Below standard"
  • Body: "More practice recommended. Use the category breakdown below to see where to focus, then come back for another CAT in a few days."

INCONCLUSIVE (also drafted in §9.5)

  • Headline: "Inconclusive"
  • Body: "After 150 questions, your performance didn't give us a clear above-or-below standard read. This usually means your ability is sitting right around the boundary, or your answers were inconsistent. More practice will help — focus on the categories where you scored lowest, then try another CAT in a few days."

ABANDONED (no verdict)

  • Per §16.5 — abandoned CATs never reach a result state. The History page shows them as "CAT — Abandoned"; opening the row goes to a minimal summary that explains the attempt was ended early and offers "Start a new CAT".

13.2 Summary page layout

In order from most prominent to least:

  1. The verdict itself — top of page, large headline + body copy from §13.1.
  2. Items administered — small fact line under the verdict. Example: "You answered 92 questions. The engine reached confidence at question 92." Honest, factual.
  3. Trajectory graph (see §13.3 below) — the most important visual on the page. Shows how the student's ability estimate moved across the test, plotted against a 0.0 reference line.
  4. Per-Client-Needs-Category breakdown — for each of the four categories: questions seen, questions correct (full credit only — see bank-marks-and-scoring.html §6 for the is_correct definition), per-category percentage. The most actionable text content on the page.
  5. Compared to your previous CATs — only shown if the student has prior CATs. Plots theta + verdict per CAT across attempt history.
  6. Primary CTA: "Review answers" — opens the shared runner Review surface (per §14) for the per-question walk-through.

13.3 The trajectory graph + per-item marker

Single line chart. X-axis = question number (1 → N items administered). Y-axis = theta (ability estimate after that question's answer). A horizontal reference line is drawn at theta = 0.0 (the passing standard).

What the shape tells the student:

  • Steady upward trace settling above 0.0 — consistent strong performance, ability climbed and stabilised above the passing standard.
  • Steady downward trace settling below 0.0 — consistent weak performance, ability climbed down and stabilised below the passing standard.
  • Up-and-down trace not settling — inconsistent answering, the engine couldn't pin down their ability cleanly. Often what produces an INCONCLUSIVE verdict.

Per-item marker. If the summary page renders a per-question breakdown alongside the graph (e.g. a scrollable list of the questions they answered), the trajectory graph shows a marker indicating which question is currently focused. As the student scrolls or clicks a different question, the marker on the trajectory updates. This lets the student see, for any individual question they answered: where on the ability curve was I when this question was served?

What this replaces. An earlier draft proposed a per-item "At your level / Above your level / Below your level" chip. The trajectory + marker delivers the same context more richly — the student can see not just whether one question was at their level, but how their level was moving over time.

13.4 Connection to Readiness Signal

CAT verdict and Readiness Signal stay separate on the dashboard — they are NOT blended into a single number.

The dashboard surfaces two distinct cards:

  • CAT card. Shows the latest CAT verdict, a count of CATs taken, the date of the last CAT, and a link to that summary page. Copy: "Latest CAT verdict: Above standard. (CAT #3 of 3 taken)".
  • Readiness Signal card. Cross-history practice signal per parent bank-consumption.html §6. Independent of CAT.

Why separate, not blended:

  • Combining them forces a weighting algorithm we cannot validate without outcome data.
  • Students should see CAT as one snapshot, Readiness as the longer-term cross-history signal. Different products, different cards.
  • If a student takes one CAT, gets ABOVE_STANDARD, and the Readiness Signal still says "Approaching," the honest framing is "one CAT is one data point; cross-history sees more." Two cards make this conversation possible.

INCONCLUSIVE verdicts weight as zero in any future blended analytics — they're "no signal," not "negative signal." If a future v2 decision blends signals, INCONCLUSIVE never pushes the Readiness Signal down.

13.5 What we deliberately do NOT show

  • No "pass probability" number. No "70% chance of passing the NCLEX." We don't have outcome data to back that.
  • No "you would have passed the real NCLEX" framing. Same reason.
  • No comparison to other students' verdicts. Different students see different questions; comparison is meaningless.
  • No raw score. CAT has no raw score by design — it has a verdict + theta + SE.
  • No "you got X out of N right." Same reason.
  • No verdict restatement on the per-question Review. Verdict lives on the summary page only — Review is about the questions, not the outcome.

It's a per-question walk-through with stem, the student's answer, the correct answer, rationale, per-option/per-element feedback, and classification tags. It's universal — every quiz type's review goes through the same component. CAT inherits it unchanged.

The flow:

  • End of a CAT (or History → click a CAT row) → CAT summary page (§13)
  • Summary page → "Review answers" CTA → shared Review surface in the runner (this section)

14.2 What CAT inherits unchanged from the shared Review

  • Per-question rendering — the 9 question-type renderers used by the live runner, in mode = "review" (per bank-consumption-runner.html §18).
  • Navigation surface = the question grid (per bank-consumption-runner.html §16). Every finished attempt shows the grid in review regardless of which mode ran, so CAT inherits it identically. Cells carry post-submit fill states (right / wrong / skipped) and the marked / current overlays per §16.4.
  • List + detail layout — grid as the list (right-edge sticky panel desktop, full-screen bottom sheet mobile), main pane shows the focused item. Same pattern as fixed-length review.
  • Filter toggles — All / Marked / Unanswered / Wrong per §16.3. (Earlier wording mentioned "Right only / By category" — those finer filters are not in v1; the v1 surface is the four toggles plus the question-grid cells. By-category drill-down lives on the analytics page, not in review navigation.)
  • Mark-for-review toggle — student can mark items in Review for later study. The mark is universal across the platform — marked items from CAT mix with marked items from any other quiz type in the personal study list.

14.3 Entry points

  • From the CAT summary page — primary CTA "Review answers."
  • From History → click a CAT row → opens the CAT summary page → "Review answers."

Note: the History row links to the summary page, not directly to Review. Review is a sub-action of the summary page, not a top-level entry point of its own.

14.4 What's deliberately NOT in this section

Difficulty annotation framing, the trajectory chart, per-item difficulty markers, verdict copy, the "Compare to your previous CATs" panel — all of these are summary-page concerns, covered in §13. They are not part of the per-question Review.

15. Re-take rules settled

How often can a student take CAT? What about question exposure across CATs? Does prior CAT data influence the next CAT's selection? Settled 2026-05-04.

15.1 Frequency

Unlimited re-takes within the student's active subscription window. Matches industry standard — UWorld and Archer both offer unlimited CAT practice. Students under exam pressure want to drill; capping hurts the learning. The engine doesn't degrade with repeated use, so there's no technical cost.

No hard cooldown. The student can start another CAT immediately after finishing one. A soft warning appears if a student starts a CAT within 1 hour of finishing one: "CAT works best with rest between sessions — continue anyway?" Soft nudge only; not a block.

15.2 Question exposure across CATs

Exclude questions seen in the student's last 3 CAT attempts. Cross-CAT exposure window only — questions seen in non-CAT modes (Custom builder, Readiness Packs, Programme assignments) do not contribute to the exclusion list.

Why "last 3 CATs":

  • Forever exclusion is too strict for a young bank. A student doing 6 CATs in their final exam prep would burn through the strongest difficulty-matched questions; by CAT #4 the engine would be picking from increasingly thin pools.
  • No exclusion is too lax. Memory effects are real — if a student saw a question 3 days ago in CAT #1, they might remember the answer in CAT #2 and contaminate the engine's measurement.
  • Last 3 CATs is roughly 2–3 weeks of practice for a typical student, which is enough time for memory of a specific question to fade for most.

Why CAT-only (not other modes):

  • CAT and non-CAT are different contexts — a student who did Q47 in a Pharmacology custom quiz two months ago can still see it in CAT today without strong memory contamination.
  • If we excluded all non-CAT exposure too, the eligible pool for CAT would collapse for any student who's used the platform for a while.
  • Only cross-CAT exposure represents the same psychometric context (timed exam-style adaptive sequence) where memory effects materially degrade measurement.

15.3 Bank-exhaustion fallback

Edge case: student is at ability 0.5, engine wants a Medium-to-Hard question, all of those at the right difficulty have been seen in their last 3 CATs.

Rule: relax the exposure rule before relaxing the difficulty rule.

  1. First try: unseen Medium-to-Hard not seen in last 3 CATs → ideal pick.
  2. If empty: Medium-to-Hard seen in last 3 CATs → fall back to allowing repeat.
  3. Never: serve a wrong-difficulty question to avoid a repeat.

Difficulty match is sacred (§7). Exposure is a soft preference, so it's the one that bends. Fallbacks are logged so the curator dashboard can flag "X% of CAT picks fell back to repeats — bank may be too small or too thinly distributed at this difficulty band."

15.4 Theta carry-over — none

Each CAT starts at theta = 0.0 regardless of the student's prior CATs. Already settled in §6. Cross-CAT theta IS shown in History / Analytics ("your last 3 CATs landed at theta 0.5, 0.6, 0.65 — improving") but doesn't seed the next CAT's starting position.

16. Runner UX specifics settled

Where the CAT runner deliberately diverges from the fixed-length runner. Settled 2026-05-04.

16.1 Progress indicator — current question only

Show only the current question number (e.g. "Question 27"), no "of N" cap. CAT can't show a count target because the terminating question count is unknown. Students familiar with CAT know the test terminates at 85–150; we don't need to engineer a "Q5 of 85 minimum" display to communicate that.

The runner's existing progress bar (used for fixed-length modes) renders differently in CAT mode: it shows what the student has answered so far, not progress toward a known total. Equivalent of a count-up timer rather than a count-down progress fraction.

16.2 Timer display + warnings — runner-level concern

CAT is timed at 4 hours (§9.3). Display, warning thresholds, and expiry behaviour are not CAT-specific — they apply to every timed mode (Timed Free Nav, Timed Sequential, CAT). Settled at the runner doc level (bank-consumption-runner.html §8) when timer behaviour is decided cross-mode. CAT inherits whatever the runner doc lands on.

Already settled at principle (§9.3): at expiry, auto-terminate, score against current theta + SE, mark termination reason as TIME.

16.3 No back navigation — strictly sequential

Once a CAT answer is submitted, the student cannot return to the question. Same shape as the existing Timed Sequential mode in the fixed-length runner — no previous-question button, no answer re-edits.

Required by the engine's design as much as by the test feel: the IRT estimate updates after each answer; allowing answer changes mid-test would corrupt the trajectory. Matches real NCLEX exactly.

16.4 No mark-for-review during the live run

No flag button during the live CAT. Matches real NCLEX. The student answers, submits, moves on.

Mark-for-review IS available in the post-attempt shared Review surface (§14) — once the CAT is complete, the student can mark items for later study from inside the Review walk-through. The mark goes to the universal personal study list (mixed with marks from any other quiz type).

16.5 Browser-close mid-CAT — abandoned, no verdict

CAT is EXAM-intent and single-sitting by design (per parent §15 + §6 + §15.4). No Resume.

Behaviour:

  • Browser-tab-close attempt → custom warning prompt: "Closing this tab will abandon your CAT exam. Your progress will not be saved." Confirms before exit.
  • If confirmed → attempt status flips to ABANDONED, termination reason = ABANDONED, no verdict generated.
  • Accidental refresh → same warning, same outcome if confirmed.
  • History display → ABANDONED CATs show as "CAT — Abandoned" with no verdict. Opening the row goes to a minimal summary that explains the attempt was ended early and offers "Start a new CAT" (per §13.1 ABANDONED row).

16.6 No pause

Per parent §15: "CAT — IRT model needs continuous engagement; pause/resume invalidates the estimate." Already settled. No pause button. The 4-hour timer never stops. The session is start-to-finish.

Real-world breaks (bathroom, food, etc.) are the student's own choice; the timer keeps running. If the student needs a real break, they abandon and start a new CAT later. Matches real NCLEX (where breaks are permitted but the timer doesn't pause for them).

17. Calibration data capture settled

What gets logged for empirical recalibration to work, and how the audit history of difficulty changes is preserved. Settled 2026-05-04.

17.1 Per-attempt response data — already captured

Empirical recalibration needs to know, for every CAT response: which item, who answered, were they correct, what was the engine's ability estimate at the time. All of this is already captured by the schema we've locked elsewhere — no new columns needed for capture itself.

From §11 (snapshots) + §12.3 (CAT columns on nclex_attempt_items):

  • Item identity → snapshotted into nclex_attempt_items at administration time.
  • Student response (correct / incorrect, plus the actual answer) → nclex_attempt_answers.
  • Engine ability estimate at pick time → nclex_attempt_items.cat_theta_before.
  • Engine SE at pick time → nclex_attempt_items.cat_se_before.
  • Item difficulty used → nclex_attempt_items.cat_item_difficulty (snapshotted from difficulty_irt).
  • Difficulty source at pick time → nclex_attempt_items.cat_item_difficulty_source.
  • Time to respond → nclex_attempt_answers.duration_seconds (existing column).

This means recalibration has all the inputs it needs without further schema work on the response-capture side. The job just queries existing tables.

17.2 Audit history of difficulty changes — one new table

Per §5.3, recalibration overwrites nclex_bank_items.difficulty_irt with the 70/30 blended value on every weekly run. To preserve history of how each item's difficulty has evolved, we add a single new audit table: nclex_bank_item_calibration_history. One row per recalibration event per item.

Columns:

ColumnTypePurpose
idUUIDPrimary key
item_idTEXTThe bank item this row records (FK to nclex_bank_items.item_id)
calibrated_atTIMESTAMPTZWhen this recalibration happened
previous_valueNUMERICThe difficulty_irt value before this recalibration
new_valueNUMERICThe difficulty_irt value after the 70/30 blend
raw_empirical_valueNUMERICThe unblended empirical estimate the calibration computed (useful for debugging the blend)
previous_sourceTEXT'CURATOR_LABEL' or 'EMPIRICAL'
new_sourceTEXTAlways 'EMPIRICAL' (recalibration never writes back to CURATOR_LABEL)

17.3 No separate job-run table

An earlier draft proposed a separate nclex_calibration_job_runs table to record each weekly job execution (start/end time, items processed, error count). Rejected: the per-run summary can be derived from the audit table on demand, by grouping rows that share the same calibrated_at timestamp window (all rows from one run share the same timestamp). One new table is enough.

17.4 Why a separate table, not JSONB on the bank row

An alternative considered: stuff the calibration history into a JSONB array column on nclex_bank_items itself, with the engine reading the latest entry. Rejected for three reasons:

  • Engine performance. CAT picks an item by querying the bank for the closest-difficulty match. With difficulty_irt as NUMERIC, that's a fast indexed query. With JSONB, the engine has to pull every candidate's array, parse it, and extract the latest entry — per-item work on every single pick. A 92-item CAT does this 92 times per student. We'd turn a fast indexed query into a slow scan.
  • Snapshots break. §12.3 snapshots difficulty_irt into nclex_attempt_items.cat_item_difficulty at administration time. With NUMERIC that's a clean copy of one number; with JSONB you'd snapshot the whole array (which then grows over time — defeating "frozen at administration"), or you'd extract the latest value at snapshot time (which means the parse-and-extract dance happens on writes too).
  • Querying history is hard. Questions like "show items whose difficulty changed by >0.5 this month" or "roll back last week's calibration" become nightmare queries against JSONB arrays. Trivial against a separate audit table.

17.5 Retention — keep forever for v1

Both the audit table and the per-attempt response data are kept indefinitely in v1.

  • Audit table: small data — one row per item per week. Even at 10,000 items running for 5 years, that's ~2.6M rows. Trivial for Postgres.
  • Trimming defeats the audit's purpose. The whole value is being able to ask "what did this look like in the past."
  • If storage ever becomes a real concern (it won't at v1 scale), revisit then.

17.6 Where the recalibration job runs

Build-time decision. Two viable shapes:

  • A scheduled Cloudflare Worker (cron triggers) that calls a small Python service for the actual statistical fit using pyirt or similar.
  • A Supabase scheduled function (pg_cron) that uses simpler in-Postgres math.

What's locked here regardless of the runtime: the schedule (Sundays 02:00 UTC, per §5.3.2), the manual trigger pathway (admin button calls the same job logic with job_trigger = 'MANUAL'), the audit table that gets written to regardless of where the job runs. The Python-vs-pg_cron choice is a Sam-and-Claude -Desktop call when the build moves forward.

18. Out of scope for v1 / deferred

Explicit non-goals for v1 CAT:

  • 2PL or 3PL models — Rasch only for v1 (§4 default).
  • Statistically-validated pass-probability statement — needs real outcome data we don't have. v1 says "above/below standard," never a probability.
  • Pearson VUE-grade exposure control — we use a recency-window exposure filter (§15.2), not the multi-factor exposure-control schemes used in production high-stakes testing.
  • Hard content-blueprint enforcement — soft constraint only for v1 (§8 default).
  • Multi-stage testing (MST) — adaptive at the section level, not the item level. Not on the v1 roadmap.
  • Cases / trends in CAT — no longer out of scope. Reversed 2026-07-14: wrappers are IN for v1 (§7.4); administration mechanics settle at build time.
  • CAT in tutored programmes or readiness packs — CAT is custom-built only in v1. Programme activities and readiness packs use fixed-length modes only.
  • Cross-CAT theta carry-over — every CAT starts at medium; prior CATs don't influence the next CAT's starting point (§15.3 default).
  • Tutor-facing CAT analytics — tutors don't get to see student CAT results in v1 (CAT is a personal assessment tool). Could surface in v2.
